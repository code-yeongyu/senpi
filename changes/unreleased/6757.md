## 2026-11-15 - One active-tool rule for a session and a hand (senpi#6749)

### What changed

- `packages/coding-agent/src/core/runtime/active-tools.ts` (new): `resolveToolSelection`, `requestedActiveToolNames`, `directActiveToolNames`, `resolveEvalOnlyToolNames`, `armedEvalOnlyToolNames`, `toolExposureOf` and `isActivatedOnRegistration`, moved unchanged in behavior out of `AgentSession` and `createAgentSession`.
- `packages/coding-agent/src/core/agent-session.ts`: `_refreshToolRegistry`, `setActiveToolsByName`, `_resolveEvalOnlyToolNames` and `_isEvalOnlyPolicyArmed` call those functions; `_getToolExposure`, `_isActivatedOnRegistration` and the module's `EVAL_ONLY_TOOL_NAMES` are gone.
- `packages/coding-agent/src/core/sdk.ts`: the tool flags and `defaultTools` resolve through `resolveToolSelection`.

### Why

- A hand answering `describe_tools` must report the active set a local session would choose; sharing the session's own rules is the only way the two cannot drift.

### Why an extension could not handle it

- The active-set and eval-only rules are session internals; no extension can read or reuse them.

### Expected merge conflict zones

- MEDIUM: `setActiveToolsByName` and the end of `_refreshToolRegistry` in `agent-session.ts`; the tool-option block of `createAgentSession` in `sdk.ts`.

## 2026-11-15 - Tools declare that they act on the calling session (senpi#6749)

### What changed

- `packages/coding-agent/src/core/extensions/types.ts`: `ToolDefinition.sessionBound?: boolean`, recorded with the definition only.
- `packages/coding-agent/src/core/extensions/builtin/todotools/tools/todo.ts`, `builtin/goal/tool-registration.ts`, `builtin/tool-search/tool.ts`, `builtin/loop/tools.ts`, `builtin/schedule/tool.ts`, `builtin/relocate-session/index.ts`: `todo`, `create_goal`, `update_goal`, `get_goal`, `tool_search`, `schedule_wakeup`, `schedule_prompt`, `list_relocation_targets` and `relocate_session` declare `sessionBound: true`.

### Why

- Under the hosted parity design v4 the loop registers no tool, so these tools run on the hand too, reached with the session's state through the session port. The hand advertises them like every other tool, and the flag tells the loop which calls must carry that state. `runs: "brain"` cannot say this: `web_search`, `webfetch` and `ask_user` declare it, yet need no session state.

### Why an extension could not handle it

- The field is part of the tool definition contract the loader records.

### Expected merge conflict zones

- LOW: the `ToolDefinition` field list after `runs`; one line in each builtin's registration.

## 2026-11-15 - A hand tells a remote loop its tool list (describe_tools, senpi#6749)

### What changed

- `packages/coding-agent/src/modes/rpc/hand-tool-catalog.ts` (new): `describeHandTools` answers `{ tools, active, evalOnly, context }` with every tool the hand serves, nothing left out. `withToolCatalog` serves the `describe_tools` loop hook (payload `{ sessionId, idle, scope }`) beside the extension loop hooks, on any hand.
- `packages/coding-agent/src/modes/hand/tool-catalog.ts`: each declaration carries `sessionBound` (a boolean).
- `packages/coding-agent/src/modes/rpc/runtime-factory-loopless.ts`: `runLoopHooks` is `withToolCatalog(extensionLoopHooks(...), ...)` over the runtime's registry, tool selection and resource loader.
- `packages/coding-agent/src/modes/rpc/loopless-runtime-settings.ts`: `looplessToolFilters` becomes `looplessToolSelection` (`{ filters, initialActiveToolNames }`), resolved by the session's `resolveToolSelection`.

### Why

- senpi#6749: a hosted loop has to show its model exactly the tools a local session on the hand's machine shows. Nothing carried that list, the eval-only routing or the machine's context files and skills.

### Why an extension could not handle it

- The loop-hook lane and the loopless runtime's registry are the hand's own.

### Expected merge conflict zones

- LOW: the `runLoopHooks` member of the loopless runtime and the `buildToolRegistry` call above it.
