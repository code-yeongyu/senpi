## 2026-11-22 - MCP prompt commands follow the live prompt catalog (senpi#7249)

### What changed

- `packages/coding-agent/src/core/extensions/builtin/mcp/prompts.ts`: `createMcpPromptCommandSync` registers prompt commands now and after every `onMcpRegistrationChanged`; a handler resolves its server and prompt by name from the live catalog when invoked, and reports a prompt the server no longer offers instead of calling it.
- `packages/coding-agent/src/core/extensions/builtin/mcp/prompts.ts`: which commands are already registered is tracked per registrar (one extension instance's `pi`, in a `WeakMap`) instead of a process-wide set or the shared service, so two runners on one shared service and a replacement runner after reload each get their own commands. `registerMcpPromptCommands` has one call shape, `(pi, servers, current?)`; `registeredMcpPromptCommands(pi)` exposes the live name/description map.
- `packages/coding-agent/src/core/extensions/builtin/mcp/service.ts`: the service-held prompt-command name set and `isMcpPromptCommandRegistered` / `markMcpPromptCommandRegistered` are removed; dedup lives with the registrar.
- `packages/coding-agent/src/core/extensions/builtin/mcp/prompt-autocomplete.ts` (new): an `AutocompleteProviderFactory` that adds this registrar's prompt commands missing from the TUI's autocomplete snapshot to `/` completions; it adds nothing the snapshot already lists, so stacking it is harmless. It keeps the snapshot's order, except that a prompt exactly matching the typed name goes first, so Enter on the first row never submits a longer command.
- `packages/coding-agent/src/core/extensions/builtin/mcp/index.ts`: attach registers through that helper; `session_start` stacks the autocomplete wrapper; `session_shutdown` and removal of the MCP extension dispose the sync.

### Why

- Prompt commands were registered once at attach. A prompt from a later catalog generation (startup race, `prompts/list_changed`) never became a command, and a registered command kept the arguments it was registered with.
- The first fix deduplicated in a process-wide set (classic, shared service), so a second runner, or a new extension instance after reload, never received the commands. Interactive mode also snapshots extension commands when it builds its autocomplete, so a late prompt ran but was never suggested.

### Why an extension could not handle it

- The MCP builtin owns both the prompt catalog and the command registration; no other extension sees the catalog generations. The autocomplete fix uses the public `ctx.ui.addAutocompleteProvider` instead of changing interactive mode.

### Expected merge conflict zones

- LOW: the attach, `session_start` and two shutdown blocks in `mcp/index.ts`; `registerMcpPromptCommands` in `mcp/prompts.ts`; the prompt-command members removed from `McpService` in `mcp/service.ts`.
