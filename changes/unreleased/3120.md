### Added
- Native model blocking persists ordered provider/model rules and `!` exceptions in the agent directory's `model-blacklist.json`, without requiring a user extension. The `/models` picker alias offers Ctrl+Alt+B block/unblock beside favorites and shows saved changes pending a fresh runtime. Blocked models are excluded from catalog-based selection and rejected before transport, including stale model objects. Policy bytes load asynchronously; synchronous SDK factories with an existing policy file require an awaited `refresh()` before use, while a missing file remains a no-op ([#3120](https://github.com/code-yeongyu/senpi/pull/3120) by [@trac3r00](https://github.com/trac3r00)).

## 2026-10-11 - Native model blacklist (saved policy, runtime enforcement)

### What changed

- `packages/coding-agent/src/core/model-blacklist.ts`: fork-owned. Ordered `provider/model` glob rules with `!` exceptions (last match wins), saved as `<agentDir>/model-blacklist.json` (atomic temp+rename, 0600). Loading and refreshing use asynchronous reads; picker `getState` reads only the saved snapshot. Refreshes and toggles share a queue, and each toggle reads the latest file before writing. A missing file blocks nothing; an unreadable or malformed file blocks every model (fail closed). Exposes the picker's `ModelBlacklistAdapter`.
- `packages/coding-agent/src/core/model-runtime.ts`: `create()` asynchronously loads the policy once (the active snapshot) from `agentDir`, else beside `modelsPath`; `modelsPath: null` without `agentDir` stays isolated. Subsequent `refresh()`/`reloadConfig()` reload saved picker state without changing active enforcement. `getModels`, `getModel`, `getAllModels`, the `*OfType` getters, `getAvailable`, `getAvailableSnapshot`, `getAllAvailable` and `getPhysicalModel` filter blocked models; `prepareRequest`, `stream`, `streamSimple` and `resolveModel` reject a blocked model (including stale objects) before any transport. New `getModelBlacklistAdapter()` returns the adapter (pre-filter available rows, saved-vs-active `getState`, `toggle`); `getError()` reports a malformed policy.

### Synchronous compatibility limit

`createSync()` and `ModelRegistry.create()` check file metadata but do not read policy bytes. A missing policy remains a no-op; an existing or inaccessible policy starts fail-closed until the caller awaits `refresh()`. Callers needing an initialized policy snapshot should use `await ModelRuntime.create()` and, if needed, pass that runtime to `new ModelRegistry(runtime)`. Isolated in-memory runtimes remain immediately usable. External file edits become visible in picker saved state on async refresh or toggle, not on every synchronous `getState()` call.

### Why

Users without any blacklist extension need the same block/unblock behavior, enforced from startup (including `--list-models`), and a toggle must survive restart without changing the running process.

### Why an extension could not handle it

Catalog filtering and the pre-transport dispatch guard belong to the runtime that owns the catalog and transport, and must apply before extensions load.

### Expected merge conflict zones

- LOW: the getter bodies, `prepareRequest`/`stream`/`streamSimple`/`resolveModel` entry lines, and the constructor tail in `model-runtime.ts`; `model-blacklist.ts` is fork-only.

## 2026-10-11 - `ExtensionUIContext.setModelBlacklist` (model picker blacklist adapter)

### What changed

- `packages/coding-agent/src/core/extensions/types.ts`: new `ModelBlacklistState` (`blocked`, `activeBlocked`, `rule?`) and `ModelBlacklistAdapter` (`getModels`, `getState`, `toggle`) types, and an optional `ExtensionUIContext.setModelBlacklist?(adapter | undefined)`. Only interactive mode implements it; RPC, app-server and the no-op context leave it absent, so extensions feature-detect it.
- `packages/coding-agent/src/core/extensions/index.ts`: re-exports the two new types.

### Why

An extension that owns a model-blacklist policy needs to list, mark and toggle models in the interactive `/model` picker, including models the runtime filtered out at startup.

### Why an extension could not handle it

The picker is not an extension surface; the adapter is the extension-facing seam that lets the policy stay in the extension.

### Expected merge conflict zones

- LOW: `types.ts` immediately above `ExtensionUIContext` and the end of that interface; the export lists in `index.ts`.

## 2026-10-11 - Model picker blacklist key and `/models` alias

### What changed

- `packages/coding-agent/src/modes/interactive/components/model-selector.ts`: `ModelSelectorComponent` takes an optional `ModelBlacklistAdapter` (10th constructor argument). With it, the picker merges `adapter.getModels()` into the runtime's available models (the runtime's copy wins), marks each row from `adapter.getState()` (`blocked`, `blocked (restart required)`, `unblocked (restart required)`), and `app.models.toggleBlacklist` (Ctrl+B) calls `adapter.toggle()` for the highlighted row with a pending state and an error line. Models absent from the runtime snapshot stay listed and searchable but `handleSelect` refuses them until a fresh process. The highlighted row is kept by id across a toggle and across the background catalog refresh (which used to snap back to the current model). Without an adapter the picker, its hints and Ctrl+B (search-box cursor-left) are unchanged.
- `packages/coding-agent/src/modes/interactive/interactive-mode.ts`: `createExtensionUIContext` implements `setModelBlacklist`, storing the adapter on the mode (shared by every UI context it creates, cleared when extension UI state resets) and `showModelSelector` passes it to the picker. `/models` routes to `handleModelCommand` exactly like `/model`, and its argument completion matches `/model`.

### Why

The blacklist policy lives in an extension, but the model picker is interactive-mode internal: only the host can add a key to it, list models the runtime filtered out, and refuse to select them.

### Why an extension could not handle it

The picker component, `/model` routing and the `ExtensionUIContext` implementation are interactive-mode internals; an extension can only reach them through the new optional `ctx.ui.setModelBlacklist` adapter.

### Expected merge conflict zones

- `model-selector.ts`: the constructor signature, `loadModelsFromSnapshot`, `refreshModels`, `updateList`, `handleInput` and `handleSelect`.
- `interactive-mode.ts`: the `ExtensionUIContext` import list, the `autocompleteProviderWrappers` field neighborhood, the model argument completion loop, the extension UI reset, `createExtensionUIContext`, the `/model` submit branch and `showModelSelector`.
