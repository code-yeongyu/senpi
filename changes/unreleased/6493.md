## 2026-11-12 - The secret lock's SQLite open follows no link, and no open of another name closes a descriptor of a held lock file (senpi#6493)

### What changed

- `packages/coding-agent/src/modes/rpc/sqlite-file-identity.ts`: `openExpectedFile(path, validate, open, close, noFollow)` takes `noFollow`.
  - With `noFollow`, `open` passes SQLITE_OPEN_NOFOLLOW. Its refusal, SQLITE_CANTOPEN_SYMLINK (classified by code only), answers `replaced`.
  - Without `noFollow`, `path` is checked by name once more right before `open`, and a refusal there opens nothing.
  - The comment on the one-at-a-time section now says what SQLite's open does: it resolves the path with an `lstat` per component, then opens `O_RDWR | O_NOFOLLOW`. It also says which window remains without `noFollow`.
- `packages/coding-agent/src/modes/rpc/ownership-safe-lock.ts`:
  - Under bun:sqlite, a lock taken with `validateFile` opens with `SQLITE_OPEN_READWRITE | SQLITE_OPEN_CREATE | SQLITE_OPEN_NOFOLLOW`, so its path must contain no symbolic link. Under node:sqlite, which takes no open flags, the open uses the name recheck.
  - A held lock taken with `validateFile` records the identity of the file it proved. The new export `openBesideHeldLocks(path, flags, mode)` refuses with `ELOCK_FILE_ALIAS` when `path` names a held lock file before the open, or when the descriptor is one after it. Such a descriptor is kept open, unused, until that lock is released. The returned `close()` re-checks before closing.
- `packages/coding-agent/src/modes/rpc/socket-transport.ts`:
  - `readSecretEntry` and `readSocketSecret` open through `openBesideHeldLocks`.
  - The directory sync opens with `O_DIRECTORY`.
  - The staging open (`O_CREAT | O_EXCL`, so always a new file) is unchanged and now has a comment.
- `packages/session-backends/sqlite-bun/src/bun-sqlite.d.ts` (the workspace's one `bun:sqlite` declaration): `new Database(filename, flags)` accepts numeric `SQLITE_OPEN_*` flags, and `constants` declares the three flags the lock uses.
- `packages/coding-agent/src/modes/rpc/endpoint-reservation-file.ts`: the store's checked open passes `noFollow: false` under both drivers. Its path is not canonicalized, so a symlinked parent directory must keep working.

### Why

- Review of senpi#6482 at b7cc535320, LOW 1: SQLite's by-name open followed a symbolic link swapped in at the lock file's name after its `lstat`. The open of a device it names can block the process synchronously (a serial tty without CLOCAL). The comment claimed the SQLite open does not wait on the file.
  - bun:sqlite takes numeric open flags, including `constants.SQLITE_OPEN_NOFOLLOW`.
  - node:sqlite always opens with `SQLITE_OPEN_READWRITE | SQLITE_OPEN_CREATE | SQLITE_OPEN_URI` (`TODO(cjihrig): Support additional flags`). SQLite's URI parameters have no no-follow option, so node gets the narrower name recheck.
- Review of senpi#6482 at b7cc535320, LOW 2: closing any descriptor of a file drops all of this process's POSIX locks on it (senpi#6478). A writer in the directory that hard-links the secret name to the lock file made the holder's own read under the lock drop that lock. The same applied to a directory name swapped for such a link at the directory sync. Another process then took the lock inside the holder's critical section.

### Why an extension could not handle it

- The publish lock and the socket secret are RPC host internals that run before extension loading.

### Expected merge conflict zones

- LOW: `openExpectedFile`/`checkedOpen` in `sqlite-file-identity.ts`; `openLockDatabase`, `openChecked` and the release in `attemptUntil` in `ownership-safe-lock.ts`.
- LOW: `readSecretEntry`, `syncDirectory` and `readSocketSecret` in `socket-transport.ts`.

### Fixed
- The RPC socket-secret repair lock no longer follows a symbolic link swapped in at its name before SQLite opens it. Under Bun the open refuses any link; under Node the name is checked again right before the open. Reading the secret or syncing its directory no longer closes a descriptor of the held lock file when a name is a hard link to it, so another process can no longer take the lock inside the repair ([#6493](https://github.com/code-yeongyu/senpi/pull/6493))
