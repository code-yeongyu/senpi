## 2026-11-22 - A dead tui endpoint keeps naming its session (senpi#7341, fixes #2680)

### What changed

- `packages/coding-agent/src/modes/rpc/host-tui-session-record.ts` (new): `TuiEndpointSession`, `TuiSessionRecord`, `writeTuiSessionRecord` (atomic tmp+rename), `readTuiSessionRecord` and `tuiSessionRecordMatches` — the session a `tui` endpoint holds, on disk.
- `packages/coding-agent/src/modes/rpc/host-daemon-paths.ts`: `tuiSessionFile` (`tui-session.json`) on `HostDaemonPaths`/`hostDaemonDirectoryPaths`, documented in the layout diagram.
- `packages/coding-agent/src/modes/rpc/host-status-all.ts`: `tuiOwner` falls back to the session record when the terminal did not answer, only when the record's `pid` and `processStartTime` match the current generation (`readHostRegistration`), so a reused socket path never inherits the previous session.
- `packages/coding-agent/src/modes/rpc/host-gc.ts`: `HostGcOptions.keepDeadNamingSessions` keeps a dead endpoint that still names a session (kept reason `session_record`), evaluated inside the endpoint's ensure lock after the three-part evidence passes.
- `packages/coding-agent/src/modes/rpc/host-gc-pass.ts`: the budgeted pass passes `keepDeadNamingSessions`, so an uncleanly exited terminal's endpoint survives automatic reaping; explicit `senpi host gc` reclaims it unchanged.

### Why

- `host status --all` read a dead `tui` row's `owner` from the live `list_sessions` answer only, so after an unclean exit the row stayed `alive: false` with `owner.session`/`owner.cwd` `null`: a client could see that a terminal existed but not which session it held, could not open its transcript and could not queue a message to it.

### Why an extension could not handle it

- The record is written under the endpoint's ensure lock next to `endpoint.json`, the daemon directory's identity surface that only the engine owns; `status --all`, `gc` and the sweep judge endpoints from exactly those files, which no extension can write.

### Expected merge conflict zones

- LOW: `host-status-all.ts` (`tuiOwner`), `host-gc.ts` (`gcEndpoint` evidence flow, kept-reason union), `host-daemon-paths.ts` (directory file list).

## 2026-11-22 - A dead tui endpoint keeps naming its session (senpi#7341, fixes #2680)

### What changed

- `packages/coding-agent/src/modes/interactive/session-control-registry.ts`: `registerTuiEndpoint` takes the terminal's `session` and writes `tui-session.json` inside the registration's ensure lock, after `endpoint.json`.
- `packages/coding-agent/src/modes/interactive/session-control-endpoint.ts`: registration passes `{ id, path, name, cwd }` from the live session; the dead-`tui` sweep passes `keepDeadNamingSessions: true`, so a dead endpoint that still names a session survives another terminal's registration.

### Why

- A terminal that died uncleanly left nothing on disk naming its session, and the startup sweep removed its endpoint within seconds of the next registration — the "kept for its next run" handle was lost twice over.

### Why an extension could not handle it

- Only registration, under the endpoint ensure lock, can write the record beside `endpoint.json`; an extension cannot take that lock or own the daemon directory.

### Expected merge conflict zones

- LOW: `registerTuiEndpoint` options and body; the `gcHostEndpoints` sweep call in `openEndpoint`.
