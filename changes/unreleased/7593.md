## 2026-11-27 - A run's launch profile carries its opener's request for a designated answerer (senpi#7593, senpi#7572)

### What changed

- `packages/coding-agent/src/core/agent-session-runtime.ts`: `AgentSessionLaunchProfile.designatedAnswerer` records that the opener asked that only the run's designated answerer resolve its prompts (`open_session.designatedAnswerer`); only the flag, never the answer key

### Why

- A run that asked must keep the rule across a host handover: the successor reopens it from the parked record built from this profile, and reopens it with no answerer instead of with the rule off.

### Why an extension could not handle it

- The parked record and the successor's reopen are built by the RPC host from the launch profile before any extension of the session loads.

### Expected merge conflict zones

- LOW: the `AgentSessionLaunchProfile` field list (one field after `persona`).

## 2026-11-27 - `ExtensionUIContext.capabilities.answerer` (senpi#7593, senpi#7572)

### What changed

- `packages/coding-agent/src/core/extensions/types.ts`: optional read-only `capabilities.answerer?: "present" | "absent"`; an RPC session reports `"absent"` while its run asked for a designated answerer and none is attached. Read it at ask time. Absent for every other UI, so an extension that never reads it behaves as before.
- `packages/coding-agent/src/core/extensions/runner.ts`: the prompt-wrapped UI context reads `capabilities` through instead of copying it once, so a change while the session runs reaches every extension.

### Why

- A prompt raised in a run nobody may answer would wait forever; the permission system needs to know at ask time that nobody can answer.

### Why an extension could not handle it

- Which connections are attached to a run is known only to the RPC host; the UI context is the one channel from host to extensions.

### Expected merge conflict zones

- LOW: the `capabilities` field of `ExtensionUIContext` (one optional member beside `secretInput`); `wrapUIPromptContext` in `runner.ts` (one getter after the spread).

## 2026-11-27 - Only a run's designated answerer resolves its prompts, when its opener asks (senpi#7593, senpi#7572)

### What changed

- `packages/coding-agent/src/modes/rpc/prompt-answerer.ts` (new): per-run answer key (32 random bytes, returned once in the opener's `open_session` reply; the host keeps its SHA-256 digest in memory, compared with `timingSafeEqual`), the answerer set, the default (`DESIGNATED_ANSWERER_BY_DEFAULT`, false)
- `packages/coding-agent/src/modes/rpc/prompt-answerer-gate.ts` (new): designation at open and attach, the reply fields (`answerer`, `answerKey`, `answererUnavailable`), and the router check that refuses an answer from anyone else with `prompt_answerer_required` before dispatch, so it covers worker isolates; the key is stripped from answers before dispatch
- `session-router-routing.ts`, `session-router-open-result.ts`, `session-attachment-commands.ts`, `session-router-attachments.ts`, `session-router-context.ts`: call sites; `host-capabilities.ts`: `prompt_answerer`; `method-classes-schema-host.ts`, `rpc-host-command-types.ts`, `rpc-host-response-types.ts`, `rpc-question-types.ts`, `attachment-types.ts`: the wire fields; `session-router-open-profile.ts`, `host-handover-parked.ts`, `host-handover-parked-open.ts`: the flag travels through a handover (a malformed flag invalidates the parked record)

### Why

- A program a run starts holds the user's RPC keys and could attach and approve the prompt that blocks the run (senpi#7572). Attachment and self-declared roles cannot tell it from the person's client.

### Why an extension could not handle it

- Answers are routed by the RPC host router before any session or extension sees them.

### Expected merge conflict zones

- LOW: one gate call beside `attachmentGate` in `session-router-routing.ts`; one field each beside `persona` in the parked record and its reopen command.
