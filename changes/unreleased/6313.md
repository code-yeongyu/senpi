## 2026-11-10 - A relayed peer-agent delivery runs under the receiving session's own preset (senpi#6305)

### What changed

- `turn-origin.ts`: a fourth turn origin, `peer`, for a turn opened by an agent's relayed delivery on a delegated connection whose host-mode delegation the forwarder granted `peer_agent`. `decidingTurnIsDelegated` is false for it, so the permission decision treats the turn as the session's own work (a client-named preset, a live parent, the host default) and never runs it above that preset.

## 2026-11-10 - admit_external_message marks an agent's relayed delivery as a peer turn (senpi#6305)

### What changed

- `admit-external-message-command.ts`: `deliveryTurnMark` returns `peer` only when the connection is delegated and the forwarder granted it `peer_agent` (`ConnectionRoles.grantedByForwarder`, read from the live authority word, never from the record or a client claim); the record's `sender.kind` of `agent` is only a consistency check.
- `connection-authority.ts`, `delegation-declaration.ts`, `connection-roles.ts`: `peer_agent` is a third host-mode role (word bit 2; retired moves to bit 3 and the epoch field to 28 bits), declarable only in `declare_delegation`, never claimable with `set_client_info`, and ignored on a legacy-mode delegation.
- `custom-capability.ts`, `host-capabilities.ts`: hosts advertise `peer_agent_role_v1`, so a forwarder declares the role only to an engine that understands it. A steer still joins the running turn; every other delivery keeps the connection's origin, so a non-agent or sender-less delivery from a remote device still asks.
- `test/suite/regressions/6305-peer-delivery-receiver-preset.test.ts`: on a host whose default preset is `full-access`, an agent's delivery on a connection the forwarder granted `peer_agent` runs its gated call without asking; a drive-granted connection without that role that labels its sender an agent still asks, and so do an `external` sender and a delivery with no sender on a `peer_agent` connection.

## 2026-11-10 - A tool-owned permission request keeps autoApproveAsk (senpi#6305)

### What changed

- `parsers.ts`: `toolOwnedPermissionRequests` passes a tool's `autoApproveAsk` through instead of dropping it, so a tool can ask the system to approve an `ask` decision for a call while `allow` and `deny` rules still match its request (an omo reply to the peer that messaged the run, oh-my-openagent#12954). `ToolPermissionRequest` (`core/extensions/types.ts`) declares the field.

## 2026-11-10 - `ToolPermissionRequest` carries `autoApproveAsk` (senpi#6305)

### What changed

- `packages/coding-agent/src/core/extensions/types.ts`: `ToolPermissionRequest` gains an optional `autoApproveAsk: true`, so a tool's own `permissionParser` can have an `ask` decision for one call approved without a prompt while `allow` and `deny` rules still match its request.

### Why

An omo reply to the agent that messaged the run must not wait on an approval nobody can give, but a user's `deny` rule for that tool must still apply; returning no request at all dropped the deny (oh-my-openagent#12954 review).

### Why an extension could not handle it

The extension tool contract is this type; the permission system reads only the fields it declares.

### Expected merge conflict zones

- None: one additive optional field.
