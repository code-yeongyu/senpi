## 2026-11-22 - A held repaint keeps rows that moved up across the viewport top (senpi#3669)

### What changed

- `packages/tui/src/viewport-shift.ts`:
  - New `movedAboveViewport` finds how far the last frame's visible rows moved up across the old viewport top.
  - Re-laid rows are new strings, so each upward offset is scored by the prefix every changed old visible row shares with the new row at that offset.
  - An offset counts only when it scores strictly higher than staying in place.
  - `shiftedBlockMoved` became `shiftedBlockCheck`, which builds one check per frame for every candidate shift.
  - The check has no fixed `2 x height` scan floor. The walk stops at the frame's first changed row, and one Z-array pass over the unchanged rows above the viewport answers the repeated-rows question for every shift.
  - `insertedAboveViewport` takes that first changed row.
- `packages/tui/src/tui.ts`:
  - `renderHeldRepaint()` takes `firstChanged` and starts its rewrite `movedAboveViewport` rows higher when no insertion above was found.
  - In `doRender()`, a held frame whose visible rows moved up takes `renderHeldRepaint()` instead of the visible-row diff.
  - `planViewportInsertScroll` is passed `firstChanged`.
- `packages/tui/src/viewport-insert-scroll.ts`: `planViewportInsertScroll` takes `firstChanged` and asks `shiftedBlockCheck` for its single shift.
- `packages/tui/test/regression-3669-held-relayout-rows.test.ts` (new): every row seen on screen stays in the buffer at each held frame of a table that re-lays out while growing, and an insertion above past identical rows longer than twice the screen height pushes no copies.

### Why

- `packages/tui/src/tui.ts`, `packages/tui/src/viewport-shift.ts`: with the scrollback replay hold on (#2836), a re-layout that shortened rows above the viewport (a wrapped table cell unwrapping) while the table grew below moved the old top row above the viewport.
  - The held frame overwrote that row's screen row, so the row was missing from the scrollback until the catch-up replay.
  - With an unchanged line count, the frame never reached `renderHeldRepaint()`.
- `packages/tui/src/viewport-shift.ts`, `packages/tui/src/viewport-insert-scroll.ts`: the fixed scan floor hid an insertion above when the identical rows above the viewport ran longer than twice the screen height, so each frame pushed extra copies.

### Why an extension could not handle it

- `packages/tui/src/tui.ts`, `packages/tui/src/viewport-shift.ts`, `packages/tui/src/viewport-insert-scroll.ts`: the repaint start row and the rows written into native scrollback are private renderer state (`previousLines`, viewport top, hardware cursor, synchronized frame writes).

### Expected merge conflict zones

- LOW: `packages/tui/src/tui.ts`: the start row and signature of `renderHeldRepaint()`, its two call sites, the new held branch before the visible-row diff in `doRender()`, and the `planViewportInsertScroll` call. `viewport-shift.ts` and `viewport-insert-scroll.ts` are fork-only.
