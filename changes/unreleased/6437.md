## 2026-11-11 - A published socket secret survives a failed cleanup or directory fsync (senpi#6437)

### What changed

- `packages/coding-agent/src/modes/rpc/socket-transport.ts`: after `link()` publishes the candidate, the private `publishSocketSecretIfAbsent` returns `published` even when the directory fsync fails or this attempt's staging file cannot be removed. Each of those is reported as a process warning, `SENPI_RPC_SOCKET_SECRET_DIRECTORY_SYNC_FAILED` or `SENPI_RPC_SOCKET_SECRET_STAGING_LEFT_BEHIND`, with the path and cause in `detail`. When `link()` itself fails, the staging file is removed first and the `link()` error is reported, never a cleanup error after it.
- `packages/coding-agent/src/modes/rpc/socket-transport.ts`: when `link()` fails with `ENOTSUP`, `EOPNOTSUPP` or `ENOSYS`, or with `EPERM` on a filesystem whose Linux statfs magic shows it has no hard links (msdos/vfat, exfat), the publication throws `SocketSecretHardLinksUnsupportedError` with `reason: "hard_links_unsupported"`, the path, and the `link()` error as `cause`. Any other `EPERM` is a sandbox, MAC policy, or immutable or append-only directory refusing the link, and it throws `SocketSecretLinkRefusedError` with `reason: "link_refused"` and the `link()` error as `cause`. There is no fallback to writing the final path, because this design never opens that path for writing.
- `packages/coding-agent/src/modes/rpc/socket-transport.ts`: the repair path inside `ensureSocketSecret` returns its secret once `rename()` installed it, even when the directory fsync after it fails. That failure is the same `SENPI_RPC_SOCKET_SECRET_DIRECTORY_SYNC_FAILED` warning.
- `packages/coding-agent/src/modes/rpc/socket-transport.ts`, `packages/coding-agent/src/modes/interactive/session-control-endpoint.ts`: `createSocketSecret` takes an optional warning reporter, with `process.emitWarning` as the default. The interactive TUI's control endpoint passes its `surface.notice`, so these warnings are shown in the TUI instead of being written to stderr under its frame.
- Tests: `test/suite/regressions/desktop-4199-socket-secret-publish-failures.test.ts` (new) injects each of those failures, including both EPERM cases and a repair whose directory fsync fails. `desktop-4199-socket-secret-tui-warnings.test.ts` (new) registers a TUI control endpoint with a failing staging cleanup. `desktop-4199-socket-secret-staging-cleanup.test.ts` now injects a close failure that leaves the descriptor open.

### Why

- These are review findings on senpi#4369. A failed staging `unlink` in `finally` replaced a `published` result or the `link()` error. A directory fsync failure failed the process that had already won the race, so it returned an error while every other reader used its secret. On a filesystem without hard links the raw `link()` errno reached the caller with nothing naming the cause. The close-failure test closed the descriptor before throwing, so it never covered a close that leaves the descriptor open.
- Review LOWs on senpi#6437: the repair path still threw on a directory fsync failure after `rename()` had installed its secret. Every `EPERM` was blamed on the filesystem, although on macOS a sandbox, MAC denial or immutable directory also returns it. The TUI's warnings went to stderr under its frame.

### Why an extension could not handle it

- The RPC host, its supervisor and the terminal control endpoint provision the secret before any extension loads.

### Expected merge conflict zones

- LOW: `publishSocketSecretIfAbsent` and `replaceSocketSecret` in `socket-transport.ts`; the `createSocketSecret` call in `session-control-endpoint.ts`.

### Fixed
- On POSIX, a process that publishes the RPC socket secret no longer fails when the directory fsync or the staging-file cleanup after the publication fails. Those failures are now warnings, and so is a failed directory fsync after a repair. In the interactive TUI these warnings are shown as notices, not written to stderr. A filesystem without hard links gets a typed refusal that names the cause, and an `EPERM` from a permission or policy check is reported as that, not as missing hard links ([#6437](https://github.com/code-yeongyu/senpi/pull/6437)).
