## 2026-11-15 - A loop-hook session queue is entered in O(1) and restarts a waiter only on a real settle (senpi#5898)

### What changed

- `packages/agent/src/execution/loop-hook-session-queue.ts`: a session keeps only its newest entry's settle promise, and a new call chains on it (O(1)), instead of copying the queue into `Promise.all` (O(n) per call, O(n²) for a stuck session that keeps receiving calls). A waiter's bound restarts on a per-session progress signal that fires only when an entry settles, so a call ahead that merely leaves (timed out or cancelled while it waited) restarts nothing. The timer cap stays module-local.
- `packages/agent/src/execution/loop-hook-host-hand.ts`: the `queueWaitMs` doc names `setTimeout`'s range instead of the constant.
- `packages/agent/src/index.ts`: no longer exports `MAX_TIMER_DELAY_MS`.

### Why

- Review of #6782: the per-call restart was unpinned by tests (L1), the constant was public API with no consumer (L2), and entering the queue cost O(n) per call (L3).

### Why an extension could not handle it

- The loop-hook link is agent-core protocol.

### Expected merge conflict zones

- LOW: `createLoopHookSessionQueues` and its wait helpers in `loop-hook-session-queue.ts`, the `queueWaitMs` doc, and the loop-hook export block of `index.ts`.
