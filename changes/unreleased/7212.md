## 2026-11-22 - RPC subscription replies (senpi#4669)

### What changed
- `packages/coding-agent/src/core/event-bus.ts` documents the reply function supplied on subscription.

### Why
- Initial state belongs to the new subscriber, not every client already connected.

### Why an extension could not handle it
- Extensions consume this channel; the runner defines its payload.

### Expected merge conflict zones
- The RPC subscription channel declaration.

## 2026-11-22 - Scope snapshot delivery to the subscribing client (senpi#4669)

### What changed
- `packages/coding-agent/src/core/extensions/runner.ts` supplies a reply function valid only during the subscription notification, and `replayRpcState` runs that same notification for one receiver without a new subscription.

### Why
- Broadcasting a snapshot would send existing clients a duplicate initial event.

### Why an extension could not handle it
- Only the runner knows which RPC listener just subscribed.

### Expected merge conflict zones
- `onRpcEvent` listener registration.

## 2026-11-22 - Replay live terminal state on RPC subscription (senpi#4669)

### What changed
- `packages/coding-agent/src/core/extensions/builtin/terminal/extension.ts` binds replay to the session lifecycle.
- `packages/coding-agent/src/core/extensions/builtin/terminal/extension-state.ts` uses the live bundle to report monitor and wake-source snapshots.

### Why
- Late listeners missed the initial publication, and terminal wake-source changes stayed on the internal bus.

### Why an extension could not handle it
- The terminal builtin owns the monitor registry and background session state.

### Expected merge conflict zones
- Terminal state publication and bundle binding.

## 2026-11-23 - Job widget state goes to the new subscriber only (senpi#4669)

### What changed
- `packages/coding-agent/src/core/extensions/builtin/job-widgets/extension.ts` answers a new RPC subscriber through the subscription's reply with the current `job_widget_state`, instead of republishing to every subscriber.
- `packages/coding-agent/src/core/extensions/builtin/job-widgets/session-host.ts` drops `resendJobWidgetState`, which only that republish used.

### Why
- A republish reached clients that already had the state and every in-process listener; a client that just attached needs it for itself.

### Why an extension could not handle it
- This is the builtin's own resend path.

### Expected merge conflict zones
- The job-widgets `session_start` subscription wiring.

## 2026-11-23 - Replay extension state to a client that attaches to an open session (senpi#4669)

### What changed
- `packages/coding-agent/src/modes/rpc/session-attachment-commands.ts` sends an `attach_session` caller that declared extension events the session's current extension state, whatever the opener declared; a compact attach gets it only after its admission answered and its baseline is queued.
- `packages/coding-agent/src/modes/rpc/session-binding.ts` and `packages/coding-agent/src/modes/rpc/connection-handler.ts` run that replay through the session's extension runner.
- `packages/coding-agent/src/modes/rpc/session-event-writer.ts` delivers those records to the one attachment, without retaining them for later attachments, and checks at write time that the same attachment still holds the session.

### Why
- The session's subscription already existed, so its replay at subscription never reached a client that attached later; an idle session left that client without state until the next change.

### Why an extension could not handle it
- Only the shared host knows which connection just attached and can address that connection alone.

### Expected merge conflict zones
- The `attach_session` admission path and the session binding's handler surface.
