## 2026-11-11 - The secret lock and the reservation store open only the validated file; busy retry and per-state claim answers (senpi#6440)

### What changed

- `packages/coding-agent/src/modes/rpc/sqlite-file-identity.ts` (new): `openExpectedFile(path, expected, open, close)` runs a synchronous SQLite open and refuses unless SQLite opened the file `expected` names. On Linux and macOS it lists the process's open regular files, by descriptor and identity, before and after the open, and accepts only when the added descriptors are all `expected`. It answers `replaced` when none is `expected` and `expected` was not already open. It answers a retryable `busy` when the listing cannot tell which descriptor is SQLite's: `expected` was already open in this process (SQLite may reuse a parked descriptor of it) and none of the added ones is `expected`, or an `expected` descriptor was added beside another file. Checked opens run one at a time per process, so contenders in the same process cannot hide each other's opens. Every filesystem call in it is asynchronous, because the secret lock reaches it from the RPC session path. On every platform it checks that the name is still a regular file with that identity. On Windows that name check covers SQLite's own handle, because SQLite opens without FILE_SHARE_DELETE.
- `packages/coding-agent/src/modes/rpc/ownership-safe-lock.ts`: an optional `expectedFile`; a lock file SQLite opened that is not that file is refused with `LockFileReplacedError` (`ELOCK_FILE_REPLACED`) and never retried as busy. An open that cannot be proven yet throws `LockFileBusyError` (`ELOCK_FILE_BUSY`), which is retried like contention until the deadline and then thrown; no lock is ever taken on an unproven file. `sqlite-file-identity.ts` loads lazily, only when `expectedFile` is passed, so it stays out of the lifecycle supervisor's startup graph.
- `packages/coding-agent/src/modes/rpc/socket-transport.ts`: the per-secret publish lock passes the identity it validated through its own descriptor as `expectedFile`.
- `packages/coding-agent/src/modes/rpc/endpoint-reservation-file.ts` (new): the store's open path moved out of `endpoint-reservation-store.ts` (owner-only precreate, no-follow validation, runtime loading). The file SQLite opened must be the validated one (`openExpectedFile`); an open that cannot be proven yet is refused as `store_busy`, which `retryWhenBusy` retries. Before the first read `<db>-journal` must be absent or a private regular file.
- `packages/coding-agent/src/modes/rpc/endpoint-reservation-busy.ts` (new): `isBusy`, moved, and `retryWhenBusy(run, policy?)`. It retries only `store_busy`, waits asynchronously between a bounded number of attempts (20 by default, with waits of 10 to 100 ms), and ends with a typed `store_busy` whose cause is the last refusal.
- `packages/coding-agent/src/modes/rpc/endpoint-reservation-error.ts` (new): `EndpointReservationError` (now accepts `ErrorOptions`) and `ReservationRejection`, with the new `role_released`. `endpoint-reservation-store.ts` re-exports both.
- Correction to the 2026-10-26 entry "Reservation reads report typed store contention (senpi#4372)", recorded here because tracker entries are append-only: senpi#4372 added the whole endpoint reservation store, not only the busy-read mapping. `endpoint-reservation-store.ts` (new) is a private SQLite database beside the endpoint lock with one `BEGIN IMMEDIATE` transaction per transition: `reserve` (expected roles, schema 2), `offer` (a fresh 256-bit nonce), `claim` (consumes the nonce once and records the participant), `grant` (the recorded participant, from the recorded issuer, bound to a SHA-256 commitment), `cancel` (revokes offers and keeps claimed identities), `markServing` (every expected role granted, failing closed on an unreadable set) and `release`. The file was created owner-only and validated through a no-follow descriptor, every refusal was a typed `EndpointReservationError`, and contention was `store_busy`. `bun-sqlite.d.ts` gained the `bun:sqlite` reference for the build typecheck.
- `packages/coding-agent/src/modes/rpc/endpoint-reservation-store.ts`: a claim retry by the recorded participant gets `already_granted_to_caller` on a granted row, and a released row is refused with `role_released`. A failed `ROLLBACK` no longer replaces the transition's own error; it is attached to that error as `rollbackError`, and busy refusals keep the raw error as `cause`. The claim comment now says `BEGIN IMMEDIATE` is what makes the claim atomic.

### Why

- Review findings on senpi#4371 and senpi#4372. The lock file and the store file were validated through one descriptor, and SQLite then reopened them by name. A name swapped in between, or a link on Windows (where O_NOFOLLOW is 0), left SQLite holding another file. For the lock, that serializes nothing. The old post-open `lstat` checked only the name, which a swap undone after SQLite's open passes; the descriptor check must hold also while another connection of the same process has the file open, the lock's contention case (review of senpi#6440). The store's rollback journal, which SQLite reads back and writes through its name, was never checked.
- The store's 100 ms busy wait blocks the event loop, and callers had no retry policy.
- A granted or released role answered `already_claimed_by_caller`, which hid its real state. A failed `ROLLBACK` replaced the error the caller needed.

### Why an extension could not handle it

- The publish lock and the reservation store are RPC host internals that run before extension loading.

### Expected merge conflict zones

- LOW: the `acquireOwnershipSafeLock` options and `openLockDatabase`.
- LOW: the imports at the top of `endpoint-reservation-store.ts`, its `claim`, `#transaction` and `#read`, and `openEndpointReservationStore`, whose open path moved to `endpoint-reservation-file.ts`.

### Fixed
- The RPC socket-secret repair lock and the endpoint reservation store refuse a file swapped between their validation and SQLite's open.
