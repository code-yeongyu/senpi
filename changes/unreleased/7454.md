## 2026-11-25 - A host restart does not re-run a run that ended on a provider error (senpi#7449)

### What changed

- `packages/coding-agent/src/core/host-restart-continuation.ts`: `restartVerdict` reads the stop reason of the newest model response in the engine-started run. When that response ended with `stopReason: "error"` (a provider 429 `rate_limit_error`, for example), the run is not continued: the interrupted-run hold stays, and `restartHoldData()` names it with the new `RestartHoldReason` `ended_on_provider_error`. A run the restart cut (aborted, or mid-tool) still continues under the senpi#7020 / senpi#7079 rules, including `RESTART_CONTINUATION_LIMIT`.

### Why

- An RPC host stopped itself on idle, and the next host start continued every session whose last engine-started run was unfinished. Thirty-one of those turns had already ended on their own with a provider 429, so within about 2 s each one sent another request into the same limit. The restart had not cut those runs, so it has nothing to continue.

### Why an extension could not handle it

- The restart decision runs inside `AgentSession` while a reopened session binds, before any extension can see a turn.

### Expected merge conflict zones

- LOW: the backward walk in `restartVerdict` and the `RestartHoldReason` union in `host-restart-continuation.ts`.

## 2026-11-25 - A restarted goal waits out its provider backoff (senpi#7449)

### What changed

- `index.ts`: on `session_start` with reason `startup` or `resume`, an active goal whose newest run ended on a provider error (`stopReason: "error"`) re-arms its provider-retry wait instead of queueing a continuation during start. Held engine turns (senpi#3853) and `reload` keep their existing paths, and a goal whose newest answer ended cleanly still continues at once.
- `session-start-continuation.ts`: `readTrailingProviderFailure()` returns that failed answer and the number of runs in a row that ended on a provider error (the retry attempt the backoff had reached), back to the last user message.
- `monitor-continuation.ts`: `resumeProviderRetryAfterRestart()` arms the `providerRetry` timer with that attempt count and the limit-wait flag, so the wake goes through the normal `providerRecovery` admission and a limit refusal still spends no continuation budget (senpi#4085).
- `provider-retry.ts`: `restartProviderRetryDelayMs()` measures the backoff the failed run had earned from the failed answer's timestamp (a limit refusal never under `limitWaitFloorMs`), waits the 1 s wake margin when it already ran out, and adds a stable per-session offset under 15 s (FNV-1a over the session id). `providerRetryDelayMs` itself adds no jitter.

### Why

- A session with an active goal whose turn ended on a 429 was waiting on its provider-retry timer when the host stopped. The next host start queued the goal continuation during `session_start`, so the session asked the provider again at once, and every such session on the host did so together.

### Why an extension could not handle it

- This is the builtin goal extension's own session-start policy.

### Expected merge conflict zones

- LOW: the `else` branch at the end of the `session_start` handler in `index.ts`; one new public method on `MonitorAwareGoalContinuation`; one new reader and one new delay helper.

### Fixed
- A host restart no longer re-runs sessions whose last turn ended on a provider error such as a 429 rate limit; those sessions stay paused with the reason `ended_on_provider_error` until resumed ([#7454](https://github.com/code-yeongyu/senpi/pull/7454)).
- A goal whose last turn ended on a provider error no longer asks the provider again as soon as its session reopens after a restart; it waits out the remaining retry backoff, and sessions that failed together wake at different times ([#7454](https://github.com/code-yeongyu/senpi/pull/7454)).
