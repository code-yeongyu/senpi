## 2026-11-05 - list_hands and select_hand on a headless engine (senpi#5938)

### What changed

- `packages/coding-agent/src/modes/rpc/hand-selection-commands.ts` (new): `list_hands { sessionId? }` and `select_hand { sessionId, device | null }`, answered from `RpcHostSessionDefaults.handSelection`. Refusals: `hand_selection_unsupported` (no directory), `unknown_session`, `hand_not_listed`, `hand_unreachable` (with `errorData.device`).
- `session-router-routing.ts` dispatches both commands. `session-router-host-reads.ts` adds `hand_selection` to `get_protocol_info.capabilities` only when a hand selection is set. `custom-capability.ts` adds `HAND_SELECTION_CAPABILITY`.
- `multi-session-host.ts` and `session-router-types.ts`: `handSelection` option and default.
- `rpc-host-command-types.ts` and `rpc-host-response-types.ts`: the two records and their answers.
- `method-classes-schema-host.ts`: their schemas.
- `method-classes.ts`: `list_hands` is `observe`; `select_hand` is `device_admin`, because it moves where the session's tools run.
- `session-attachment-gate.ts`: `list_hands` is exempt as a read.
- `scripts/rpc-inbound-samples.ts` and the regenerated `docs/engine-socket/fixtures/rpc-inbound-samples.json` carry one sample each.

### Why

- senpi#5938, R4: a client (the desktop executor picker, sisyphuslabs/omo-desktop-app#5885) had no way to see which hands a headless engine can reach, or to choose one for a session.

### Why an extension could not handle it

- Host-level RPC commands, the capability list and the method-class table are owned by the multi-session host.

### Expected merge conflict zones

- LOW: the `dispatch` chain in `session-router-routing.ts`, the host schema and class tables, and `answerProtocolInfo`.

## 2026-11-05 - a headless engine records which hand runs each session's tools (senpi#5938)

### What changed

- `packages/coding-agent/src/modes/headless/hand-selection.ts` (new): `createHandSelection(directory)`.
  - A `HandDirectory` port: `list`, plus `link(device)` returning `{ transport, placement }`.
  - A chosen hand replaces the session agent's `toolHost` with `createRemoteToolHost` on that hand's link. `null` gives back the ToolHost the session had.
  - Each choice is appended to the session file as a `custom` entry `hand_selection { device }`.
  - `restore` re-applies the last recorded choice when the session opens. A recorded hand that cannot be linked then gets a remote host on a closed transport, so its calls end as "The hand is unreachable" and never run in this process.
- `packages/coding-agent/src/modes/headless/headless-host.ts`: `HeadlessHostOptions.hands` builds the selection and wraps `createRuntime` to restore before presence gates the session. No CLI flag sets it yet; without it, every host is unchanged.

### Why

- senpi#5938, R4: the user chooses which machine runs Dori's tools, and the choice must survive a restart without ever falling back to local.

### Why an extension could not handle it

- The session's ToolHost and the headless host's runtime factory are engine internals that no extension API reaches.

### Expected merge conflict zones

- LOW: `headlessHostOptions` and the `createRuntime` wrappers in `headless-host.ts`.

### Added
- A headless engine built with a hand directory advertises `hand_selection`. It lists the hands it can reach (`list_hands`) and records, per session, which one runs that session's tools (`select_hand`). A recorded hand that cannot run the calls fails them instead of running them locally ([#5949](https://github.com/code-yeongyu/senpi/pull/5949))
