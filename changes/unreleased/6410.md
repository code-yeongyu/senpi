## 2026-11-11 - Sync dequeue/edit leaves a durable queued input untouched (senpi#4087)

### What changed

- `packages/coding-agent/src/core/agent-session.ts`: `dequeueQueuedInput` / `editQueuedInput` no longer change an input the pending-input store owns. When the copy is still queued they answer `conflict` and change nothing; a drained durable copy still answers `already_delivered`. The guard runs before the still-queued probe because the probe itself removes/replaces the native message, and reads the native queue non-destructively through `peekQueuedMessages`. The store-backed `changeQueuedInput` passes `viaStore` so its native half is not refused.
- `packages/coding-agent/src/core/pending-input-session.ts`: new `hasAdmitted(clientMessageId)` sync read for the guard, backed by the store once its open finishes. Inputs the store never admitted (no client id, or a restored input whose store never opened) keep the legacy sync answers.

### Why

- A sync dequeue/edit mutated the queue without writing any record, so the record stayed `queued` and a reopen re-queued the input (`restoreQueuedInput` re-enqueues anything the record did not retire). Re-derived on current main: the held-copy accessors and the `UncertainJournal` fixture from the issue are gone, the L-c2 recovery-callback loop no longer exists, and the L-c1 edit-after-landed-reservation case is already refused by `reduceMutation` (covered by `pending-input.test.ts`).

### Why an extension could not handle it

- The queued-input records and the agent's native queue are session internals; only one synchronous step inside the session can refuse a change before the native queue is probed.

### Expected merge conflict zones

- LOW: `packages/coding-agent/src/core/agent-session.ts`, `_changeQueuedInput` and the `dequeueQueuedInput` / `editQueuedInput` doc comments; `packages/coding-agent/src/core/pending-input-session.ts`, `SessionPendingInputs.hasAdmitted`.

### Fixed

- Sync dequeue/edit of a queued input admitted with a client id no longer removes or rewrites it without a record: it answers `conflict` and leaves the copy untouched, so a reopen cannot resurrect it; change a durable copy through `changeQueuedInput` ([#6410](https://github.com/code-yeongyu/senpi/pull/6410)).
