## 2026-11-02 - An exhausted fallback chain names every model it tried (senpi#5518)

### What changed

- `packages/coding-agent/src/core/agent-session.ts`: each failed assistant message records a `FallbackAttempt` on the retry controller; the eight `retry_fallback_exhausted` emission sites go through one `_emitFallbackExhausted` that reports the turn's exhaustion exactly once; the last-rung failure path in `_processAgentEvent` (which never reaches `_handleRetryableError` because `_isHardErrorFallbackEligible` needs a candidate) now emits it too, and its `auto_retry_end.finalError` lists every model with its reason. `retry_fallback_exhausted` gains `attempts`.

### Why

- senpi#5518: a turn whose last rung failed ended with only that rung's error and no exhaustion event, so the user never learned why each designated model failed (a subscription chain ended on an API key's credit-balance error).

### Why an extension could not handle it

- Fallback candidate selection, retry outcome and the terminal `auto_retry_end` live in the core retry path in `agent-session.ts`; no hook sees the per-rung failures or the turn-ending decision.

### Expected merge conflict zones

- LOW: the `retry_fallback_exhausted` member of the `AgentSessionEvent` union and the `auto_retry_end` block near the end of `_processAgentEvent`.

## 2026-11-02 - Print mode lists each model of an exhausted fallback chain (senpi#5518)

### What changed

- `packages/coding-agent/src/modes/print-mode.ts`: after `Model fallback exhausted: <chain> (<error>)`, one stderr line per attempt: `  <provider/model>: <reason>`.

### Why

- senpi#5518: the exhausted notice named only the chain and the last error.

### Why an extension could not handle it

- Print mode's stderr notices are written by its own event subscriber; extensions do not own that output.

### Expected merge conflict zones

- LOW: the `retry_fallback_exhausted` branch of the print-mode event subscriber.
