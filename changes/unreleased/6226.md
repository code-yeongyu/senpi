## 2026-11-08 - tool_search stages matches into the next request on strict openai-completions transports (senpi#6219)

### What changed

- `packages/coding-agent/src/core/agent-session.ts`: new `_stagedToolNames`/`_stagedCallWatch` fields; `bindCore` wires an optional `setStagedTools` action; the next-turn context builder merges staged tool definitions into the request `tools` for `openai-completions` models (skipped when senpi#2095 declared tools already carry every tool) and consumes staging one-shot; the preflight hook promotes a staged tool the model calls (the "first call activates" contract, since the executor pipeline resolves staged tools from the request payload and never reaches `resolveUnknownToolCall` otherwise); a turn ending without tool results drops unconsumed staging; a staged request answered with an empty response and no tool results warns through the UI notify channel (the transport-swallowed-call fingerprint).

### Why

- On transports whose tool-call parser only recognizes functions present in the request `tools` array (vLLM glm47 with `--enable-auto-tool-choice`), a model call for a deferred (`exposure: "search"`) tool is silently swallowed: finish_reason `"stop"`, empty content, and the turn ends. The tool can never be called, because activation happens only at call resolution and the call never arrives.

### Why an extension could not handle it

- Staging must alter the provider request payload for the request immediately after a search, which only the session's context builder controls; extensions can promote tools (`setActiveTools`) but that is a permanent active-set change, which senpi#1682 removed precisely because incidental matches made it.

### Expected merge conflict zones

- LOW: `agent-session.ts` around the `_lazyToolActivation` field block and the `_installAgentNextTurnRefresh` context-builder return (both dense fork areas).

## 2026-11-08 - optional setStagedTools on the extension API runtime (senpi#6219)

### What changed

- `packages/coding-agent/src/core/extensions/types.ts`: optional `ExtensionAPI.setStagedTools?(names: readonly string[]): void` plus `SetStagedToolsHandler`, and the optional member on `ExtensionActions`/`ExtensionRuntime`.
- `packages/coding-agent/src/core/extensions/loader.ts`: `createExtensionAPI` delegates `setStagedTools` to the shared runtime at call time (same shape as `setActiveTools`).
- `packages/coding-agent/src/core/extensions/runner.ts`: `bindCore` copies the new optional action onto the shared runtime.
- `packages/coding-agent/src/core/extensions/builtin/tool-search/`: `ToolSearchRuntime` gains the optional hook; the service exposes `stage(names)`; the tool-search builtin wires the hook and `tool_search.execute` stages its search matches.

### Why

- Staging needs a host-controlled channel from a tool execution to the next request's payload; without it the tool-search builtin has no way to make matches callable for one request without activating them.

### Why an extension could not handle it

- The channel must cross the extension API boundary into the session's request builder; there is no existing extension-visible way to influence only the next request's tool payload.

### Expected merge conflict zones

- LOW: `types.ts` around the tool API section (`setActiveTools`) and the `ExtensionActions` handler list; `loader.ts` in `createExtensionAPI`; `runner.ts` in `bindCore`'s member copies.
