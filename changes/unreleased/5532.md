## 2026-11-02 - Ctrl+J inserts a newline in Windows Terminal (senpi#611)

### What changed

- `packages/tui/src/components/editor.ts`: `handleInput` passes the Warp-normalized input through `normalizeWindowsTerminalCtrlJInput`, so in a direct Windows Terminal session a standalone LF reaches the editor as the CSI-u Ctrl+J sequence (`ESC[106;5u`) and inserts a newline through `tui.input.newLine`.
- `packages/tui/src/windows-terminal-input.ts` (fork-only): `isWindowsTerminalSession` (a `WT_SESSION` GUID, no `TERM_PROGRAM`, no SSH or multiplexer session, win32 or linux) and `normalizeWindowsTerminalCtrlJInput`.

### Why

- `packages/tui/src/components/editor.ts`: Windows Terminal sends CR for Enter and a bare LF for Ctrl+J. Legacy matching also reads LF as Enter for terminals that send LF for plain Enter (#156), and the submit binding is checked before the newline binding, so the default Ctrl+J newline submitted the prompt in Windows Terminal and WSL. In a Windows Terminal session a standalone LF can only be Ctrl+J.

### Why an extension could not handle it

- `packages/tui/src/components/editor.ts`: the key identity is decided inside the shared `Editor` before any consumer sees the input; the Warp-on-WSL normalization already sits at this seam.

### Expected merge conflict zones

- LOW: `packages/tui/src/components/editor.ts`, the first statement of `handleInput` and the import block.
