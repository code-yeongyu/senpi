## 2026-11-22 - Start or refuse queued input after a provider error (senpi#6868, #7363)

### What changed

- `packages/coding-agent/src/core/agent-session.ts`: after retries and fallback finish, queued input starts a new turn. Under a provider usage hold, input a sender waits on (an RPC input with a client id, a peer delivery) is refused before dispatch; a person's TUI input without a client id stays queued. The hold is decided by the same #3131 guard a prompt runs (now `_guardAccountHolds`), so servable usage releases it and a fallback model serves the input where one exists. A refused peer delivery settles its sender with the typed error and drops its admission, so a redelivery is admitted again; a journal failure during the refusal is logged and the run still settles. User aborts still leave the input waiting. Transient errors without a hold keep the omo#14428 backoff for peer deliveries.
- `packages/coding-agent/src/core/pending-input-session.ts`, `packages/coding-agent/src/core/pending-input-types.ts`, `packages/coding-agent/src/core/pending-input.ts`, and `packages/coding-agent/src/core/retry-fallback/usage-limit.ts`: reuse the existing usage-limit error and pending-input journal to record the refusal.

### Why

- A terminal provider error ends the agent loop before it polls for queued follow-ups. A remote sender cannot provide an unrelated prompt to wake its own already-queued input.

### Why an extension could not handle it

- The session owns retry settlement, queue admission, and the journal transaction that removes refused input.

### Expected merge conflict zones

- The queued continuation decision in `packages/coding-agent/src/core/agent-session.ts`.

## 2026-11-22 - Report the refusal of a queued RPC prompt (senpi#6868, #7363)

### What changed

- `packages/coding-agent/src/modes/rpc/client-admissions.ts` and `packages/coding-agent/src/modes/rpc/effect-status.ts`: project the pending-input journal's usage-limit refusal as a failed input effect, including its reason and detail.

### Why

- A waiting sender needs a terminal receipt even when its input never reaches a turn.

### Why an extension could not handle it

- The RPC admission ledger owns effect receipts and their recovery after reopen.

### Expected merge conflict zones

- The admission event subscriber and restore path.

### Fixed

- Follow-ups queued behind a failed provider request now start a new turn. Under a usage hold, a queued RPC or peer input fails explicitly (a fallback model serves it where one is configured), while a person's own queued input stays queued. Input queued after an exhausted provider-timeout retry now starts at once instead of staying parked. User aborts still leave follow-ups queued ([#6868](https://github.com/code-yeongyu/senpi/issues/6868)).
