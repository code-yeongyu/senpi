## 2026-11-15 - A forwarded session_shutdown's signal also aborts at the loop's cancel (senpi#5898)

### What changed

- `packages/coding-agent/src/core/extensions/runner.ts`: `runSessionShutdownHandler` passes each handler a signal that aborts at the handler cap and, when the event brings one (a shutdown a hosted loop forwarded to a hand), at that event's own signal too. A local session's shutdown event has no `signal`, so it keeps the cap alone.

### Why

- Review of #6753: the loop's cancel reached a forwarded shutdown handler's `ctx.signal`, but its `event.signal` aborted only at the cap.

### Why an extension could not handle it

- The runner builds the signal each shutdown handler receives.

### Expected merge conflict zones

- LOW: `runSessionShutdownHandler`'s `run` in `runner.ts`.

## 2026-11-15 - A hand's loop-hook parsers state which parts are strict; the #6753 entry's type name is corrected (senpi#5898)

### What changed

- `packages/coding-agent/src/modes/rpc/loop-hook-envelope.ts`: new. Lists the fields each forwarded event's envelope may carry (besides `sessionId`, `idle`, `scope`), and the fields of a compaction preparation and its file sets.
- `packages/coding-agent/src/modes/rpc/loopless-loop-hooks.ts`: an envelope field the event's list does not name is refused (`malformed <event> payload: unknown field <name>`). A forwarded `session_shutdown` carries the call's signal, so its handlers' `event.signal` aborts at the loop's cancel.
- `packages/coding-agent/src/modes/rpc/loop-hook-payloads.ts`: a preparation or a file-set object with a field it does not name is refused.
- `packages/coding-agent/src/modes/rpc/compaction-settings-schema.ts`: the settings are a strict object; an unknown field is refused.
- `packages/coding-agent/src/modes/rpc/agent-message-schema.ts`, `session-entry-schema.ts`: still loose, now on record. An unknown field on a transcript message or session entry reaches the handlers untouched, because a newer loop adds optional fields a hand one version behind must hand on, not refuse.
- Correction to the #6753 entry ("A hand serves a hosted loop's compaction and shutdown events"): `LoopHookCall.run` takes a `LoopHookCallBinding` (#6751's binding, plus the loop's `cancel`), not a `LoopHookCallScope`; no type of that name exists.

### Why

- Review of #6753 (L1): the commit called the payloads strictly parsed while every object was loose. The rule is now explicit per part: the parts the loop-hook lane defines itself are strict, and the loop's own records (messages, entries) are loose.
- Review of #6753 (L3): the fragment named a type that does not exist.

### Why an extension could not handle it

- These are the hand's own boundary parsers.

### Expected merge conflict zones

- LOW: the prologue of `extensionLoopHooks`, `preparationOf` and `fileOpsOf`, and the schema module headers.

## 2026-11-15 - The hand runs one session's loop-hook calls one at a time, and a cancel still reaches them (senpi#5898)

### What changed

- `packages/agent/src/execution/loop-hook-host-hand.ts`: `serveLoopHooks` registers and queues each call when it arrives. A call's hooks start only once the previous call's hooks on the lane (one session) have settled, a cancelled call's included. The frame handler still returns at once, so `hook.cancel` reaches the call it names while it runs or while it waits; a call cancelled while waiting starts with its signal already aborted.
- `packages/agent/src/execution/loop-hook-host-protocol.ts`: the protocol header documents that ordering.

### Why

- Review of #6753 (L4): #6753 stopped awaiting `serve()` so a cancel could arrive, and with it the hand stopped serializing a session's calls. A cancelled call whose handlers ignore their signal could then run alongside the session's next call.

### Why an extension could not handle it

- The loop-hook link is agent-core protocol.

### Expected merge conflict zones

- LOW: `serve` in `loop-hook-host-hand.ts` and the protocol header in `loop-hook-host-protocol.ts`.
