## 2026-11-24 - Vendor-prefixed Gemini model ids are detected as Gemini 3+ (senpi#7414, senpi#7413)

### What changed

- `packages/ai/src/api/google-shared.ts`: `getGeminiMajorVersion` matches `gemini-<N>` after an optional non-alphanumeric boundary (`/(?:^|[^a-z0-9])gemini(?:-live)?-(\d+)/`) instead of anchoring on `^gemini`. Ids such as `google-gemini-4-hydrogen`, `google-gemini-3_7-flash` and `models/gemini-3-pro-preview` now resolve to their major version, so `requiresToolCallId`, `requiresThoughtSignatureReplay`, `supportsMultimodalFunctionResponse` and `supportsGoogleStrictToolSampling` apply to them. Unprefixed ids and non-Gemini ids such as `gemma-3-27b-it` resolve exactly as before.

### Why

- senpi#7413. A custom provider that fronts Gemini through a Google-API-compatible gateway lists its models with a vendor prefix. Those ids resolved to `undefined`, so every Gemini 3+ rule in this file was off for them: tool call ids were omitted, unsigned tool calls were not replayed as text (a mid-session switch to such a model failed with `400 Function call is missing a thought_signature`), and function responses were treated as pre-3. The `[functionResponse, text]` reordering proposed in senpi#4337 keys on the same helper, so it needs this to reach those ids.

### Why an extension could not handle it

- The version check is a private helper inside the shared Google message converter that runs while the request body is built; no extension hook sees a model id there or can change how it is classified.

### Expected merge conflict zones

- LOW: the one-line regex in `getGeminiMajorVersion`. Upstream still anchors on `^gemini`; keep the boundary form when syncing.
