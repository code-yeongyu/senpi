## 2026-11-13 - An answer whose admission baseline ends without writing it is still written, once (senpi#6587)

### What changed

- `packages/coding-agent/src/modes/rpc/compact-admission-baseline.ts`: an admission baseline that ends before it handed its answer to the connection's queue tells the answer's `BaselineAnswer`, which then writes the answer the ordinary way, once. An answer handed over after the baseline ended goes the ordinary way at once. Inside the queue's own cut the write waits one microtask.
- `packages/coding-agent/src/modes/rpc/session-event-writer.ts`: `baselineAnswer(peer, socketEpoch)` now lives here, beside `enqueueControl`, which is that ordinary way. It writes only for the socket the request was made on and only for a connection that has a queue. It was in `session-event-writer-recovery.ts`.
- `packages/coding-agent/src/modes/rpc/compact-open-admission.ts`, `compact-subscribe-admission.ts`, `compact-reset-stream.ts`: each passes the socket its request was made on.
- `packages/coding-agent/src/modes/rpc/compact-subscribe-admission.ts`: the handler also ends its baseline on every way out (a `finally` that hands over nothing; only the first hand-over counts).

### Why

- The queue takes no baseline while a recovery drops records, and an overflow drops every baseline already queued. The answer of a compact `open_session`, `subscribe_sessions` or `reset_stream` travels in one, so the request got no response; in the second case the answer had been counted as given.
- A subscribe's activation installs its baseline before the handler hands the answer over. A failure between the two left a baseline the queue had taken waiting for an answer for ever, with the rest of the connection's queue behind it (the review of senpi#6573).

### Why an extension could not handle it

- It is the RPC host's own answer path.

### Expected merge conflict zones

- MEDIUM: `BaselineAnswer` and `admissionBaseline` in `compact-admission-baseline.ts`.
- LOW: the block above `enqueueControl` in `session-event-writer.ts`.
