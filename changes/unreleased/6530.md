## 2026-11-12 - The process boot instant comes from the kernel's boot record (senpi#3152)

### What changed

- `packages/coding-agent/src/core/extensions/builtin/terminal/process-identity.ts`: `processBootAtMs()` reads the kernel's recorded boot instant (`btime` in `/proc/stat` on Linux, `kern.boottime` from `/usr/sbin/sysctl`, by absolute path, on macOS) instead of rounding `now - os.uptime()`; elsewhere it still computes from uptime. The read is asynchronous (`fs.promises.readFile`, and an async `execFile` of `sysctl` on macOS) so a session never blocks the shared host on it, and it is cached once per process as a promise: every later call awaits that promise and does no I/O. A read that found no value is dropped, so the next call retries it, and the uptime fallback is never memoized. Callers keep their 120 s `sameBoot` tolerance.
- The kernel's recorded boot instant moves with a wall-clock step, so a cached value can go stale. `sameBootAsOwn` (used by the lease, reclaim-lock, orphan-reaper and schedule-runner checks) re-reads the record fresh, uncached, once before a 'different boot' verdict stands, and the fresh read replaces the cache; the probes take an optional `{ fresh: true }` for this (`OwnBootReader`, default `ownBootAtMs`). A live peer that recorded the moved instant is no longer called stale.
- `processBootAtMs()` is now async, and so are `holdSessionFile`, `currentResidentWriter` and the `bootAtMs` probe of `WriterProbes` and the orphan reaper. `AgentSessionRuntime`'s constructor no longer takes the session hold: `createAgentSessionRuntime` and the multi-session switch take it with the new `holdRuntimeSession` and pass it in, releasing it if construction throws. `TerminalRuntimeSession` takes the boot instant from its async creator. Each writer fence resolves the boot instant before its check-then-write, so nothing yields between the check and the write it guards.

### Why

- `os.uptime()` counts whole seconds, so two reads that straddled an uptime tick computed boot instants a second apart (senpi#3152, senpi#4301). Caching one read instead would break agreement between processes after a wall-clock step; the kernel's record moves for every reader alike.

### Why an extension could not handle it

- The boot instant is read by the builtin terminal and schedule lease code itself.

### Expected merge conflict zones

- LOW: `processBootAtMs` in `process-identity.ts`.
- MEDIUM: callers of `holdSessionFile`, `processBootAtMs`, `currentResidentWriter`, and `new AgentSessionRuntime(...)` / `new TerminalRuntimeSession(...)` (both take one more argument).

## 2026-11-12 - A runtime's session hold is taken before it is constructed, and the writer fence reads the boot instant first (senpi#3152)

### What changed

- `packages/coding-agent/src/core/session-holders.ts`: `holdSessionFile` is async (its holder record carries the async boot instant), and it resolves that record before it reads the reference count, so nothing yields between that check and the record it guards. The move lock's own record is awaited the same way.
- `packages/coding-agent/src/core/agent-session-runtime.ts`: the constructor takes the session hold as a seventh argument and no longer touches the holder file. `createAgentSessionRuntime` takes it with the new `holdRuntimeSession` before constructing and releases it if construction throws; `persistSession`, `apply` and `switchSession` await their holds.
- `packages/coding-agent/src/core/session-holders.ts`: the holder record's shape is exported as `HolderRecord`.
- `packages/coding-agent/src/core/session-writer-claims.ts`: `WriterProbes.bootAtMs` is an `OwnBootReader`; a claim from another boot on this host is checked against a fresh read before the check runs, so a writer that started after a wall-clock step is not displaced; `acquireWriterClaim` resolves it before its check and passes the value into `ownerGone`, so no await lands between proving the owner gone and publishing the next claim.

### Why

- The boot instant is read asynchronously so one session never blocks the shared host on it (the no-sync session-path audit), and a constructor cannot await, so the hold moved to the async creators.

### Why an extension could not handle it

- Session holds and writer claims are core session ownership.

### Expected merge conflict zones

- MEDIUM: callers of `holdSessionFile` and `new AgentSessionRuntime(...)`, which now await the hold or pass one in.

### What changed

## 2026-11-12 - A multi-session switch takes the replacement's hold first; the resident writer reads the boot instant asynchronously (senpi#3152)

### What changed

- `packages/coding-agent/src/modes/rpc/session-registry-switch.ts`: the replacement runtime's hold is taken with `holdRuntimeSession` and passed into its constructor BEFORE the switched runtime releases its own, as before, so the shared holder record never disappears in between; a throwing construction releases the new hold.
- `packages/coding-agent/src/modes/rpc/host-handover-resident-writer.ts`: `currentResidentWriter` is async, and the handover verdict closure resolves the boot instant before it reads or records a verdict; a writer that looks like another boot is checked against a fresh read first.
- `packages/coding-agent/src/modes/rpc/session-router-residency.ts`: awaits `currentResidentWriter()`.

### Why

- The boot instant is read asynchronously (senpi#3152), and the session hold moved out of the runtime's constructor.

### Why an extension could not handle it

- The RPC registry and handover are host internals.

### Expected merge conflict zones

- LOW: `createEntrySwitchSession` and `currentResidentWriter`.
