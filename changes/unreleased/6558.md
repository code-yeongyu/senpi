## 2026-11-12 - Project verbs refuse user-global files by real path, from the roots the loader actually loads (senpi#6547, senpi#6558)

### What changed

- `packages/coding-agent/src/core/skills.ts`: `userGlobalSkillRoots()` holds the two fixed user-global skill roots (the agent dir's skills root, `~/.agents/skills`) plus the roots a caller passes; `loadSkills` builds its skill allowlist from it, and the RPC refusal builds its list from it too.
- `packages/coding-agent/src/core/resource-loader.ts`: `ResourceLoader.getUserSkillRoots?()` is an OPTIONAL member, so a custom loader without it still type-checks and the verbs fall back to the two fixed roots. `DefaultResourceLoader.getUserSkillRoots()` returns the global `skills` settings roots plus the own folder (or file) of every skill loaded with user provenance, wherever it came from (a package, `-e`, an extension's `resources_discover` path, `--skill`, the SDK's `additionalSkillPaths`), never the selected root it was found under, which for a package is the whole package folder. The allowlist passed to `loadSkills` keeps the package folders, which contain a package's skills.

### Why

- The senpi#6547 security review (CLEAR, 2 LOWs): a session opened in `$HOME` could read and rewrite `~/.agents/skills/<x>/SKILL.md` through the skill verbs, and `read_project_file` / `write_project_file` never refused at all, reaching the global context file.
- The senpi#6558 security review (REQUEST-CHANGES): refusing the allowlist's roots refused a whole package folder, so a project installed globally from its local path, or loaded with `-e .`, lost its own `AGENTS.md`, MCP file and skills; the required interface member broke custom loaders (TypeError in the verbs); skills added through `extendResources` and `additionalSkillPaths` were loaded but never refused; and a root not created yet compared unresolved, so with `$HOME` behind a link a write creating `~/.agents/skills/...` was not refused.

### Why an extension could not handle it

- The refusal is a containment decision inside the RPC verbs' path resolution, and its roots come from what the loader loaded; both are core runtime code no extension can replace or observe early enough.

### Expected merge conflict zones

- LOW: the `userGlobalSkillRoots` extraction and the allowlist call in `skills.ts`; the optional `getUserSkillRoots` member on `ResourceLoader`, `DefaultResourceLoader.getUserSkillRoots` / `selectedGlobalSkillRoots`, and the `userSkillRoots` argument in `updateSkillsFromPaths`; the refusal call sites in `modes/rpc/project-file-commands.ts`, `project-skill-commands.ts` and `project-mcp-commands.ts`, and the shared helpers (`insideUserGlobalRoots`, the nearest-existing-parent real path) in `modes/rpc/project-file-path.ts`.

### Fixed
- RPC: `read_project_file` / `write_project_file`, `read_project_skill_file` / `write_project_skill_file` and `get_project_mcp_servers` / `set_project_mcp_servers` refuse a file whose real path lies in the agent dir or in a user-global skill root the engine loads (`~/.agents/skills`, a selected skill root, the folder of a user skill loaded from a package, `-e`, an extension or `--skill`), so a session opened in `$HOME` can no longer read or edit global skills, the global context file or the global MCP file through the project verbs. A package's own folder is not such a root: a project installed globally from its local path, or loaded with `-e .`, keeps its own files. A root that does not exist yet is compared through its nearest existing parent's real path (senpi#6547, senpi#6558 reviews)
- SDK: `ResourceLoader.getUserSkillRoots` is optional, so a custom `ResourceLoader` without it keeps type-checking and working; the project verbs then refuse only the agent dir and `~/.agents/skills` as user-global (senpi#6558 review)
