## 2026-11-12 - Project verbs refuse user-global files by real path, from the roots the loader actually loads (senpi#6547, senpi#6558)

### What changed

- `packages/coding-agent/src/core/skills.ts`: `userGlobalSkillRoots()` holds the two fixed user-global skill roots (the agent dir's skills root, `~/.agents/skills`) plus the roots a caller passes; `loadSkills` builds its skill allowlist from it, and the RPC refusal builds its list from it too. `LoadSkillsResult.userScanDirs` (optional) lists the given paths that are folders walked for user-provenance skills, read from the stat `loadSkills` already takes of each path.
- `packages/coding-agent/src/core/resource-loader.ts`: `ResourceLoader.getUserSkillRoots?()` is an OPTIONAL member returning the global `skills` settings roots, so a custom loader without it still type-checks; the RPC verbs refuse the folder of every user-provenance skill from the required `getSkills()` themselves, so a loader without it loses only those extra roots. New OPTIONAL `getUserSkillScanDirs?()`: every folder walked for user-provenance skills, from the package manager plus each user skill directory passed straight to `loadSkills` (`--skill`, an extension's `resources_discover`, the SDK's `additionalSkillPaths`), the latter taken from `loadSkills`' `userScanDirs` rather than a second `statSync` of every skill path. The allowlist passed to `loadSkills` keeps the package folders, which contain a package's skills.
- `packages/coding-agent/src/core/package-manager.ts`: `ResolvedPaths.skillScanDirs` lists the folders `collectResourceFiles` walks for user-provenance skills (a package's `skills` folder, a manifest or settings skill folder), threaded through the package and local-entry collectors as one set per resolve.

### Why

- The senpi#6547 security review (CLEAR, 2 LOWs): a session opened in `$HOME` could read and rewrite `~/.agents/skills/<x>/SKILL.md` through the skill verbs, and `read_project_file` / `write_project_file` never refused at all, reaching the global context file.
- The senpi#6558 security review (REQUEST-CHANGES): refusing the allowlist's roots refused a whole package folder, so a project installed globally from its local path, or loaded with `-e .`, lost its own `AGENTS.md`, MCP file and skills; the required interface member broke custom loaders (TypeError in the verbs); skills added through `extendResources` and `additionalSkillPaths` were loaded but never refused; and a root not created yet compared unresolved, so with `$HOME` behind a link a write creating `~/.agents/skills/...` was not refused.
- The senpi#6558 round-2 review (FIX_FIRST): refusing only each skill's own folder left the folders the loader walks for top-level `*.md` skills open, so `write_project_file` could create `<pkg>/skills/AGENTS.md` or `<dir>/CLAUDE.md` and plant a user skill; a custom loader without `getUserSkillRoots` had no user skill refused; and a package whose `SKILL.md` sits at its root refused the whole project folder.
- The senpi#6558 whole-suite run: a second `statSync` of every skill path in `updateSkillsFromPaths` (two passes per RPC `open_session`) pushed the synchronous filesystem calls of a session open past the senpi#11437 per-skill-directory budget.

### Why an extension could not handle it

- The refusal is a containment decision inside the RPC verbs' path resolution, and its roots come from what the loader loaded; both are core runtime code no extension can replace or observe early enough.

### Expected merge conflict zones

- LOW: the `userGlobalSkillRoots` extraction, the allowlist call and the `userScanDirs` result field in `skills.ts`; the optional `getUserSkillRoots` / `getUserSkillScanDirs` members on `ResourceLoader`, `DefaultResourceLoader.getUserSkillRoots` / `getUserSkillScanDirs` / `selectedGlobalSkillRoots`, and the `provenanceByPath` / scan-dir lines in `updateSkillsFromPaths`; in `package-manager.ts` the `scanDirs` parameter on `collectResourceFiles`, `collectFilesFromPaths`, `collectManifestFiles`, `collectFilesFromManifestEntries`, `addManifestEntries`, `collectDefaultResources`, `applyPackageFilter`, `applyPackageDeltaFilter` and `resolveLocalEntries`, and `skillScanDirs` on the accumulator and `ResolvedPaths`; the refusal call sites in `modes/rpc/project-file-commands.ts`, `project-skill-commands.ts` and `project-mcp-commands.ts`, and the shared helper `insideUserGlobalRoots` in `modes/rpc/project-file-path.ts`.

### Fixed
- RPC: `read_project_file` / `write_project_file`, `read_project_skill_file` / `write_project_skill_file` and `get_project_mcp_servers` / `set_project_mcp_servers` refuse a file whose real path lies in the agent dir or in a user-global skill root the engine loads (`~/.agents/skills`, a selected skill root, the folder of a user skill loaded from a package, `-e`, an extension or `--skill`), so a session opened in `$HOME` can no longer read or edit global skills, the global context file or the global MCP file through the project verbs. A top-level `*.md` file directly in a folder the engine walks for user skills (a package's `skills` folder, a `--skill` or extension skill folder) is refused too, since the next load would take it as a skill; a package whose `SKILL.md` sits at its root refuses only that file when it is the session's own project. A package's own folder is not such a root: a project installed globally from its local path, or loaded with `-e .`, keeps its own files. A root that does not exist yet is compared through its nearest existing parent's real path (senpi#6547, senpi#6558 reviews)
- SDK: `ResourceLoader.getUserSkillRoots` and the new `ResourceLoader.getUserSkillScanDirs` are optional, so a custom `ResourceLoader` without them keeps type-checking and working; the project verbs still refuse the agent dir, `~/.agents/skills` and every user-provenance skill the loader lists through `getSkills()` (senpi#6558 review)
