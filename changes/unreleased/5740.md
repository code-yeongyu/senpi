### Added
- Split sessions present a hand's extension UI on the attached client: widgets, notices, status, titles and editor text that an extension produces on the hand while a call runs go in order to the loop that owns the call (its `ui-presentation` plane) and are presented there exactly as on a fused session, before the call ends. Presentation never changes a call's result or error: when the loop cannot take one, it is presented on the hand's own UI and reported on the runner's error channel. Dialogs stay off the port, and the hand still reports no UI to extensions. Fused sessions are unchanged ([#5740](https://github.com/code-yeongyu/senpi/pull/5740)).

## 2026-11-04 - Presentation port for a hand's extension UI (S30, senpi#5740)

### What changed

- `packages/coding-agent/src/core/extensions/ui-presentation.ts` is new: the presentation methods, the hand's per-call port (`openPresentationPort`), the loop's `ui-presentation` plane handler (`servePresentation`, fail-closed), the hand's `PresentationBroker`, and `isPresentationOnly`.
- `packages/coding-agent/src/core/extensions/runner.ts`: `hasUI()` is false while the UI is presentation-only, so a port never makes an extension ask a dialog the hand cannot answer.

### Why

Brain/hand split S30 (F12, F39): UI produced on the hand must reach the client the user is looking at, as it does in one process.

### Why an extension could not handle it

The UI an extension's `ctx.ui` resolves to, and `hasUI`, are the runner's.

### Expected merge conflict zones

`runner.ts` `hasUI()` and its import block.

## 2026-11-04 - Loopless calls present through the port (S30, senpi#5740)

### What changed

- `packages/coding-agent/src/modes/rpc/runtime-factory-loopless.ts`: the loopless runtime sets a `PresentationBroker` on its runner and runs each call through it, so a call that carries its nested plane presents its extension UI on the loop that owns it and ends after its presentations were presented. A presentation the loop cannot take is reported through the runner's `emitError` and never changes the call's result or error. A device file operation's `tool_call` check (`fileGuards.beforeToolCall`) runs through it too, with that operation's nested requester. Its UI reaches the attached client only when the brain names the presentation plane in `createRemoteToolHost({ filePlanes })`. By default, file operations host no plane, so that UI stays on the hand and the refused presentation is reported through the runner's error channel.

### Why

Brain/hand split S30: the hand's tool calls are where that UI is produced.

### Why an extension could not handle it

The loopless runtime's execute path is core.

### Expected merge conflict zones

`runtime-factory-loopless.ts` `execute` wiring next to S29's nested requester.
