## 2026-10-30 - A same-model sibling sits out a walk after a model-shared failure (senpi#4083)

### What changed

- `packages/coding-agent/src/core/retry-fallback/shared-failure.ts`: new `isModelSharedFailure(reason, errorMessage)`. A network blip on the model, the model overloaded (`overloaded`, `529`, `high demand` with no rate-limit or usage-limit text) and a content refusal are model-shared; account limits, billing, credentials, rate limits and server errors are not.
- `packages/coding-agent/src/core/retry-fallback/controller.ts`: `tryFallback` records the failed model (provider-free, namespace-stripped id) for the duration of the walk when the failure is model-shared, and the candidate scan skips that model on any other provider with the skip reason `same-model`.
- `packages/coding-agent/src/core/retry-fallback/candidates.ts`: optional `isSameModelSkipped` filter after the network-blip skip.
- `packages/coding-agent/src/core/retry-fallback/expansion.ts`: `withoutNamespace` is exported so the controller compares ids the way bare expansion matches families.

### Why

- senpi#4083: a bare chain entry expands to the same model on two providers. After a connection error on one, the walk spent a request on the other, which failed the same way and read on the card as the same model tried twice.

### Why an extension could not handle it

- The candidate scan and its skip filters are internal to the retry-fallback controller; no extension hook sees or filters fallback candidates.

### Expected merge conflict zones

- LOW: `tryFallback` and the `nextCandidate` filter object in `controller.ts`; the skip sequence in `candidates.ts`.

### Fixed
- After a network blip, an overloaded model or a content refusal, the fallback walk no longer retries the same model on a second provider that a bare chain entry expanded to; account, billing, credential, rate-limit and server failures still move to it ([#4083](https://github.com/code-yeongyu/senpi/issues/4083))
