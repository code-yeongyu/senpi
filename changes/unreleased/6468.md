## 2026-11-12 - Owner-checked release for the MCP grants lock (senpi#6431)

### What changed
- `packages/coding-agent/src/core/extensions/builtin/mcp/env-grants-store.ts` writes a random owner token beside the grants lock directory right after acquiring, and removes the directory (on release and at process exit) only while that token is still this writer's; otherwise the lock reads as lost and the write is refused. `update()` takes the lock through the new `lockGrantsFile`.

### Why
- proper-lockfile removes a lock by path and never checks that it is still the holder's, so a writer taken over after going stale could delete the next writer's lock (the #6428 race).

### Why an extension could not handle it
- The grants store is engine code, vendored into oh-my-openagent; the lock lives inside it.

## 2026-11-12 - Document the lockSync callers' takeover residual (senpi#6431)

### What changed
- `packages/coding-agent/src/core/auth-storage.ts`, `packages/coding-agent/src/core/settings-manager.ts` and `packages/coding-agent/src/core/trust-manager.ts` carry a comment at each `lockSync` call: the library releases by path, and a sync holder is taken over only if its process stalls past the stale bound inside its short critical section. Comments only; no behaviour change.

### Why
- So the residual of the #6428 race at these calls is visible where the lock is taken, and tracked in #6431.

### Why an extension could not handle it
- These locks belong to engine-owned stores.

## 2026-11-12 - Name the package-update cleanup lock's takeover risk (senpi#6431)

### What changed
- `packages/coding-agent/src/package-manager-cli.ts` comments its `lockSync` in `cleanupManagedInstall`: the lock uses the library's default 10 s stale bound, a sync holder cannot refresh, and its critical section is a recursive delete of the staging trees, so a slow delete alone can outlast the bound and let the update path take the lock over. Comment only; the fix is tracked in #6431.

### Why
- The earlier comment understated this site's risk (review of #6468).

### Why an extension could not handle it
- The managed-install update lock is engine-owned.
