## 2026-11-12 - A host-level command whose handler throws is still answered (senpi#6483)

### What changed

- `packages/coding-agent/src/modes/rpc/host-line-answer.ts` (new): `answerLine` dispatches one parsed command and answers its line; a throw is answered `success: false` with the request's id and command (`internal_error` with the message as `errorData.detail`, or the session registry's own refusal code when the error is one), the stderr line is written there, and what follows an answered line still runs.
- `packages/coding-agent/src/modes/rpc/answered-requests.ts` (new): which requests in flight already had an answer taken for writing, watched from a line's dispatch until that line is done. `answerLine` asks it, so a handler that answered under the request's id and then threw gets no second answer, and a command sent without an id gets none.
- `packages/coding-agent/src/modes/rpc/session-event-writer.ts`: `enqueueControl` tells it of each value at the two points where it takes one into a queue, and of none it refused.
- `packages/coding-agent/src/modes/rpc/compact-open-admission.ts`: a comment corrected; the code is unchanged.
- `packages/coding-agent/src/modes/rpc/multi-session-host.ts`: `handleParsed` answers through `answerLine`.
- `packages/coding-agent/src/modes/rpc/rpc-error-types.ts`: the code `internal_error`.
- `packages/coding-agent/docs/rpc.md`: what the caller receives.

### Why

- On the multi-session host a host-level command whose handler threw got no response: the line's rejection was written to stderr only, and the caller waited out its own timeout. Only session-scoped commands were answered when they threw.

### Why an extension could not handle it

- It is the host's own request dispatch.

### Expected merge conflict zones

- LOW: the last lines of `handleParsed` in `multi-session-host.ts`; the error-code union in `rpc-error-types.ts`.
