## 2026-11-12 - A move's landing asserts its lock after the stamp check, and a record's stamp writes only its own keys (senpi#6463's reviews)

### What changed

- `packages/coding-agent/src/core/session-move/move-ledger.ts`: the closure `commit` hands its landing is the stamp check, then the move record's lock; the separate lock line after the first stamp check is gone, since `commit` runs the same closure.
- `packages/coding-agent/src/core/session-move/move-record-file.ts`: a record write takes only `up` and `host` from its stamp and writes them before the record, its landing and its time.
- `packages/coding-agent/src/core/session-move/move-landing.ts`: the stamp's type is named, `UptimeStamp`.

### Why

- The stamp check's read is awaited; a lock taken during that read inside the landing was seen only after the file had landed.
- A stamp typed as any record, spread last, could replace the record's custody fields; spread first, it could still add a `committing` the landing did not have.

### Why an extension could not handle it

- It is the move ledger's own commit path and record format.

### Expected merge conflict zones

- LOW: `commit` in `move-ledger.ts`, `write` in `move-record-file.ts`.

## 2026-11-12 - A workflow of its own measures on macOS that a wall-clock step does not move the uptime a move record is aged by (senpi#6463's review)

### What changed

- `.github/workflows/move-stamp-age-macos.yml` (new): one job on a hosted macOS runner. It steps the clock one hour forward with sudo, and checks `os.uptime()` under node and bun and the built stamp age across the step. It runs on a pull request and on `main` only when a file its path filter names changes: every production source file that chooses, writes or reads a stamp's clock (the rule's pattern is written once, in the file's header), and the workflow itself. The restore of the clock is armed before the clock is touched, and a step that always runs puts the runner back on network time. `packages/coding-agent/test/move-stamp-age-workflow.test.ts` holds the filter to that rule, and the node and bun versions to the macOS job's in `ci.yml`.

### Why

- The stamp age's premise had been measured on Linux only. A step in the main macOS job would not have run on a pull request, so its first run would have been on `main` after the merge.

### Why an extension could not handle it

- This is one of the repository's own CI workflows.

### Expected merge conflict zones

- NONE: the file is new, and `.github/workflows/ci.yml` is not changed.
