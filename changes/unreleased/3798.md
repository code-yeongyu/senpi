## 2026-11-02 - Name the refused event in a recovery failure diagnostic

### What changed

- `recovery-content-lifecycle.ts`: `snapshot()` returns the validator's state (`activeIndex`, `activeKind`, `lastEndedIndex`).
- `recovery-stream-failure.ts`: `terminateRecoveryStreamForFailure` takes an optional `event` (`RecoveryFailureEvent`: the refused event's type, its `index`, the block count `blocks` and the lifecycle snapshot) and writes it as `details.event` of the failure diagnostic.
- `recovery-stream-wrapper.ts`: `canStart` and `isActive` take the event type and pass the refused event through `terminateForFailure`.

### Why

"Invalid assistant content event order" named neither the event nor the state that refused it; the Anthropic Subscription lane's response restarts (Claude Code's output-limit recovery) could only be diagnosed by reconstructing the stream from the CLI's transcript. The diagnostic carries no block content.

### Why an extension could not handle it

The diagnostic is written by the middleware at the moment it refuses the event.

### Expected merge conflict zones

- `recovery-stream-wrapper.ts`: the `canStart` / `isActive` helpers and their call sites.

## 2026-11-02 - One query, several Anthropic responses: the provider keeps its event protocol sequential

### What changed

- `stream-events.ts`: `applyStreamEvent` ends every block the SDK left open (`closeOpenBlocks`: a `content_block_stop` the provider synthesizes for each block whose `index` is still set, oldest first) before it starts a new block and before a later `message_start`. A later `message_start` (`startResponse`, counted by the new `SdkResponseTracker` in `StreamEventContext`) also appends a `claude_sdk_oauth_response_restart` diagnostic (`response`, `closedBlocks`, `previousStopReason`) and keeps the first response's id. Blocks keep appending by position, as before. Usage keeps main's per-request accounting (`updateUsage` scope `request-start` resets the counters, the SDK's terminal `result` restores the cumulative billing), so a restarted response neither overwrites nor double-counts the billed total.
- `stream.ts`: one `createSdkResponseTracker()` per query, passed in the event context. The terminal `result` usage is applied as before (the SDK's own total).
- `test/anthropic-subscription-output-limit-continuation.test.ts`: the real provider wrapped by the real `wrapStreamWithModelRecovery` against scripted SDK streams: a continuation after a cap stop between blocks, after a cap stop inside a block, a restart while the continuation's own block is open, a block re-emitted at the same index, and the usage split (the latest response as request context, the terminal result as billing).

### Why

Claude Code's output-limit recovery: when a response stops with `max_tokens` (its output cap, 64000 tokens in 2.1.296), the CLI appends its "Output token limit hit. Resume directly …" meta prompt and streams a second response inside the same query; a retried request restarts a response the same way. Every response numbers its blocks from zero and reports its usage from zero, and the restart can arrive while the earlier block is still open. The text-tool-call recovery middleware validates a strict sequential protocol on the provider's events (one open block, indices that only grow) and ends the turn with "Invalid assistant content event order" otherwise; the whole response, 64k tokens of reasoning on Claude Fable 5.1 at `xhigh`, was lost each time.

### Why an extension could not handle it

The builtin lane maps the SDK stream to pi-ai events; an extension sees only the mapped events, after the middleware has already refused them.

### Expected merge conflict zones

- `stream-events.ts`: `applyStreamEvent` (the `message_start` branch moved to `startResponse`), `StreamEventContext`.
- `stream.ts`: the `applyStreamEvent` call's context literal.
