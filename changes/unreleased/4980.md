## 2026-10-30 - Keep-alive bytes keep a slow first token alive; keep-alive-only silence is capped (senpi#4608)

### What changed

- `packages/agent/src/stream-keepalive.ts` (new): `createTransportLiveness` records when the provider last reported bytes and when the last assistant event arrived, and judges a fired silence bound: expire it, extend it to one bound after the last byte, or end the request with `StreamKeepAliveTimeoutError` once keep-alives alone exceeded the keep-alive budget.
- `packages/agent/src/agent-loop.ts`: `streamAssistantResponse` passes `onTransportActivity` to the stream function (chaining a caller's own hook) and hands the liveness to the assistant event reader. When the start or idle bound fires and the provider reported bytes within one full configured bound, the deadline is re-armed instead of ending the request; each assistant event restarts the keep-alive budget. A caller abort past a keep-alive timeout still reads as the abort.
- `packages/agent/src/types.ts`: `AgentLoopConfig.streamKeepAliveTimeoutMs` (unset or non-positive: keep-alives are unbounded).
- `packages/agent/src/agent.ts`: `AgentOptions.streamKeepAliveTimeoutMs` and `Agent.streamKeepAliveTimeoutMs`, forwarded into the loop config.

### Why

- The silence bounds counted only public assistant events. With the empty-assistant recovery wrapper holding `start` back until content commits, the start bound is a first-content bound, so a request the provider had accepted and kept alive with SSE `ping` events or `:` comment keep-alives was cut at `streamStartTimeoutMs` (90 s until 2026-09-02, 300 s since) while the model was still producing its first token. The retry re-sent and re-billed the whole prompt, and relays in front of the API had to inject a synthetic content-shaped event to keep slow requests alive.

### Why an extension could not handle it

- The bounds live inside the loop's per-request event reader; no hook sees a request between its start and its first event, and the bytes are only visible to the provider adapter.

### Expected merge conflict zones

- MEDIUM: `agent-loop.ts` `streamAssistantResponse` stream-function options, `createAssistantEventReader` and `readNextAssistantEvent` signatures and deadline handler.
- LOW: `types.ts` next to `streamStartTimeoutMs`; `agent.ts` timeout option plumbing.

## 2026-10-30 - `StreamOptions.onTransportActivity` (senpi#4608)

### What changed

- `packages/ai/src/types.ts`: new optional `StreamOptions.onTransportActivity`, called whenever a response body delivers bytes, keep-alives included. Liveness only; adapter support is explicit.

### Why

- The agent loop needs to tell a connection that is alive but has no content yet from a dead one, and only the adapter sees the bytes. A callback in the options crosses lazy and recovery wrappers unchanged, which a method on the inner stream would not.

### Why an extension could not handle it

- The option is part of the core stream contract every adapter receives.

### Expected merge conflict zones

- LOW: `types.ts` `StreamOptions`, next to `onProviderStreamEvent`.

## 2026-10-30 - Anthropic SSE reports transport activity (senpi#4608)

### What changed

- `packages/ai/src/api/anthropic-messages.ts`: `iterateSseMessages` calls an `onBytes` callback for every non-empty body chunk, before parsing, so `ping` events and `:` comments count; `iterateAnthropicEvents` and the stream pass `options.onTransportActivity` into it.
- `packages/ai/src/api/simple-options.ts`: `buildBaseOptions` forwards `onTransportActivity`.

### Why

- Keep-alives are dropped by the SSE parser (comments) or the event filter (`ping`), so the agent loop could not see that an accepted request was still alive while the model thought before its first token.

### Why an extension could not handle it

- The SSE reader is internal to the adapter.

### Expected merge conflict zones

- LOW: `iterateSseMessages` read loop and signature; `iterateAnthropicEvents` call site; `buildBaseOptions` field list.

## 2026-10-30 - Keep-alive timeout is a provider stream stall (senpi#4608)

### What changed

- `packages/ai/src/utils/retry.ts`: `PROVIDER_STREAM_STALL_ERROR_PATTERN` and `PROVIDER_STALL_PHASES` recognize `Provider stream sent only keep-alives and timed out after <n>ms (...)`; users read "kept the connection alive but sent no response", with `retry.provider.keepAliveTimeoutMs` as the setting to raise.

### Why

- The new bound must take the same same-model retry and fallback path as the other stream bounds, and explain itself in plain words.

### Why an extension could not handle it

- The stall classifier is the shared retry gate.

### Expected merge conflict zones

- LOW: the stall pattern alternation and the phase table.

## 2026-10-30 - `retry.provider.keepAliveTimeoutMs` (senpi#4608)

### What changed

- `packages/coding-agent/src/core/settings-manager.ts`: `DEFAULT_STREAM_KEEP_ALIVE_TIMEOUT_MS` (15 minutes) and `getAgentStreamKeepAliveTimeoutMs()` (`0` disables the cap).
- `packages/coding-agent/src/core/retry-fallback/settings.ts`: `ProviderRetrySettings.keepAliveTimeoutMs`.
- `packages/coding-agent/src/core/sdk.ts`: passes the cap to the agent as `streamKeepAliveTimeoutMs`.

### Why

- Keep-alive bytes now keep a request alive past the start and idle bounds, so a server that only ever sends keep-alives needs its own generous, configurable bound: longer than any observed first-token latency and Anthropic's 10-minute non-streaming ceiling, well short of the 60-minute turn inactivity lease.

### Why an extension could not handle it

- Agent stream bounds are created from settings at session construction.

### Expected merge conflict zones

- LOW: `settings-manager.ts` timeout getters; `sdk.ts` agent options; `ProviderRetrySettings`.
