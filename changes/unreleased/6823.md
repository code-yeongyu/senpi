## 2026-11-16 - An explicit no-decision trust entry stops inheritance (desktop pull request worktrees)

### What changed

- `packages/coding-agent/src/core/trust-manager.ts`: an explicit `null` saved for a folder in `trust.json` is now an entry that holds no decision. The nearest-entry walk stops there, so neither a folder above it nor, for a linked git worktree, the main checkout decides for it (`getSavedProjectTrust` returns `null`). `ProjectTrustUpdate.decision` takes `"no_inherit"`, which `setMany` saves as that `null`; a `null` update still removes the folder's entry. `ProjectTrustStore.getNearestEntry` returns the nearest entry including the no-decision one; `getEntry` and `get` report it as no decision. `getProjectTrustNoInheritOption(cwd)` is the option that saves it; `/trust` never offers it. `getSavedProjectTrustState` reports what is saved as a decision, `"no_inherit"` for the explicit no-decision entry, or `null` for nothing saved; `getSavedProjectTrust` keeps returning the decision alone, with both undecided values as `null`. `ProjectTrustStore.revision()` changes on every write made through the store, in any process: each write bumps a generation file (`trust.json.generation`) under the store lock.
- `packages/coding-agent/src/core/linked-worktree-checkout.ts`: `linkedWorktreeMainCheckoutDir` and its file helpers moved here unchanged from `trust-manager.ts` (the file was at the size ceiling).

### Why

- The desktop app: a pull-request worktree of another repository took the base checkout's trust through linked-worktree inheritance. Saving "do not trust" for it also overrides Full access; an entry that only withholds inheritance leaves the folder decided as if nothing were saved, so Full access still trusts it.
- Compatibility: `readTrustFile` has accepted `null` since trust gating was added, and no earlier writer saved one (a `null` update deleted the key). Older readers skip the entry and keep walking, so there the folder inherits as before.

### Why an extension could not handle it

- The trust store and its inheritance rule are core; a `project_trust` handler cannot change what a saved decision means for other readers.

### Expected merge conflict zones

- LOW: `findNearestTrustEntry`, `ProjectTrustStore.getEntry`/`setMany`, `getSavedProjectTrust`.

## 2026-11-16 - A remembered trust answer never stands in for an explicit no-decision entry (desktop pull request worktrees)

### What changed

- `packages/coding-agent/src/main.ts`: the runtime factory reads what is saved for the folder with `getSavedProjectTrustState`. Its per-process memo of an unsaved answer (`projectTrustByCwd`) records what was saved for the folder when the answer was given and the store's `revision()`. An answer given with nothing saved holds while nothing is saved for the folder. An answer given under the explicit no-decision entry (`set_project_trust` `no_inherit`) holds only while the store revision is unchanged. A saved decision is always re-read, never remembered.

### Why

- #6823 review H1: both undecided values read as `null`, so a folder this process had earlier resolved trusted without saving (for example through a `project_trust` handler, or a session-only answer) stayed trusted for every later session after `no_inherit`, which defeats the marker in the desktop's own flow (it saves `no_inherit` on an open session).
- #6823 review L1: keying the memo by the entry it was answered under keeps an answer given under `no_inherit` ("Trust (this session only)") for the process's later sessions of that folder (`/new`, `/fork`), which open without a prompt, instead of dropping it silently.
- #6823 review M1: a memo keyed only by the saved value came back after an intervening save restored that value (`no_inherit`, `do_not_trust`, `no_inherit`); a `no_inherit` answer now needs an unchanged store revision, and every write through the store, by any process, bumps the revision's generation under the store lock (review round 3, L1). An answer given with nothing saved keeps the base behaviour and survives writes for other folders (round 3, L2).

### Why an extension could not handle it

- The memo lives in the CLI runtime factory's closure.

### Expected merge conflict zones

- LOW: the saved-trust read at the top of `createServices` in `main.ts`.

## 2026-11-16 - `set_project_trust` takes `no_inherit` (desktop pull request worktrees)

### What changed

- `packages/coding-agent/src/modes/rpc/project-workspace-commands.ts`: `set_project_trust` accepts `no_inherit`, which saves the explicit no-decision entry for the session's folder. `get_project_trust` never lists it. It adds no trust to the session it is sent in: a trust that came only from Full access stays, any other trust goes unless a `project_trust` handler decides the folder is trusted; such a handler never refuses it.
- `packages/coding-agent/src/modes/rpc/method-classes-schema-session.ts`, `packages/coding-agent/src/modes/rpc/rpc-session-command-types.ts`: the `no_inherit` literal.

### Why

- The desktop marks a pull-request worktree of another repository with it before the head is checked out, instead of saving "do not trust". An engine without it answers `invalid_argument`, which tells the desktop to fall back to `do_not_trust`.

### Why an extension could not handle it

- `set_project_trust` is an RPC core command.

### Expected merge conflict zones

- LOW: `writeProjectTrust` and the `set_project_trust` schema literal.
