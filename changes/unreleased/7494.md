## 2026-11-26 - OSC 7577 Program Resume reports (senpi#7493)

### What changed

- `packages/coding-agent/src/modes/interactive/interactive-mode.ts`: a new `programResumeToken` option creates a `ProgramResumeReporter` (new fork-only `program-resume-reporter.ts`) when stdout is a TTY. `syncProgramResume()` runs after every session rebind (startup, new, resume, fork), on assistant `message_end` and on `agent_end`, so the terminal's record follows the session once its file is written; the SIGCONT handler re-reports with a fresh time; an interactive quit in `shutdown()` sends `clear=1` before `stop()`. Signal shutdowns (SIGHUP/SIGTERM) and dead-terminal exits send nothing.

### Why

- A terminal that implements the OSC 7577 Program Resume Protocol (rev 0.5) can bring the agent session back after the terminal restarts, with the command `[APP_COMMAND, "--session", <absolute session file>]` and the session cwd. The protocol forbids clearing on SIGHUP/SIGTERM, because that is when the record is needed.

### Why an extension could not handle it

- The report must be written to the TUI's own terminal at session rebind, on SIGCONT and at the quit/signal split of `shutdown()`, none of which the extension API exposes; the token also has to be taken before any extension or tool child starts.

### Expected merge conflict zones

- LOW: `InteractiveModeOptions`, the `rebindCurrentSession()` tail, the `message_end`/`agent_end` cases, the `handleCtrlZ()` SIGCONT handler and the interactive-quit branch of `shutdown()` each gain one line.

## 2026-11-26 - Take the OSC 7577 token at startup (senpi#7493)

### What changed

- `packages/coding-agent/src/cli.ts` and the compiled entry `packages/coding-agent/src/bun/cli.ts`: the first import of each is the new fork-only `program-resume-startup.ts`, which calls `handOffProgramResumeToken()` (`core/program-resume-token.ts`). Under Bun on darwin/linux, when `OSC7577_TOKEN` is set, the process re-executes itself in place through libc `execve` (same pid, same argv; a compiled binary drops its embedded `/$bunfs/` entry) with the token removed from its environment and written to a pipe whose read end is named by `SENPI_OSC7577_TOKEN_HANDOFF=<pid>:<fd>`. The new image reads it only when the pid matches, puts it back into `process.env` alone and continues. It runs at most once per process; an embedding entry that runs code before loading the CLI calls `handOffProgramResumeToken()` as its own first statement.
- `packages/coding-agent/src/main.ts`: right after the presenter-authority slot, `main()` awaits `takeProgramResumeToken()`, which removes `OSC7577_TOKEN` from `process.env` and, under Bun on darwin/linux, from the libc environment through `bun:ffi` `unsetenv`, and passes the token to `InteractiveMode` as `programResumeToken`.

### Why

- The protocol says a reporting program removes the token from every program it starts. Under Bun, neither `delete process.env.X` nor `unsetenv` reaches the startup environment Bun keeps: `Bun.spawn`/`spawnSync` without an `env` and every Worker's `process.env` copy from it, so an eval cell's `Bun.spawn` child received the token (review finding on #7494, reproduced). Only a process image whose startup environment never held the token is clean; libc `execve` is used because Bun's `process.execve` closes every descriptor above 2. The unsetenv stays for the fallback path (Windows, no libc, a failed exec).

### Why an extension could not handle it

- The exec has to happen before any other module of the process runs, and the token has to reach `InteractiveMode` construction; extensions load long after both.

### Expected merge conflict zones

- LOW: one import line at the top of `cli.ts` and of `bun/cli.ts`, one statement at the top of `main()` and one `InteractiveMode` option.

## 2026-11-26 - OSC 7577 Program Resume encoder (senpi#7493)

### What changed

- `packages/tui/src/index.ts` exports `encodeProgramResume`, `isProgramResumeToken` and the `ProgramResumeReport` type from the new fork-only `program-resume.ts`. The encoder builds `OSC 7577 ; pid=…:time=…:(argv=<b64,…>[:cwd=<b64>] | clear=1):mac=<sha256(body + ":" + token)> ST` per revision 0.5, and returns `undefined` for a malformed token or a command the terminal would reject (empty, a program starting with `-`, a relative program path, control characters, a relative cwd, more than 64 elements, or a sequence over 2048 bytes).

### Why

- The TUI package already owns the other terminal OSC encoders (title, OSC 9;4 progress, OSC 7501 program status).

### Why an extension could not handle it

- It is a renderer-library export consumed by interactive mode.

### Expected merge conflict zones

- LOW: one export line next to the `program-status.ts` export.
