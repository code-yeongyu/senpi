## 2026-11-13 - Land one session's retained-record writes in issue order (senpi#6595)

### What changed

- `packages/coding-agent/src/modes/rpc/session-router-residency.ts`: `recordRetainedSession` chains each write for a session after the previous one issued for it, and `clearRetainedRecord` (close, reclaim) joins the same chain; `recordedPath` still moves at issue time.
- `packages/coding-agent/src/modes/rpc/session-registry-types.ts`: `RpcSessionEntry` gains `recordWrite`, the session's last issued record write.

### Why

- `packages/coding-agent/src/modes/rpc/session-router-residency.ts` and `packages/coding-agent/src/modes/rpc/session-registry-types.ts`: a fire-and-forget stamped write (`followRetainedRecord` or the `set_session_context` sync) that first clears a switched-from entry enqueued itself after a park issued later, so the parked session stayed stamped resident and the next start skipped reopening it; a close or reclaim issued in the same gap was overtaken the same way, so the closed session's record survived and the next start reopened it (senpi#6594).

### Why an extension could not handle it

- `packages/coding-agent/src/modes/rpc/session-router-residency.ts` and `packages/coding-agent/src/modes/rpc/session-registry-types.ts` are the RPC host's own handover record; extensions have no hook into how the host orders its record writes.

### Expected merge conflict zones

- `packages/coding-agent/src/modes/rpc/session-router-residency.ts`: `recordRetainedSession`, now split into the chaining function and `writeRetainedRecord`.
- `packages/coding-agent/src/modes/rpc/session-registry-types.ts`: the field after `recordedPath`.
