## 2026-11-03 - A stale pre-#4436 writer no longer loses signed-in Claude accounts (senpi#5594)

### What changed

- `packages/coding-agent/src/core/credential-accounts.ts`: `renameCredentialAccount` awaits the rewrite of the renamed Claude CLI account's dir record (`renameAccountLink`) inside the same auth.json lock as the rename, so a later re-link restores the display name the user chose.
- `packages/coding-agent/src/core/auth-storage.ts`: the async load settles the Claude CLI account records inside its held store lock (`settleAccountLinks`): while a slot the legacy sign-out marked `legacy_sign_in_retired` is left, every recorded account dir no slot references takes its account back (`relinkAfterStaleWrite`) instead of keeping a fresh `dirId` and a sign-in prompt, and each healthy Claude CLI account whose dir has no record gets one (`backfillAccountLinks`); a record it cannot write is reported once. The synchronous load still signs legacy slots out at once and only leaves the revision unset while Claude CLI accounts exist, so the first async read settles the records; `settleLoad()` runs that read on demand and skips a store whose first load failed or found it locked, so startup never waits out a held lock. An async read records a load failure only when it is not the failure already recorded since the store last loaded (`recordAsyncLoadFailure`), so a broken or locked store is reported once per startup. No account-record I/O is synchronous on the session path.

### Why

- An engine from before senpi#4436 that is still running writes its token-shaped copy of the entry back over the Claude CLI slots; the next load gave the account a new dir and orphaned the dir holding the working login, and a second account the stale copy did not hold was lost (senpi#5594).

### Why an extension could not handle it

- The sign-out runs at the auth.json load seam in core, before any extension loads.

### Expected merge conflict zones

- LOW: the `withLockAsync` callback of `reloadLockedAsync` and the revision line of `reload()`; the `renameSlotDisplayName` return in `renameCredentialAccount`.

## 2026-11-03 - Startup credential notices wait for the async load (senpi#5594)

### What changed

- `packages/coding-agent/src/main.ts`: `collectAuthDiagnostics` and `interactiveAuthNotices` are async and await `authStorage.settleLoad()` before taking notices; every call site (model listing, runtime creation, interactive start, print mode) awaits them.

### Why

- The first auth.json load is synchronous and cannot re-link Claude CLI account dirs after a stale pre-#4436 write; without the settle, a fresh start told the user to sign in again for accounts its own async load re-linked a moment later (senpi#5594).

### Why an extension could not handle it

- The startup notices are collected by the CLI entry point before any extension runs.

### Expected merge conflict zones

- LOW: the `collectAuthDiagnostics` / `interactiveAuthNotices` signatures and their four call sites in `main()`.

## 2026-11-03 - Signed-in account dirs record their account (senpi#5594)

### What changed

- `packages/coding-agent/src/core/extensions/builtin/anthropic-subscription/claude-cli-account-link.ts` (new): every read and write is asynchronous (`node:fs/promises`). `writeAccountLink` keeps `.senpi-account.json` inside each signed-in account dir (slot name, `signedInAt`, display name; no token, 0600); `renameAccountLink` rewrites the display name on a rename; `backfillAccountLinks` records existing signed-in accounts; `relinkAfterStaleWrite` runs only while a `legacy_sign_in_retired` slot is left and re-links unreferenced dirs (read in dir-id order; newest sign-in per name wins, ties by dir id; the record's display name wins over the stale slot's; a healthy slot keeps its dir; a missing account is appended), returning the same list when nothing changed so a second load writes nothing.
- `packages/coding-agent/src/core/extensions/builtin/anthropic-subscription/oauth-login.ts`: a login awaits the record write right after it claims its slot; a failed record write keeps the sign-in and is reported through the login's progress, and the next load's backfill writes the record again.

### Why

- auth.json alone cannot keep the slot-to-dir link while an older engine can overwrite the entry (senpi#5594).

### Why an extension could not handle it

- This is the extension's own login path.

### Expected merge conflict zones

- LOW: the claim step in `login()` of `oauth-login.ts`.
