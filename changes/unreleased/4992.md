## 2026-10-30 - Extension failures carry a user-facing contract; the runner logs their stacks (senpi#4990)

### What changed

- `packages/coding-agent/src/core/extensions/types.ts`: `ExtensionError` gains optional `userFacing` (`UserFacingErrorInfo`: `code`, `message`, `action?`, `docsUrl?`); `stack` stays for programmatic listeners and is documented as never rendered.
- `packages/coding-agent/src/core/extensions/runner.ts`: every capture site builds its error through `extensionFailureFields` (message, stack, user-facing contract), and `emitError` records each failure in the debug log through `recordExtensionFailure` before notifying listeners.
- `packages/coding-agent/src/core/extensions/index.ts`: exports `UserFacingError`, `userFacingErrorOf` and `UserFacingErrorInfo`.

### Why

- `packages/coding-agent/src/core/extensions/types.ts`: an extension had no typed way to say a failure is meant for the user, so a coded, actionable failure was rendered like a crash.
- `packages/coding-agent/src/core/extensions/runner.ts`: hosts rendered `err.stack` on screen; it now has one home, the debug log.
- `packages/coding-agent/src/core/extensions/index.ts`: extensions import the contract from the public package.

### Why an extension could not handle it

- `packages/coding-agent/src/core/extensions/types.ts`: the error record and its listeners are the runner's contract with every host.
- `packages/coding-agent/src/core/extensions/runner.ts`: handler failures are caught inside the runner before any extension sees them.
- `packages/coding-agent/src/core/extensions/index.ts`: the public export surface is core.

### Expected merge conflict zones

- `packages/coding-agent/src/core/extensions/types.ts`: the `ExtensionError` interface and the type import block.
- `packages/coding-agent/src/core/extensions/runner.ts`: the `catch` blocks of the emit helpers (`emitProjectTrustEvent`, provider and virtual-model registration, `reportHandlerFailure`, boundary entries, session-before, model_select, tool_result, user_bash, before_provider_request/headers, input), `emitError`, and the import block.
- `packages/coding-agent/src/core/extensions/index.ts`: the export list next to `wrapRegisteredTool`.

## 2026-10-30 - Startup extension diagnostics use the calm notice line (senpi#4990)

### What changed

- `packages/coding-agent/src/core/agent-session-services.ts`: provider and virtual-model registration failures become `reportExtensionFailureLine` diagnostics (extension name, reason without paths, debug log location) instead of `Extension "<path>" error: <message>`.
- `packages/coding-agent/src/core/project-trust.ts`: `project_trust` handler failures use the same line.

### Why

- `packages/coding-agent/src/core/agent-session-services.ts`: the diagnostic printed the extension's absolute install path; the details belong in the debug log.
- `packages/coding-agent/src/core/project-trust.ts`: same framing as above.

### Why an extension could not handle it

- `packages/coding-agent/src/core/agent-session-services.ts`: these diagnostics are built by the session services before any extension can observe them.
- `packages/coding-agent/src/core/project-trust.ts`: the trust decision runs in core before the session starts.

### Expected merge conflict zones

- `packages/coding-agent/src/core/agent-session-services.ts`: the two `catch` blocks in the provider and virtual-model registration loops and the import block.
- `packages/coding-agent/src/core/project-trust.ts`: the `onExtensionError` call in `resolveProjectTrusted` and the import block.

## 2026-10-30 - Extension failures show as a notice box, never a stack (senpi#4990)

### What changed

- `packages/coding-agent/src/modes/interactive/interactive-mode.ts`: `showExtensionError` renders `extensionErrorNoticeSpec(describeExtensionError(...))` through `showNoticeBox` (warning tone) instead of the `Extension "<path>" error:` headline plus every stack line.

### Why

- `packages/coding-agent/src/modes/interactive/interactive-mode.ts`: a user-actionable failure (omo computer use's launch-context refusal) appeared as a crash dump with internal paths and module frames.

### Why an extension could not handle it

- `packages/coding-agent/src/modes/interactive/interactive-mode.ts`: the runner's error listener is wired by `InteractiveMode`; extensions cannot change how their own failures are rendered.

### Expected merge conflict zones

- `packages/coding-agent/src/modes/interactive/interactive-mode.ts`: the body of `showExtensionError` and the import block (`extension-error-format.ts`, `error-notice.ts`).

## 2026-10-30 - Print mode and package commands keep stacks off the terminal (senpi#4990)

### What changed

- `packages/coding-agent/src/modes/print-mode.ts`: the runner `onError` writes the notice lines to stderr instead of `Extension error (<path>): <message>`.
- `packages/coding-agent/src/package-manager-cli.ts`: a settings error's stack goes to the debug log and the terminal shows `Details: <debug log>`.
- `packages/coding-agent/src/index.ts`: exports `UserFacingError`, `userFacingErrorOf` and `UserFacingErrorInfo`.

### Why

- `packages/coding-agent/src/modes/print-mode.ts`: same calm notice on every surface.
- `packages/coding-agent/src/package-manager-cli.ts`: a stack on the terminal is not something the user can act on.
- `packages/coding-agent/src/index.ts`: extensions need the contract from the package root.

### Why an extension could not handle it

- `packages/coding-agent/src/modes/print-mode.ts`: print mode owns the runner's error listener.
- `packages/coding-agent/src/package-manager-cli.ts`: package commands run before any extension loads.
- `packages/coding-agent/src/index.ts`: the package export surface is core.

### Expected merge conflict zones

- `packages/coding-agent/src/modes/print-mode.ts`: the `onError` option of `bindExtensions` and the import block.
- `packages/coding-agent/src/package-manager-cli.ts`: `reportSettingsErrors` and the import block.
- `packages/coding-agent/src/index.ts`: the `./core/extensions/index.ts` export list.

### Fixed
- An extension failure no longer prints its absolute path and stack trace in the TUI, print mode or startup diagnostics: it shows a short notice (what happened and what to do for a coded failure, otherwise "Something went wrong in <extension>" with a one-line reason and the debug log location), and the stack goes to the debug log ([#4990](https://github.com/code-yeongyu/senpi/issues/4990))

### Added
- `UserFacingError` / `userFacingErrorOf`: extensions throw a failure with `code`, `message`, `action` and an optional `docsUrl` (or set a `userFacing` property on any thrown object), and every host shows only those fields; RPC `extension_error` carries the resulting `notice` ([#4990](https://github.com/code-yeongyu/senpi/issues/4990))
