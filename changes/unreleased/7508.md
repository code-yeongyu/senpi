## 2026-11-26 - One publisher per release tag; the draft cleanup keeps a draft another run published (senpi#7469)

### What changed

- `scripts/release.mjs`: after preparing a version, the closing line says the tag's Build Binaries run publishes it (it dispatches `publish-npm.yml` publish-only itself). It no longer prints a `gh workflow run publish-npm.yml ... -f publish-only=true` command for a person to run. If that publish-only run fails, it says to re-run it (`gh run rerun <its run id> --failed`, which keeps `build_run_id` so finalize runs again) and to dispatch publish-only by hand only when Build Binaries itself failed.
- `scripts/release-draft-cleanup.sh`: before deleting a draft GitHub Release because npm lacks the version, it lists the `publish-npm.yml` dispatch runs. It keeps the draft (exit 1, with the recovery steps) while a run that really published the version succeeded: a dispatched run whose title has the version and `publish-only` and not `dry-run`. The stamp run and dry runs carry the version in their titles too and do not count. It also keeps the draft when the runs cannot be listed.

### Why

- For 2026.11.25 the printed hand dispatch and the tag's Build Binaries dispatch both published. The hand run published every package. Build Binaries' run met the registry's lag on the main package and failed, and its finalize deleted the draft even though npm had the release.

### Why an extension could not handle it

- This is release tooling, which runs in GitHub Actions; no extension runs there.

### Expected merge conflict zones

- LOW: the closing log line of `scripts/release.mjs`; the end of `scripts/release-draft-cleanup.sh`, before its final delete.

## 2026-11-26 - A manual publish-only run is refused while another publisher handles the tag (senpi#7469)

### What changed

- `.github/workflows/publish-npm.yml`: the release job of a manual publish-only run (`build_run_id` empty, not a dry run) first refuses, before checkout and before any publish, while a Build Binaries run for `v<version>` is queued or running, or while another publish-only run of the version (not a dry run, not this run) is running or has published it, naming those runs. When Build Binaries succeeded but its publish-only run failed, it refuses and names the recovery: `gh run rerun <that run> --failed`. A manual run stays available when Build Binaries itself failed. The run title carries the version and marks publish-only and dry runs (`run-name: Release <version>[ publish-only][ dry-run]`), which the guard and the draft cleanup read.
- `.github/workflows/build-binaries.yml`: the run title carries the tag (`run-name: Build Binaries <tag or ref>`), so a dispatched recovery run, which runs on main, is still matched to its tag by the guard.

### Why

- Two publish-only runs of one tag raced in 2026.11.25, and the second run's finalize deleted the draft GitHub Release.

### Why an extension could not handle it

- This is a release workflow; no extension runs in it.

### Expected merge conflict zones

- LOW: the top of `publish-npm.yml` (the `run-name` line) and the first step of its release job; the top of `build-binaries.yml` (its new `run-name` line).
