## 2026-11-09 - Provider access declarations on provider hooks, and a hand's request-hook dispatch (custody CK21, senpi#6278)

### What changed

- `packages/coding-agent/src/core/extensions/types.ts`: `ProviderHookOptions` (`HandlerRegistrationOptions` plus `providers?: readonly ProviderId[]`) is the registration option type of `pi.on("before_provider_request" | "provider_stream_event" | "after_provider_response", ...)`; `Extension.handlerProviders` records each declared handler's providers.
- `packages/coding-agent/src/core/extensions/loader.ts`: `on()` validates a `providers` declaration on those three events (a non-empty array of non-empty provider ids, else it throws naming the extension), on every side, also for a handler whose `runs` side does not register it, and records it; other events ignore the option, as they ignore `previewSafe`.
- `packages/coding-agent/src/core/extensions/runner.ts`: `emitBeforeProviderRequest` takes an optional fourth argument, `HandRequestHookDispatch` (`only`, `model?`). With it, only the extensions `only` accepts run, the event carries that model and no headers, and the sessionless drop does not apply. Without it, which is every existing caller, dispatch is unchanged.

### Why

- A hand advertises to a hosted brain which providers' calls need the device's request and stream hooks; an undeclared hook means every provider (#5849). The declaration never filters dispatch anywhere.
- A hand serving a hosted loop's `hook.model_request` runs the user's request hooks on a runner that has no loop of its own.

### Why an extension could not handle it

- The declaration is part of the extension registration API, and the hand's request-hook dispatch is the runner's own dispatch.

### Expected merge conflict zones

- LOW: the three provider-hook `on()` overloads in `types.ts`, the `Extension` interface, the `on()` registration body in `loader.ts`, and the head of `emitBeforeProviderRequest` in `runner.ts`.

## 2026-11-09 - Hand hook advertisement and the request-hook contract (custody CK21, senpi#6278)

### What changed

- `packages/coding-agent/src/core/hand/hook-contract.ts` (new): `HookRequestInput`, the pinned shape of `HookModelRequestInput` (`{ payload, model? }`: the fused `before_provider_request` input without the request headers or the model's `headers`); `hookRequestInputOf`, `hookRequestInputForCall` (none for an aux call), `parseHookRequestInput` (closed envelope), `serveHookModelRequest` (placement claim first, then the input, then the hooks) and `loopHookRequestHooks` over a hand's loop-hook runner, whose result carries the hooks' failures (`errors`) and the messages and notices they sent (`sent`, `notices`, `droppedLate`) with the `output`, as every loop-hook reply does.
- `packages/coding-agent/src/core/egress/wire.ts`: `HookModelRequestReply` gains the optional `errors` (`HookFailure`: `extensionPath`, `event`, `error`), `sent`, `notices` and `droppedLate`, so a user hook's failure on the hand reaches the hosted side instead of disappearing.
- `packages/coding-agent/src/core/hand/hook-advertise.ts` (new): `handHookAccess` (request and stream hooks of the user's extensions from their `providers` declarations, `"*"` for any undeclared one), `computeAdvertHash` (`sha256:` over the canonical JSON of the extension set hash, cwd and project-local hook set), and `createHandHookLink`, which sends every bound session's `hand.session.advertise` first on each (re)connect and refuses a `hook.model_request` its session's advertisement on that connection did not precede. Only that check and the reply's send are ordered on the link; each request's hooks run concurrently outside it, so a slow hook holds back no other session's reply and no reconnect's advertisements, and a reply whose connection was replaced meanwhile is not sent.

### Why

Row CK21 of hosted model-key custody (#5849): the brain needs the device's hook view before it dispatches a hooked call, and the hook input must be exactly what a fused session's hooks see.

### Why an extension could not handle it

The advertisement and the hook contract are part of the custody wire between a hosted brain and the device, below every extension.

### Expected merge conflict zones

- None: both files are new and fork-only.

## 2026-11-09 - A hand runs a hosted loop's request hooks (custody CK21, senpi#6278)

### What changed

- `packages/coding-agent/src/modes/rpc/loopless-tool-handlers.ts`: `extensionLoopHooks` serves `before_provider_request` (payload `{ sessionId, idle, input }`, the input in CK21's closed envelope): the user's request hooks (the same `isUserLoopHook` set as `input` and `before_agent_start`, now exported) run on the payload with the loop's effective model, inside a loop-hook call bound to that session, and the reply is `{ output }` with the payload they produced.

### Why

A hosted loop's request hooks run on the user's machine, in the same extension instances as its tool and loop hooks (#5849).

### Why an extension could not handle it

The loop-hook link and the events it serves are the hand runtime itself.

### Expected merge conflict zones

- LOW: the event branches of `extensionLoopHooks`.
