### Fixed

- With two or more logins for one provider, an account whose credential the token endpoint refused (HTTP 401, `invalid_grant`, an expired, reused or invalidated refresh token, a revoked token) or whose token was revoked or invalidated server-side (with or without an HTTP status) is now blocked and the request moves to a sibling account before any output, instead of failing the request; transient token-endpoint failures still retry the same account, and any other failed refresh never blocks one. Unrelated session invalidation and statusless transport failures carrying auth diagnostics do not block an account ([#5010](https://github.com/code-yeongyu/senpi/pull/5010), fixes [#3037](https://github.com/code-yeongyu/senpi/issues/3037), part of [#2304](https://github.com/code-yeongyu/senpi/issues/2304))

## 2026-10-30 - An auth failure of one pooled account fails over (senpi#2304, senpi#3037, senpi#5010)

### What changed

- `packages/coding-agent/src/core/credential-pool/classify.ts`: before any auth prose, a failed refresh (`ModelsError` code `oauth` in the cause chain) classifies as `failover` with `auth_error` only when its `OAuthTokenEndpointError` cause refused the credential (`isRefusedGrant`: any 401, a 400 naming `invalid_grant`, `refresh_token_*` or `token_revoked`, or a 403/404 whose OAuth JSON body does), and as `fail_request` otherwise. A provider diagnostic in the auth category or with an auth token code (`token_revoked`, `token_invalidated`, ...; not `token_expired`) classifies as `failover` with `auth_error` unless a provider fault or a 429 takes precedence, including statusless network/timeout faults. `REVOKED_TOKEN_TEXT` joins `INVALID_KEY_TEXT` as the prose last resort under the same provider-fault guard, matching token revocation rather than unrelated session invalidation.
- `packages/coding-agent/src/core/credential-pool/rotation-events.ts`: `rotationErrorFromEvent` attaches the event's whole provider diagnostic, not only its HTTP status.

### Why

- A refused refresh token (no status) and a statusless revoked-token frame classified as `fail_request`, so one dead account dead-ended a pool with healthy siblings, and a pinned dead account was selected on every request.

### Why an extension could not handle it

- Classification runs inside the core credential-pool engine that `ModelRuntime` drives; no extension hook sees the failure before it is classified.

### Expected merge conflict zones

- LOW: the auth branch of `classifyCredentialFailure` and the regex block above it in `classify.ts`; `rotationErrorFromEvent` in `rotation-events.ts`.
