## Bundled skill resolves to a real file beside the executable (2026-11-22)

### What changed

- `index.ts`: `bundledSkillPath()` resolves the module-relative copy, then the shipped skill directory beside the executable (new `getImagegenSkillDir()` row in `config.ts`'s `ShippedAsset` table), then the embedded `type: "file"` import; a Bun locator (`/$bunfs/…`, `~BUN…`, `%7EBUN…`, via new `isBunVirtualPath()` in `config.ts`) is never returned. The miss notice now names both probed locations once. `registerImageGenExtension` takes an optional injectable environment so compiled-binary layout is testable from source runs.
- `core/bundled-resources.ts`: the read-permission root is `getImagegenSkillDir()` instead of the module-relative directory, so a compiled binary advertises the real sidecar root.
- `scripts/build-binaries.sh`: stages `dist/core/extensions/builtin/imagegen/skill/` to `skill/` beside each compiled binary, beside the theme and asset dirs.

### Why

- In a `bun build --compile` binary the embedded import resolves to `/$bunfs/root/SKILL-<hash>.md` (POSIX) or `B:\~BUN\root\…` (Windows): existsSync passes, descriptor-based readers get ENOENT, and no client or child process can open it. Clients list skills by path and offer to open them (senpi#3799), so the advertised path must be a real on-disk file — the same sidecar mechanism the codemode bun skill, themes, and interactive assets already use.

### Merge-conflict zones

- LOW: resolution order lives in `index.ts`; the asset-table row and getter live in `config.ts`.
- LOW: one staging line pair in `scripts/build-binaries.sh`, covered by `scripts/build-binaries-staging.test.mjs`.

## Release staging ships the imagegen skill beside the binary (2026-11-22)

### What changed

- `scripts/build-binaries.sh`: the per-platform staging block copies `dist/core/extensions/builtin/imagegen/skill/` to `skill/` beside each compiled binary, next to the theme and asset directories. `scripts/build-binaries-staging.test.mjs` runs the real staging block and asserts `skill/SKILL.md` lands in the archive.

### Why

- A compiled binary's embedded `type: "file"` import resolves to a Bun locator (`/$bunfs/…`, `B:\~BUN\…`) that no descriptor-based reader or external process can open (senpi#3799). The runtime resolves the skill from the shipped directory beside the executable, so the build must stage it there.

### Expected merge conflict zones

- LOW: one staging line pair inside the `# Copy shared files` block, shared with any other lane adding staged assets.
