### Added
- RPC `prompt`, `steer` and `follow_up` accept `chainCount`, the hop count of a thread call from another session. It is admitted against the user's `threads.chainCountLimit`: with no limit set every count is admitted, and past the limit the input is refused with `errorCode: "chain_count_limit"` and `errorData: { count, limit }` before anything of it runs. An admitted count is reported on the `input` extension event as `chainCount` ([#5923](https://github.com/code-yeongyu/senpi/pull/5923)).

## 2026-11-05 - Thread calls carry their chain count and meet the user's limit (senpi#5923)

### What changed

- `packages/coding-agent/src/modes/rpc/rpc-session-command-types.ts`: `prompt`, `steer` and `follow_up` take an optional `chainCount`.
- `packages/coding-agent/src/modes/rpc/method-classes-schema-session.ts`: the three schemas accept `chainCount`, a positive safe integer.
- `packages/coding-agent/src/modes/rpc/chain-admission.ts` is new: `admitInputChain()` admits an input's `chainCount` with `admitChainCall()` against `settingsManager.getThreadChainCountLimit()`, or returns the typed refusal (`errorCode: "chain_count_limit"`, `errorData: { count, limit }`). A `chainCount` that is not a positive safe integer is refused first with `errorCode: "invalid_chain_count"` and `errorData: { chainCount }`, since the RPC boundary only shape-checks a command and a malformed count would never compare above the limit.
- `packages/coding-agent/src/modes/rpc/connection-handler.ts`: `prompt`, `steer` and `follow_up` run `admitInputChain()` first, before `holdAutomaticInput` can keep the input as a notice, and answer its refusal.
- `packages/coding-agent/src/modes/rpc/client-input-handler.ts`: runs the same admission before `ClientAdmissions` records anything and passes an admitted count to the session.

### Why

senpi#5641 / #5899 (decision K8): the user-set thread chain count limit has to be read where chains are created. A thread call reaches another session as RPC input, so the limit is enforced there. Unset means unlimited; there is no default cap and no cost limit.

### Why an extension could not handle it

The refusal has to happen before the input is admitted and recorded, which only the RPC input path controls.

### Expected merge conflict zones

- LOW: the `prompt`/`steer`/`follow_up` command types and schemas, their cases in `connection-handler.ts`, the top of `handleClientInput` and its error mapping.

## 2026-11-05 - A terminal refuses a thread call's `chainCount` (senpi#5923)

### What changed

- `packages/coding-agent/src/modes/interactive/session-control-rpc-commands.ts`: `chainCount` is in `UNSERVED_INPUT_FIELDS`, so a terminal's session-control endpoint refuses a thread call carrying it with `unsupported_field` instead of admitting it.

### Why

A terminal admits input as text through its external admission, which cannot carry a hop count; admitting the call would restart its chain there and bypass the user's `threads.chainCountLimit` (decision K8).

### Why an extension could not handle it

The terminal's input admission is the session-control endpoint itself.

### Expected merge conflict zones

- LOW: `UNSERVED_INPUT_FIELDS`.

## 2026-11-05 - Input carries a thread call's chain count (senpi#5923)

### What changed

- `packages/coding-agent/src/core/agent-session.ts`: `PromptOptions` and `QueuedInputOptions` take `chainCount`, passed to the `input` event from `prompt()` and from `_runInputHandlers` for steer and follow-up input.

### Why

A session that received a thread call needs the call's hop count so a thread call it sends next carries one more (decision K8).

### Why an extension could not handle it

The `input` event is built inside the session.

### Expected merge conflict zones

- LOW: the `emitInput` call in `prompt()`, `_runInputHandlers` and its call in `_admitQueuedInput`.

## 2026-11-05 - `InputEvent.chainCount` (senpi#5923)

### What changed

- `packages/coding-agent/src/core/extensions/types.ts`: `InputEvent.chainCount?: number`.
- `packages/coding-agent/src/core/extensions/runner.ts`: `emitInput` takes an optional eighth argument `chainCount` and puts it on the event when set.

### Why

Extensions that send thread calls read the received hop count from the `input` event (decision K8).

### Why an extension could not handle it

The event shape and its emitter are owned by the runner.

### Expected merge conflict zones

- LOW: the `InputEvent` interface and the `emitInput` signature.
