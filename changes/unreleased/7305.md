## 2026-11-22 - A Windows sync credential write that cannot replace auth.json says the file may be in use (senpi#6860)

### What changed

- `packages/coding-agent/src/core/auth-storage.ts`: `FileAuthStorageBackend.withLock` rethrows a win32 rename of the staged file over `auth.json` that fails with EPERM, EACCES or EBUSY as an "auth.json may be in use" error carrying the native `code` and the original error as `cause`. Staging failures and every other error pass through unchanged.

### Why

- Sync writers (`set`, `remove`, `setSlot`, reload write-back) cannot wait for another process to close the file without blocking the session loop, so they only reported a bare `EPERM ... rename` (senpi#6860; the async path already retries, #6849).

### Why an extension could not handle it

- The write happens inside the core credential store under its file lock; no extension hook observes or wraps that rename.

### Expected merge conflict zones

- LOW: the `next !== undefined` branch of `withLock` in `auth-storage.ts`.

### Fixed
- On Windows, a credential write that cannot replace `auth.json` because another process holds it open now reports that the file may be in use, keeping the original error code, instead of a bare `EPERM ... rename` ([#6860](https://github.com/code-yeongyu/senpi/issues/6860))
