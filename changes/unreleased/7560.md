## 2026-11-27 - A normal stop refuses a draining host that still holds sessions (senpi#7132)

### What changed

- `packages/coding-agent/src/modes/rpc/host-observe-request.ts`: `ObserverCensus` reads the host's `list_sessions` over the supervisor's observer link. The read is `observe: true`, carries only `include_workers`, and never carries `hold_host`. It answers with the host's own response, or `undefined` when the link is lost or the host gives no answer within 10 s.
- `packages/coding-agent/src/modes/rpc/host-lifecycle-activity.ts`: `SupervisorActivity.listSessions` sends that read over the observer connection and hands its response lines to the census before any other reading.
- `packages/coding-agent/src/modes/rpc/host-admission.ts`: `HostAdmission` takes an optional `HostSessionCensus` and exposes it as `listSessions`.
- `packages/coding-agent/src/modes/rpc/host-lifecycle.ts`: the supervisor gives its admission the activity's census.
- `packages/coding-agent/src/modes/rpc/host-admission-proxy.ts`: a connection accepted after admission stopped (it has no hop to the host) gets its `list_sessions` answered from the census, with its own request id. An unanswered census reads `host_stopping` as before, and so does every other request on that connection.
- `packages/coding-agent/src/modes/rpc/host-stop.ts`: `occupancyRefusal` is the one occupancy gate of a hard stop. A host that answers `get_protocol_info` (ready or stopping) but not its session count is refused `sessions_unknown`, and a count above zero is refused `sessions_live`. A socket where nothing answers `get_protocol_info` stays stoppable, and `force` skips the gate. `StopHostResult` gains the `sessions_unknown` reason.
- `packages/coding-agent/src/modes/rpc/host-runner.ts`: `senpi host stop` runs the same gate. Its `sessions` field is `null` in every answer (refused, `stopped`, `drained`, `--force` included) whose count the host did not answer; it used to print zero counts there.
- `packages/coding-agent/src/modes/rpc/host-status.ts`, `packages/coding-agent/src/modes/rpc/host-status-rows.ts`: `parseSessionRows` and `readSessionCounts` return `undefined` for an unanswered listing instead of an empty one. `host status` lists a stopping host's sessions too.

### Why

- Once a drain began, the supervisor answered `host_stopping` to every request on a new public connection, `list_sessions` included, because a draining host destroys connections that arrive after its drain. Both stop paths read that refusal as zero sessions and signalled the generation, which cut a turn that was still streaming.

### Why an extension could not handle it

- The supervisor, its admission proxy and the stop gate are host lifecycle internals; no extension runs in the supervisor or decides a stop.

### Expected merge conflict zones

- LOW: `host-admission-proxy.ts`, the request branch chain in `requests()`.
- LOW: `host-stop.ts`, the occupancy check in `stopHostLocked`; `host-runner.ts`, the census in `stopOutcome`.
- LOW: `host-lifecycle-activity.ts`, `connectObserver` and `observeHostEvent`; `host-lifecycle.ts`, the `HostAdmission` construction.

### Fixed
- A normal `senpi host stop` (and `stopHost` without `force`) no longer ends a draining host that still holds a session, which cut off an answer that was still streaming. A draining host keeps answering `list_sessions`, and a host that answers but does not give its count is refused with the new reason `sessions_unknown` instead of being treated as empty. `senpi host stop` now prints `sessions: null` rather than zero counts whenever the host did not answer its count, forced and drained stops included ([#7560](https://github.com/code-yeongyu/senpi/pull/7560))
