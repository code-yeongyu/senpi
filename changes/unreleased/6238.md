## 2026-11-08 - `admit_external_message`: a relayed peer-agent message admitted as a delivery (senpi#6233)

### What changed

- `packages/coding-agent/src/modes/rpc/admit-external-message-wire.ts` (new): the record (`deliveryId`, `text`, `sender?`, `displayText?`, `deliverAs`, `expectedTurnId?` string, `whenIdle?`, `chainCount?`), its reply `{ kind, turnId }`, and the field check both validators run (closed sender shapes, a record naming `remote_origin` refused).
- `packages/coding-agent/src/modes/rpc/admit-external-message-command.ts` (new): the handler. It runs the K8 chain guard first, refuses a `command_line` sender from a remote device, keys the ledger as `rpc:local/<id>` or `device:<deviceId>/<id>`, answers `already_admitted` for an id the transcript holds, stamps the connection's remote device and engine provenance on a remote delivery, and marks the delivery with the connection's turn origin.
- `packages/coding-agent/src/modes/rpc/method-classes-schema-delivery.ts` (new): the inbound schema; `method-classes-schema-session.ts` spreads it in.
- `packages/coding-agent/src/modes/rpc/method-classes.ts`: `admit_external_message: "drive"` (the method-classes digest moves).
- `packages/coding-agent/src/modes/rpc/connection-handler.ts`: the case, fed with `ConnectionRoles.originOf` and the connection origin.
- `packages/coding-agent/src/modes/rpc/rpc-session-command-types.ts`, `rpc-response-types.ts`, `rpc-input-validation.ts`: the record, its response and its field check joined to the existing unions and validator.
- `packages/coding-agent/src/modes/rpc/host-idle-handover.ts`: the record is new work, like `wake`.

### Why

A client relaying one agent's message to a session on another device could only send it as a user prompt (`role: "user"`, the `input` event, slash dispatch), never as the delivery `pi.session.admitExternalMessage` writes in process (#6233). The security design gate made the engine-stamped origin, the namespaced and restart-safe ledger, the per-lane approval origin and the chain guard binding.

### Why an extension could not handle it

The RPC record table, the method-class table and the connection's authenticated origin are engine-owned; an extension cannot add a session record or read which device a connection speaks for.

### Expected merge conflict zones

- LOW: `connection-handler.ts` (one case beside `wake`), `method-classes.ts` (one table row), the two union files.

## 2026-11-08 - Engine-stamped delivery provenance and a delivery's turn origin (senpi#6233)

### What changed

- `packages/coding-agent/src/core/external-admission.ts`: `admit(input, stamp)` takes an engine-only `DeliveryStamp` (remote origin, chain count, turn mark) that `pi.session.admitExternalMessage` never passes; `writtenDeliveryIds` folds the transcript's delivery ids.
- `packages/coding-agent/src/core/turn-origin.ts`: `hasInputTurnMark`.
- `packages/coding-agent/src/core/agent-session.ts`: a marked custom message (a delivery) sets the turn's origin at `message_start`, as a user message does, so a remote device's follow-up consumed inside a local turn runs under the delegated approval rule.

### Why

senpi#6233 security gate H1/H2/H3: a remote delivery's provenance must be engine-authored, a remote follow-up must not inherit a local turn's origin, and replay must be refused after a restart.

### Why an extension could not handle it

Admission, the turn-origin rule the permission decision reads, and the transcript fold are core session state.

### Expected merge conflict zones

- LOW: the one `message_start` condition in `agent-session.ts` `_handleAgentEvent`.

## 2026-11-08 - `SessionControlRemoteOrigin` on a delivery's details (senpi#6233)

### What changed

- `packages/coding-agent/src/core/extensions/session-control-types.ts`: `SessionControlRemoteOrigin`, the engine-stamped `remote_origin` and `chain_count` fields of `SessionControlDeliveryDetails`, and `sessionControlRemoteOriginOf`.

### Why

A delivery admitted over RPC for a remote device carries the device the engine authenticated, for human surfaces and audit (#6233).

### Why an extension could not handle it

The fields are written by the engine's admission; an extension reads them through the exported parser.

### Expected merge conflict zones

- None: additive optional fields.

### What changed

- `packages/coding-agent/src/modes/interactive/components/remote-delivery-message.ts`: a delivery with `details.remote_origin` renders "Relayed from device ..." first, then the claimed sender, over its display text.
