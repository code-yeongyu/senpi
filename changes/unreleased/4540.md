## 2026-10-27 - The reply language survives compaction and long tool output (omo#11527)

### What changed

- `packages/coding-agent/src/core/reply-language-reading.ts`: new. `readReplyLanguage` reads the language a user message is written in from the user's own lines only: fenced and inline code, `<name>...</name>` blocks (`<environment_context>`, reminders), links, quoted (`>`) lines and lines that read as pasted log or error output are dropped. The first remaining line with two or more words decides; otherwise all remaining prose does. A non-Latin script with at least 30% of the words names the language. Latin-dominant text is not named. A script shared by several languages is named by its script (`Cyrillic script`). `readReplyLanguageRequest` reads an explicit reply-language request ("앞으로 답변은 영어로 해줘", "영어로 답해줘", "reply in Korean from now on"), skipping negated requests and other tasks such as translation. The last request in the message wins. The tag strip is a single linear pass, so an unclosed `<` (TypeScript generics) no longer triggers the quadratic regex backtracking that took 345-1137 ms on a 100 KB paste.
- `packages/coding-agent/src/core/user-language.ts`: new. `insertReplyLanguageNotes` adds one user-role note after a tool-result run that is followed by the next assistant message (or the end of the context). It is added once 4000 characters of tool results, custom messages, bash output and branch summaries have built up since the user's last message. The note names the reply language the user explicitly asked for; otherwise the non-Latin language they write in. A run that carries words the user typed into a tool's answer gets no note, since those words already follow it as a user message (senpi#2920, senpi#2118). A note can only name one of the fixed language names (`REPLY_LANGUAGE_NAMES`), so no user text is ever copied into it. A note already in the context (converted output converted again) keeps its language. Each message's reading is cached in a `WeakMap` keyed by the message and its content object, so repeated `convertToLlm` calls do not re-read history. `replyLanguageOf` computes the same state over a message list.
- `packages/coding-agent/src/core/messages.ts`: `convertToLlm` runs `insertReplyLanguageNotes` first. A compaction summary with a `userLanguage` renders the same note after `</summary>` inside its own text block, so no new user message is added. `CompactionSummaryMessage` gains the optional `userLanguage` and `userLanguageRequested`.
- `packages/coding-agent/src/core/session-manager.ts`: `projectSession` sets `userLanguage`/`userLanguageRequested` on the newest compaction summary from the user messages before that compaction entry (`annotateCompactionUserLanguage`). It is derived at projection time, so sessions compacted before this change get it too, an explicit request survives the compaction, and the session file format is unchanged.
- `packages/coding-agent/src/core/tool-result-user-words.ts`: the private `wordMessage` is exported as `followerMessage` and takes any `Message` source, so the reply-language note reuses its provenance rule.

### Why

- omo#11527: a Korean-speaking user got English replies after compactions and tool-heavy turns. After a compaction the context held no Korean user turn and nothing that named the user's language. The summary prompt (`extensions/builtin/compaction/prompts.ts`) has no language field and its English template produces English prose. Long English tool output then sat between the last Korean message and every reply. The only language rule was one sentence in the Handoff section of the system prompt.
- The note is derived only from the messages, at fixed positions, so each request extends the previous one byte for byte and the provider's cache prefix stays valid.

### Why an extension could not handle it

- The note must be part of every provider request and of compaction-summary rendering, which `convertToLlm` and the session projection own. A `context` hook would not reach the summarization and transport paths that call `convertToLlm` directly.

### Expected merge conflict zones

- LOW: the `convertToLlm` head in `messages.ts` and the compaction-summary case; the tail of `projectSession` in `session-manager.ts`.

## 2026-10-27 - Compaction summaries can carry the user's reply language (omo#11527)

### What changed

- `packages/agent/src/harness/messages.ts`: `CompactionSummaryMessage` gains the optional `userLanguage` and `userLanguageRequested`, set by the coding agent's session projection.

### Why

- The `AgentMessage` union takes `compactionSummary` from this interface, so the coding agent's reply-language note needs the fields here (omo#11527).

### Why an extension could not handle it

- A type in the shared message union.

### Expected merge conflict zones

- LOW: the `CompactionSummaryMessage` interface.

### Fixed
- Replies stay in the user's language after a compaction and after long English tool output. The context now names the reply language after the compaction summary and after long tool-output stretches: the language the user explicitly asked for, otherwise the non-Latin language (such as Korean) they write in.
