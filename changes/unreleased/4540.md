## 2026-10-27 - The reply language survives compaction and long tool output (omo#11527)

### What changed

- `packages/coding-agent/src/core/user-language.ts`: new. `readReplyLanguage` reads the language of one user message by script (Hangul, kana, Han, Thai, Greek, Hebrew, Cyrillic, Arabic, Devanagari), counting words (unspaced scripts at two characters a word) after dropping fenced/inline code, links and tagged blocks such as `<environment_context>`. A non-Latin script that is at least 30% of the words names the language; Latin-dominant text is not named (English needs no note, and Latin-script languages cannot be told apart safely); a script shared by several languages is named by its script (`Cyrillic script`). `insertReplyLanguageNotes` adds one user-role note naming that language after a tool-result run that the next assistant message (or the end of the context) follows, once 4000 characters of tool results, custom messages, bash output and branch summaries have accumulated since the user's last message. The user's own message, or words they typed into a tool's answer, resets the count. The note carries the tool result's request-local provenance like the user-words message does. A note already in the context (converted output converted again) is recognized and keeps its language.
- `packages/coding-agent/src/core/messages.ts`: `convertToLlm` runs `insertReplyLanguageNotes` first; a compaction summary with a `userLanguage` renders the same note after `</summary>` inside its own text block, so no two user messages become adjacent. `CompactionSummaryMessage` gains the optional `userLanguage`.
- `packages/coding-agent/src/core/session-manager.ts`: `projectSession` sets `userLanguage` on the newest compaction summary from the latest user message before that compaction entry on the path (`annotateCompactionUserLanguage`). It is derived at projection time, so sessions compacted before this change get it too and the session file format is unchanged.
- `packages/coding-agent/src/core/tool-result-user-words.ts`: the private `wordMessage` is exported as `followerMessage` and takes any `Message` source, so the reply-language note reuses its provenance rule.

### Why

- omo#11527: a Korean-speaking user got English replies after compactions and tool-heavy turns. After a compaction the context held no Korean user turn and nothing that named the user's language: the summary prompt (`extensions/builtin/compaction/prompts.ts`) has no language field and its English template produces English prose, and long English tool output then sat between the last Korean message and every reply. The only language rule was one sentence in the Handoff section of the system prompt.
- The note is derived only from the messages at fixed positions, so each request extends the previous one byte for byte and the provider's cache prefix stays valid.

### Why an extension could not handle it

- The note must be part of every provider request and of compaction-summary rendering, which `convertToLlm` and the session projection own; a `context` hook would not reach the summarization and transport paths that call `convertToLlm` directly.

### Expected merge conflict zones

- LOW: the `convertToLlm` head in `messages.ts` and the compaction-summary case; the tail of `projectSession` in `session-manager.ts`.

## 2026-10-27 - Compaction summaries can carry the user's language (omo#11527)

### What changed

- `packages/agent/src/harness/messages.ts`: `CompactionSummaryMessage` gains an optional `userLanguage`, set by the coding agent's session projection.

### Why

- The `AgentMessage` union takes `compactionSummary` from this interface, so the coding agent's reply-language note needs the field here (omo#11527).

### Why an extension could not handle it

- A type in the shared message union.

### Expected merge conflict zones

- LOW: the `CompactionSummaryMessage` interface.
