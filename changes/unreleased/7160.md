## 2026-11-21 - The agent dir is created 0700 whatever the umask (senpi#6560)

### What changed

- `packages/coding-agent/src/cli.ts`: the launcher calls `ensureAgentDir(getAgentDir())` right after the `--version` answer, before the help fast path (whose trust lookup takes the trust-store lock inside the agent dir) and the runtime snapshot, both of which ran before `main()` and could be the first to create the agent dir.
- `packages/coding-agent/src/main.ts`: `main()` also calls `ensureAgentDir(getAgentDir())` (`src/utils/ensure-agent-dir.ts`) once, before the auth, models-discover, package, config, host and schedule commands and before migrations, so no later recursive `mkdir` under the agent dir creates it with the umask's mode. The internal supervisor route moved ahead of the auth and models-discover dispatch so that it still runs before the default agent dir is touched; it fires only on its private flag.
- The fork-only creation sites `migrations-state.ts`, `beta/omo-local-update.ts`, `modes/interactive/runtime-notice-presenter.ts` and `legacy-pi-edits.ts` use the same helper.

### Why

- The RPC host refuses a key root that group or others can write (`modes/rpc/rpc-public-key.ts`, #3795). Under umask 0002 the first `senpi` command left the agent dir 0775, and every later host failed with `unsafe_key_record ... writable by group or others`.
- An existing directory is never re-moded, so a loose agent dir senpi did not create is still refused with its `chmod go-w` hint.

### Why an extension could not handle it

- Extensions load after the agent dir has already been created by startup, migrations and settings.

### Expected merge conflict zones

- LOW: the lines between the `--version` answer and the help fast path in `cli.ts`.
- LOW: the first dispatches in `main()` (internal supervisor, auth, models discover) and the `getAgentDir()` line that follows them.

## 2026-11-21 - The trust store creates its directory 0700 whatever the umask (senpi#6560)

### What changed

- `packages/coding-agent/src/core/trust-manager.ts`: `writeTrustFile` and `acquireTrustLockSync` pass `mode: 0o700` to their recursive `mkdirSync` of the trust store's directory (the agent dir). They keep their own `mkdirSync` rather than calling `ensureAgentDir`: both are on the RPC session path, whose synchronous-fs baseline (`test/suite/no-sync-in-session-path.baseline.json`) is shrink-only, and the mode alone already yields 0700 under any umask that leaves the owner bits.

### Why

- The trust lookup can be the first write under a fresh agent dir (`senpi --help` in a project with skills reaches it before `main()`), and under umask 0002 it left the agent dir 0775, which the RPC host then refuses as its key root.

### Why an extension could not handle it

- The trust store is read before any extension loads.

### Expected merge conflict zones

- LOW: the two `mkdirSync` lines in `writeTrustFile` and `acquireTrustLockSync`.
