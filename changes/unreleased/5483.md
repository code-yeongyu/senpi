- Added `createRemoteToolHost()` and `createRemoteExecutor()` (`src/execution/remote-tool-host.ts`, `src/execution/remote-executor.ts`): a `ToolHost` that runs a session's tool calls on a hand over the durable-core `Transport`, one lane per execution scope, and the hand's side that runs them, each execution ID at most once and each scope bound to its root. Nothing selects the remote ToolHost yet ([#5483](https://github.com/code-yeongyu/senpi/pull/5483)).

## 2026-11-02 - Remote ToolHost and hand executor (senpi#5483)

### What changed

- `packages/agent/src/execution/remote-tool-host.ts` is new: `createRemoteToolHost({ transport, sessionRef? })` sends each raw call of a batch to a hand on the scope's lane, emits the tool events, waits per call in `sequential` mode, forwards an abort, and returns result messages in source order; a call is never re-sent.
- `packages/agent/src/execution/remote-executor.ts` is new: `createRemoteExecutor({ transport, openScope })` opens scopes lazily, refuses a known scope with another root and a repeated execution ID, never passes the session reference on, and keeps `sequential` tool barriers per scope.
- `packages/agent/src/execution/remote-protocol.ts` is new: the `invoke`, `abort`, `settled` and `refused` messages and a strict decoder.
- `packages/agent/src/index.ts` exports the three modules, the reference transport and the `Transport` types.

### Why

- Brain/hand split (senpi#5482): a session must be able to run its tool calls on a hand, first on one machine over the in-process carrier.

### Why an extension could not handle it

- The ToolHost seam and the transport live in the agent core; an extension cannot replace where the loop dispatches tool calls.

### Expected merge conflict zones

- LOW: `packages/agent/src/index.ts` export list, next to the internal-events exports.

## 2026-11-02 - One tool-info projection for sessions and loopless runtimes (senpi#5483)

### What changed

- `packages/coding-agent/src/core/tool-info.ts` is new: `toolInfoOf(entry)` is the `pi.getAllTools()` projection of one registered tool.
- `packages/coding-agent/src/core/agent-session.ts`: `getAllTools()` maps its tool definitions through `toolInfoOf`; the projection is unchanged.

### Why

- A loopless runtime (a hand) must answer `pi.getAllTools()` exactly as a session does; the permission system resolves extension tools' permission parsers with it.

### Why an extension could not handle it

- `getAllTools` is the host's own registry projection.

### Expected merge conflict zones

- LOW: `AgentSession.getAllTools()` body.

## 2026-11-02 - Runtime facts a runner without a session can answer (senpi#5483)

### What changed

- `packages/coding-agent/src/core/extensions/runner.ts`: `bindSessionlessFacts({ getAllTools, getLoadedHookSources? })` lets the host of a runner without a session bind the registered-tool list and the hook configuration sources; its contexts then answer `getLoadedHookSources()` instead of refusing it as loop-side. An unbound runner without a session still refuses both.

### Why

- A hand runs its extensions' `tool_call` handlers before every call (senpi#5482); the builtin handlers read both facts, and refusing them refused every call.

### Why an extension could not handle it

- The session-less context narrowing is the runner's.

### Expected merge conflict zones

- LOW: next to `bindCore()` and in `withoutSession()`.

## 2026-11-02 - Shell tool hooks refuse calls on a runtime without a session (senpi#5483)

### What changed

- `packages/coding-agent/src/core/extensions/builtin/hooks/index.ts`: on a runtime without a session, the `tool_call` handler refuses the call when any PreToolUse or PostToolUse hook is configured and passes it through when none is; the `tool_result` handler does nothing there. Sessions are unchanged.

### Why

- Tool hooks get the session's ID in their input, which a hand does not have; running the tool past configured hooks would skip them. Forwarding them to the session's process is the two-sided forwarding change.

### Why an extension could not handle it

- This is the builtin hooks extension itself.

### Expected merge conflict zones

- LOW: the top of the `tool_call` and `tool_result` handlers.

## 2026-11-02 - A hand's scopes on loopless runtimes, with tool handlers on every call (senpi#5483)

### What changed

- `packages/coding-agent/src/modes/rpc/loopless-execute-grant.ts`: a second closed-allowlist caller, `remote-tool-executor` (`grantLooplessExecuteToRemoteExecutor()`); `looplessGrantRunsToolHandlers()` tells whether calls made with a grant run the tool handlers. The check in `execute()` is unchanged.
- `packages/coding-agent/src/modes/rpc/loopless-tool-call.ts`: with handlers, a call runs the `tool_call` handlers after argument validation (a block, an abort or a throw stops it before the tool runs), the tool, then the `tool_result` handlers, applying their override as a session does.
- `packages/coding-agent/src/modes/rpc/loopless-tool-handlers.ts` is new: the runtime's own extension runner's `tool_call`/`tool_result` emission.
- `packages/coding-agent/src/modes/rpc/runtime-factory-loopless.ts`: runs those handlers for the remote executor's grant, and binds `getAllTools` and the loader's hook sources on its runner.
- `packages/coding-agent/src/modes/rpc/remote-executor-scope.ts` is new: `createLooplessHandScopes(configuration)` opens one loopless runtime per scope with the remote executor's grant, cwd = the scope's absolute root.

### Why

- Closes the remote executor's side of the obligation recorded on senpi#5413: no untrusted call reaches a loopless runtime's tools past its permission checks.

### Why an extension could not handle it

- The loopless runtime and its execute guard are the RPC host's.

### Expected merge conflict zones

- LOW: new files; the `execute` closure in `runtime-factory-loopless.ts`.
