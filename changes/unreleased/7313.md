## 2026-11-22 - Expose transport activity to Agent callers (#5018)

### What changed
- `packages/agent/src/agent.ts` adds `Agent.onTransportActivity(listener)` and forwards the loop's `onTransportActivity` (SSE pings, keep-alive comments of the active request) to its subscribers.

### Why
- `packages/agent/src/agent.ts` kept transport bytes inside the loop, so the session retry watchdog could not tell a provider that was alive but not yet streaming from a wedged one.

### Why an extension could not handle it
- Transport bytes are reported only through the loop config `packages/agent/src/agent.ts` builds; no event or extension hook carries them.

### Expected merge conflict zones
- `packages/agent/src/agent.ts`: the public fields block, the method next to `subscribe`, and the loop config object (`streamKeepAliveTimeoutMs` neighbourhood).

## 2026-11-22 - Keep-alives restart the retry watchdog (#5018)

### What changed
- `packages/coding-agent/src/core/provider-timeout-retry.ts`: before a retried request streams, each transport byte restarts the watchdog bound, capped by `keepAliveTimeoutMs`. `packages/coding-agent/src/core/agent-session.ts` passes `Agent.onTransportActivity` and `streamKeepAliveTimeoutMs` to it.

### Why
- `packages/coding-agent/src/core/provider-timeout-retry.ts` cleared only on the first assistant event, so `packages/coding-agent/src/core/agent-session.ts` aborted a retried request at the watchdog bound while keep-alives proved the provider alive.

### Why an extension could not handle it
- The retry continuation and its watchdog run inside `packages/coding-agent/src/core/agent-session.ts` and `packages/coding-agent/src/core/provider-timeout-retry.ts`; extensions do not own provider retries.

### Expected merge conflict zones
- `packages/coding-agent/src/core/provider-timeout-retry.ts`: `BoundedRetryContinuation` and `runBoundedRetryContinuation`; `packages/coding-agent/src/core/agent-session.ts`: the `runBoundedRetryContinuation` call.
