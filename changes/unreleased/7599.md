## 2026-11-28 - Generated default extension shims are presence markers (#7597)

### What changed

- `packages/coding-agent/src/core/resource-loader.ts` keeps an existing generated shim while it targets a regular builtin module of the same name, and resolves default-extension factories through `extensions/generated-default-shim.ts`: every generated shim that names a default's builtin loads this process's in-process factory, in whatever agent dir the loader is given and whichever installation the URL points to. A shim whose target is gone still takes the dead-target repair; a user-authored file of the same name is still loaded as the user's file.
- `packages/coding-agent/src/core/generated-shim-banner.ts` recognizes the complete first-line sentence across brands and parses the single generated re-export.

### Why

- Distinct installations generate distinct absolute URLs for the same builtin. Replacing a live target on startup changed the shared file every time the other installation seeded it, and importing a kept foreign shim would run the other installation's builtin and its module graph.

### Why an extension could not handle it

- Resource seeding writes the shared file, and the loader resolves its factory, before extensions load.

### Expected merge conflict zones

- `DefaultResourceLoader.ensureGlobalDefaultExtensions`, `buildGlobalDefaultExtensionLoadOptions`, dead-target repair and generated shim recognition.

## 2026-11-28 - The public extension loader resolves generated default shims (#7597)

### What changed

- `packages/coding-agent/src/core/extensions/generated-default-shim.ts` (new) resolves a generated default-extension shim in any agent dir to this process's in-process builtin factory, skips one whose target is gone, and leaves every other file to the regular import.
- `packages/coding-agent/src/core/extensions/loader.ts` `discoverAndLoadExtensions` loads with that resolver, as `DefaultResourceLoader` does.

### Why

- Without it, the public loader imported a generated shim's URL, which can be another installation's builtin and its whole module graph.

### Why an extension could not handle it

- The loader picks the module for a discovered extension path before any extension runs.

### Expected merge conflict zones

- The `loadExtensions` call at the end of `discoverAndLoadExtensions` and the loader's import block.

## 2026-11-28 - Serialize watcher-triggered session reloads (#7597)

### What changed

- `packages/coding-agent/src/core/extensions/builtin/config-reload/reload-queue.ts` (new) holds one reload queue shared across engine copies serving the same event loop. A session's slot is released when its reload settles or after `RELOAD_SLOT_TIMEOUT_MS` (60 s), whichever comes first; a reload past the bound keeps running on its own and is logged once as `reload_slot_released` (`log.ts`).
- `packages/coding-agent/src/core/extensions/builtin/config-reload/index.ts` sends every session with a pending change through that queue, admitted by the same rules as before (idle, nothing pending, not compacting, no veto). A queued session rechecks admission when its turn comes, and a follow-up requested from a reload's own `session_start` is queued without waiting on that reload.
- `packages/coding-agent/src/core/extensions/builtin/config-reload/generated-shim-filter.ts` filters generated re-exports using the same parser as resource seeding.

### Why

- One watched change could start a reload in every session at once. Cross-brand generated shims reached that path as user edits.

### Why an extension could not handle it

- This builtin owns the watcher's pending changes, admission decision and reload handoff.

### Expected merge conflict zones

- `flushPending`, `reload-queue.ts` and generated-shim filtering.
