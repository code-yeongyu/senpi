### Added
- Attach the interactive TUI to an existing RPC endpoint with `--attach <address> --session <ref>`, using authenticated local sockets or Windows named pipes. Read paged history, stream responses, send input and answer dialogs without creating a local session. It attaches only to a session the endpoint retains on disconnect (`list_sessions` rows now report `retain_on_disconnect`) and refuses any other with `session_not_retained`, so exiting or a dropped connection never ends the session. A refused or unacknowledged dialog answer brings the dialog back, a crash restores the terminal, and disconnect keeps the transcript visible ([#4271](https://github.com/code-yeongyu/senpi/pull/4271)).

## 2026-10-25 - A record-driven RPC attachment presentation (senpi#4269)

### What changed

- `attach.ts`, `attach-client.ts`, `attach-dialogs.ts`, and `run-attached-tui.ts`: authenticate, attach, subscribe, read state and backward history, render dialogs, forward identified inputs, and release only the caller's attachment. They refuse a session that is not retained on disconnect, track each dialog answer to its reply and show the dialog again when it is refused, end the connection on a record they cannot read, restore the terminal on an uncaught throw or rejection, and leave at once on a signal during connect. The terminal is restored before the attachment is released, and a second signal while that release waits exits at once, non-zero.
- `session-control-commands.ts`: a terminal's control-endpoint row reports `retain_on_disconnect: true`, since a release there never ends the terminal's session.
- `record-renderer.ts`: projects persisted entries and incremental or cumulative stream records into existing message components.

### Why

- An explicit attachment should present an existing session without owning a runtime, changing its profile, or falling back to a new local session.

### Why an extension could not handle it

- A presentation without a local session must be composed before session extensions exist.

### Expected merge conflict zones

- LOW: new presentation modules; the existing interactive runtime is unchanged.
- LOW: `session-control-commands.ts`: one field in `sessionRow`.

## 2026-10-26 - Published retention and refused grant answers (senpi#4269)

### What changed

- `packages/coding-agent/src/modes/rpc/session-registry.ts`, `packages/coding-agent/src/modes/rpc/worker-session-registry.ts`, `packages/coding-agent/src/modes/rpc/session-registry-types.ts`, `packages/coding-agent/src/modes/rpc/rpc-host-response-types.ts`: every `list_sessions` row reports `retain_on_disconnect`.
- `packages/coding-agent/src/modes/rpc/connection-handler.ts`, `packages/coding-agent/src/modes/rpc/extension-ui-response.ts`: a grant answer from a connection that was not asked, or lacks `grant_select`, gets a `grant_answer_refused` reply instead of no reply.
- `packages/coding-agent/src/modes/rpc/connection-handler.ts`, `packages/coding-agent/src/modes/rpc/session-worker-client.ts`: the grant-answer rules (the asked connection, with `grant_select`) apply to the request the response answers, its `uiRequestId` or, in the short form, its `id`, on in-process and worker sessions alike.

### Why

- A client attaching to an existing session must know whether its own release could end it, and a refused answer must not look accepted to the person who gave it.

### Why an extension could not handle it

- Listing rows and extension UI response replies are host wire behavior.

### Expected merge conflict zones

- LOW: the row builders in both registries; the grant-answer guards in the connection handler and the session worker client.
