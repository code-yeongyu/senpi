## 2026-11-13 - A custom loader's lost scan-folder refusal is documented on `getUserSkillScanDirs` (senpi#6558 delta-2 review LOWs)

### What changed

- `packages/coding-agent/src/core/resource-loader.ts`: the JSDoc of the OPTIONAL `ResourceLoader.getUserSkillScanDirs?()` states what a custom loader without it keeps (the refusal of the agent dir, `~/.agents/skills`, its `getUserSkillRoots` and every user-provenance skill from `getSkills()`) and what it loses (the refusal of a new top-level `*.md` file in a folder it walks for user skills), and why `getSkills()` cannot stand in for it. No runtime change in this file.

### Why

- The senpi#6558 delta-2 security review (APPROVE-WITH-NITS, 2 LOWs): a custom or delegating `ResourceLoader` that omits the optional method silently lost the scan-folder refusal, and neither the interface nor the SDK changelog bullet said so. Deriving the folders from the required `getSkills()` was rejected: a walked folder holding no skill yet, the exact folder a planted top-level file would turn into a skill, lists nothing there, so the derivation would miss the case the refusal exists for. Making the member required would break custom loaders, which senpi#6558 made it optional to avoid.

### Why an extension could not handle it

- The member is part of the core `ResourceLoader` SDK interface, which an extension cannot document or change.

### Expected merge conflict zones

- LOW: the `getUserSkillScanDirs` JSDoc on the `ResourceLoader` interface in `resource-loader.ts`.
