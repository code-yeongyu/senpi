## 2026-10-25 - Assistant streams capture block seeds at emission and keep one ordered progress lane (senpi#4277, part of #4272)

### What changed

- `packages/ai/src/utils/event-stream.ts`: `EventStream` keeps one ordered queue whose entries are public events or
  internal progress records. Ordinary iteration yields only public events with the same microtask timing as before:
  a queued progress record is skipped in the same `next()` call, and a waiting reader that receives one keeps
  waiting. `AssistantMessageEventStream` takes `{ captureBlocks }`; with it, `push(event, hint?)` freezes the event's
  capture carrier before queuing. Every instance registers a progress writer; a records reader is registered only
  when the class does not replace `[Symbol.asyncIterator]`. Ordinary iteration drops each event's carrier as it is
  dequeued, so a wrapper that reads that way can only lose controls, never forward wrong ones. `done` is now
  `protected`; `mapIterator` and `enqueueProgress` are new protected members.
- `packages/ai/src/utils/assistant-capture.ts` (fork-only, new): the carrier and record vocabulary. Carriers live in
  a `WeakMap` keyed by the event object (never enumerable, never serialized) and hold frozen copies: usage, changed
  message metadata, the public block at start/end (provider scratch and symbols removed), the exact raw argument
  prefix the adapter emitted, UTF-16 coverage and delta offsets, and the parse frontier `parsedThrough`.
  Progress records are `message_block_state` (native insert/end), `message_block_metadata` (changed fields only) and
  `message_tool_arguments_reset` (authoritative raw replacement). `assistantRecords` reads records;
  `assistantEvents` reads events and hands each record to a callback as it is read.

### Why

- Provider events carry the shared live partial and the queue held references, so a seed read when a consumer
  resumed could already contain later bytes, and native insertions/ends happened with no event at all. The facts
  have to be frozen when the producer emits them, and native-only transitions need their own ordered lane
  (R3.C6.2; contract ruling 05, decisions D1-D5).

### Why an extension could not handle it

- Capture has to run inside the producer's `push`, before the event is queued; extensions only see events after
  the consumer resumes, when the live partial may already be ahead.

### Expected merge conflict zones

- MEDIUM: `EventStream` queue and iterator internals (`#queue` entry type, `push`/`deliver`, `mapIterator`,
  `FifoQueue.prepend`) and the `AssistantMessageEventStream` constructor, `push` and iterator overrides.

## 2026-10-25 - Anthropic, Responses and Completions capture seeds and native transitions at emission (senpi#4277, part of #4272)

### What changed

- `packages/ai/src/api/anthropic-messages.ts`: the stream is created with capture. Unknown (native) blocks record a
  `message_block_state` insert at `content_block_start` and an end at `content_block_stop` after `raw.input` is
  parsed; each `signature_delta` records only its delta as `thinkingSignatureDelta`.
- `packages/ai/src/api/openai-responses-shared.ts`: `processResponsesStream` enables capture on its stream; a
  `function_call` start carries its possibly nonempty raw prefix (`item.arguments`) while its parsed seed stays
  `{}`; native items record insert and replacement end in original index order, including image reconciliation
  and terminal backfill; an `arguments.done` that does not extend the streamed prefix records an authoritative
  `message_tool_arguments_reset`.
- `packages/ai/src/api/openai-responses.ts`, `packages/ai/src/api/openai-codex-responses.ts`,
  `packages/ai/src/api/azure-openai-responses.ts`: the stream is created with capture, so `start` is captured too.
- `packages/ai/src/api/openai-completions.ts`: the stream is created with capture. Deferred mixed-event flushes
  emit starts whose coverage matches what they already hold: replayed deltas start at offset 0, and a tool start's
  raw prefix is the deferred normalized deltas (function or grammar spelling) with its parse frontier at their end.
  Per-chunk `reasoning_details` signature growth is not recorded (each chunk re-serializes the whole list); the
  `thinking_end` block and the terminal message carry the final signature.
- `packages/ai/src/api/lazy.ts`: the lazy wrapper is carrier-aware. Its forwarder reads the inner stream with
  `assistantEvents`, so events keep their carriers and progress records cross to the outer stream as they are read
  without an extra forwarder turn; the outer stream registers a records reader that keeps its cancellation.

### Why

- These adapters mutate public blocks without an event (native insert/end, signature growth, raw replacement) and
  hold raw argument spelling in adapter state; only the adapter knows them at emission time (R3.C6.2, ruling 05
  D1-D3). Builtin providers load through `lazyApi`, so the lazy wrapper must carry what the adapter captured.

### Why an extension could not handle it

- The mutations happen inside adapter closures before any event exists; no hook exposes the emitted raw spelling,
  coverage or native transitions.

### Expected merge conflict zones

- LOW: each adapter's stream construction line.
- LOW: `anthropic-messages.ts` `content_block_start` native branch, `signature_delta` branch and the
  `content_block_stop` `providerNative` branch.
- MEDIUM: `openai-responses-shared.ts` `createSlot` (function call and native slots), the image backfill loop,
  the `arguments.done` branch and the native `output_item.done` branches.
- LOW: `openai-completions.ts` `flushDeferredBlocks`.
- LOW: `lazy.ts` `setCancellationHandler` and the source iterator in `lazyStream`.

## 2026-10-25 - Internal-only ordered agent channel for capture records (senpi#4277, part of #4272)

### What changed

- `packages/agent/src/agent-loop.ts`: when the run has an internal sink, `streamAssistantResponse` reads the
  provider stream as ordered records, hands progress records to the sink in order, and carries the provider
  carrier onto `message_start`, `message_update` and `message_end` (the terminal carrier holds the final
  normalized message). Agent-stamped thinking timing goes to the sink as `message_block_metadata` after the event
  it amends. Progress records do not re-arm the idle or start bound. Without a sink the loop reads the public stream
  exactly as before.
- `packages/agent/src/agent.ts`: a run's loop config gets the sink only when an internal listener exists at run
  start; `processEvents` dispatches each event to the internal channel before public listeners, with no microtask
  when there is no internal listener.
- `packages/agent/src/internal-events.ts` (fork-only, new): `subscribeInternalAgent` registers an internal-only
  listener (not exported from the package barrel, no production subscriber in this increment); records are frozen
  `{ event | progress, sequence }` with one increasing sequence per agent.

### Why

- Contract-owner lane decision (option 3): S02a ends at an ordered internal agent channel that public
  `Agent.subscribe` listeners, extensions and emitted events never see; the AgentSession bridge is S02b.

### Why an extension could not handle it

- `Agent.subscribe` is the public listener path and reaches extensions; an internal-only channel cannot be built on
  top of it.

### Expected merge conflict zones

- MEDIUM: `agent-loop.ts` `streamAssistantResponse` (iterator creation, the record branch, the thinking case and
  the terminal emits) and `createAssistantEventReader`.
- LOW: `agent.ts` `createLoopConfig` return object and the `processEvents` listener loop.
