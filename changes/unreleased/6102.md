## 2026-11-06 - A trailing CR submits the paste burst instead of joining it (senpi#3076)

### What changed

- `packages/tui/src/stdin-buffer.ts`: `consumeUnbracketedBurst` reads raw-mode framing as the key/paste split it is: an Enter key arrives as a bare CR, while a paste carries LF or CRLF. A burst read that ends with a bare CR now emits its paste without that CR and then the CR as a key event, so the submit is processed after the paste is committed. The CR is held for `burstWindowMs` only so the LF half of a CRLF pair split across reads still joins its paste, and a held Enter is released before any read that is not that LF, so a following write is never swallowed. A read whose trailing CR follows an already-committed burst paste inside the window is forwarded as Enter instead of being released as paste content. The held trailing break is now a `HeldLineBreakKind` (`enter` | `paste` | `keystroke`) instead of the former `endsPaste` boolean. LF and CRLF behaviour and the bracketed-paste path are unchanged.

### Why

- Automation that types into the TUI writes its text and then Enter as two reads (`herdr pane send-text`, then `send-keys Enter`). When that CR landed inside the 20 ms burst window the paste detector emitted it as `paste("\r")`, the editor inserted a pasted newline, and the request stayed in the editor behind a `[paste #N]` marker with nothing submitted (senpi#3076).

### Why an extension could not handle it

- Stdin framing decides what reaches the editor as a key before any extension sees an input event; a swallowed Enter never becomes an input event an extension could reinterpret.

### Expected merge conflict zones

- `packages/tui/src/stdin-buffer.ts`: `consumeUnbracketedBurst`, the held-line-break block in `process()`, `holdTrailingNewline`/`releaseHeldNewline`, and the `heldNewline*` field declarations.
- `packages/tui/test/stdin-buffer.test.ts`: the `StdinBuffer unbracketed paste bursts` block.
- `packages/tui/test/paste-submit-contract.test.ts`: the whole file.

### Fixed
- An Enter written right after the text it submits is no longer swallowed as part of that paste: a bare CR that ends a burst read, or follows a burst paste inside the burst window, submits the request, while LF and CRLF line endings stay in the paste ([#3076](https://github.com/code-yeongyu/senpi/issues/3076), [#6102](https://github.com/code-yeongyu/senpi/pull/6102)).
