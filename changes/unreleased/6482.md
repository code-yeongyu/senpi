## 2026-11-12 - Lock and store validation runs in the checked-open section without opening an existing file; in-process lock holders queue (senpi#6482)

### What changed

- `packages/coding-agent/src/modes/rpc/sqlite-file-identity.ts`: `openExpectedFile(path, validate, open, close)` now takes the caller's `validate()`, which returns the identity it found, in place of that identity. It runs inside the same one-at-a-time section as SQLite's open, so no validation of a checked file can land in another checked open's descriptor listing window. `validate` must neither open an existing file nor block. When the listing before the open succeeded and the listing after it fails, the open answers `busy` and never falls back to the name check alone. The comment on the accepted case now says what remains: call discipline, meaning code that opens a checked file outside `openExpectedFile`.
- `packages/coding-agent/src/modes/rpc/ownership-safe-lock.ts`:
  - The option `expectedFile` is replaced by `validateFile: () => Promise<FileIdentity>`, which runs before each open attempt, inside the checked open.
  - Callers that pass `validateFile` wait in an in-process queue per lock path, in arrival order, before any validation or SQLite open. They hold their place until they release the lock. The wait counts against the lock's deadline and gives up with a busy refusal.
  - A legacy lock directory is refused before that wait.
  - `isBusy` classifies by code only: SQLite's primary SQLITE_BUSY or SQLITE_LOCKED (node:sqlite `errcode`, bun:sqlite `SQLITE_BUSY*`/`SQLITE_LOCKED*`) and this module's busy refusals. It no longer matches "busy" or "locked" in a message that may name the path.
  - `sqlite-file-identity.ts` still loads lazily, only when `validateFile` is passed.
- `packages/coding-agent/src/modes/rpc/socket-transport.ts`: the publish lock's path (`socketSecretLockPath`) and its validation (`validateSocketSecretLock`) are now separate. The validation is passed to the lock as `validateFile`. It never opens an existing lock file: an absent one is created owner-only (`O_EXCL | O_NOFOLLOW | O_NONBLOCK`), and an existing one must be a regular file by `lstat`.
- `packages/coding-agent/src/modes/rpc/endpoint-reservation-file.ts`: `precreatePrivate` runs as the store's `validate`, inside the checked open, and validates an existing store file by `lstat` instead of opening it. It creates an absent one the same way. The `store_busy` comment now says exactly when the open is busy.

### Why

- Review of senpi#6440 at f47f5c7b93 (LOW 1-3). The validation opens of the secret lock and of the store ran outside the serialization. A concurrent `ensureSocketSecret` whose validation handle stayed open across another repair's listings counted as that repair's added `expected` descriptor. With a name swapped for a file this process holds SQLite locks on, and swapped back afterwards, that repair accepted the impostor (reproduced, now a regression test). A failed second listing silently skipped the descriptor proof.
- senpi#6478, review of senpi#6482 at 12db821aba (MEDIUM): closing any descriptor of a file drops all of this process's POSIX locks on it. An in-process contender's validation open and close of the lock file dropped the SQLite lock of a repair holding it across awaits, so another process took the lock inside that critical section, and the holder's `COMMIT` failed. Re-running validation on every attempt repeated this for the whole critical section. The store's precreate open and close had the same pattern. A validation that opens no existing file is safe for every spelling of the file's inode, not only for its path. The in-process queue also keeps contenders of one lock off the file while the lock is held, and serves them in order.
- Review of senpi#6482 (LOW): a FIFO at the lock path blocked the validation open, and with it every checked open of the process. A non-regular lock file under a path containing "busy" or "locked" was retried until the deadline instead of being refused at once.

### Why an extension could not handle it

- The publish lock and the reservation store are RPC host internals that run before extension loading.

### Expected merge conflict zones

- LOW: the `acquireOwnershipSafeLock` options, the function itself (now split into the in-process wait and `attemptUntil`), `openLockDatabase`, `openChecked` and `isBusy`.
- LOW: `ensureSocketSecret`'s lock acquisition and the publish-lock helpers in `socket-transport.ts`.

### Fixed
- The RPC socket-secret repair lock and the endpoint reservation store validate their file inside the same serialized section as SQLite's open, without opening an existing file. A concurrent validation can no longer hide a swapped file or drop this process's lock (#6478), and a FIFO at the lock path no longer stalls other opens. In-process holders of the repair lock queue in arrival order within the lock's deadline. A failed descriptor listing after the open is retried instead of trusting the file name, and lock contention is recognized by error code, not by words in the path ([#6482](https://github.com/code-yeongyu/senpi/pull/6482))
