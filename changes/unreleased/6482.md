## 2026-11-12 - The validation open of a checked file runs inside the checked-open section; a failed second listing is busy (senpi#6482)

### What changed

- `packages/coding-agent/src/modes/rpc/sqlite-file-identity.ts`: `openExpectedFile(path, validate, open, close)` now takes the caller's `validate()`, a no-follow open of `path` (open, fstat, close) that returns the identity it found, in place of that identity. It runs inside the same one-at-a-time section as SQLite's open, so no validation open of a checked file can land in another checked open's descriptor listing window. When the listing before the open succeeded and the listing after it fails, the open answers `busy` and never falls back to the name check alone. The comment on the accepted case now says what remains: call discipline, meaning code that opens a checked file outside `openExpectedFile`.
- `packages/coding-agent/src/modes/rpc/ownership-safe-lock.ts`: the option `expectedFile` is replaced by `validateFile: () => Promise<FileIdentity>`. It runs before each open attempt, inside the checked open. `sqlite-file-identity.ts` still loads lazily, only when `validateFile` is passed.
- `packages/coding-agent/src/modes/rpc/socket-transport.ts`: the publish lock's path (`socketSecretLockPath`) and its validation (`validateSocketSecretLock`) are now separate. The validation is passed to the lock as `validateFile`.
- `packages/coding-agent/src/modes/rpc/endpoint-reservation-file.ts`: `precreatePrivate` runs as the store's `validate`, inside the checked open. The `store_busy` comment now says exactly when the open is busy.

### Why

- Review of senpi#6440 at f47f5c7b93 (LOW 1-3). The validation opens of the secret lock and of the store ran outside the serialization. A concurrent `ensureSocketSecret` whose validation handle stayed open across another repair's listings counted as that repair's added `expected` descriptor. With a name swapped for a file this process holds SQLite locks on, and swapped back afterwards, that repair accepted the impostor (reproduced, now a regression test). A failed second listing silently skipped the descriptor proof.

### Why an extension could not handle it

- The publish lock and the reservation store are RPC host internals that run before extension loading.

### Expected merge conflict zones

- LOW: the `acquireOwnershipSafeLock` options, `openLockDatabase` and `openChecked`.
- LOW: `ensureSocketSecret`'s lock acquisition and the publish-lock helpers in `socket-transport.ts`.
