## 2026-11-12 - The compiled binaries and the bundle scan for stale zod 4 and zod 3 copies (senpi#6497 follow-up)

### What changed

- `scripts/bundle-zod-core-guard.mjs`: the scan also recognises an unpatched zod 3.x classic copy by its emoji pattern string (`^(\p{Extended_Pictographic}|\p{Emoji_Component})+$`, which zod 4.6.x's own `zod/v3` layer rewrote) and reports it as stale "3.x"; the earlier `ZodEffects` marker is not used because every zod 4 package's `zod/v3` layer carries it and the real bundle imports that layer. The only stale zod allowed is what the vendored `@anthropic-ai/claude-agent-sdk` embeds in its own published files, and `STALE_ZOD_ALLOWANCE` pins it to the exact SDK version (the installed package and every `bun.lock` / `package-lock.json` entry must equal it) and to the sha256 of every SDK source file that carries a stale copy (`sdk.mjs`, `bridge.mjs`, `browser-sdk.js`, hashed as published, with the stale copies each carries); an SDK file carrying a stale copy that is not pinned fails. In the bundle and the compiled binaries only placement, count and version are checked: stale copies only in `chunks/sdk-*.js` and `chunks/session-worker.js` (in a binary, the binary itself), exactly one 4.6.2 core and one `zod/v3` layer in each (the copies of `sdk.mjs`, the entry the CLI imports), and none at all fails. Output bytes are not hashed because the bundler renames identifiers by graph and `bun build --compile` folds `process.platform` per target. A pass prints the SDK version, the source hashes and every allowed copy.
- `scripts/assert-binary-zod-cores.mjs` (new) runs that scan from `scripts/build-binaries.sh` right after each platform's `bun build --compile`, before the release archives are made, and prints the allowed copies; `scripts/build-coding-agent-bundle.mjs` prints them for the bundle.
- `scripts/bundle-zod-core-guard.test.mjs`, `scripts/bundle-zod-binary-guard.test.mjs`, `scripts/zod-real-output.test-support.mjs` (new): fixtures are real bundler output (zod 3.25.76 is caught; zod 4.6.7's `zod/v3` and `zod/v4` are not); an SDK version bump, a changed byte in a pinned SDK source, an unpinned SDK file with a stale copy, an extra stale copy in another chunk or binary, and a missing copy fail, while an unrelated export appended to the session worker and per-target folded binary bytes pass; the real installed SDK is checked against the pinned version and hashes; the binary scan's exit codes and its place in the build script. `scripts/build-coding-agent-bundle.test.mjs` checks the real built bundle's report.

### Why

- The compiled binaries were protected only by the lockfile pin; nothing scanned their output. The guard also could not see a stale zod 3.x copy reached through `zod/v3` (it was covered only because such a layout also bundles a 4.0.0 core).

### Why an extension could not handle it

- The release build scripts are core.

### Expected merge conflict zones

- LOW: the compile loop in `scripts/build-binaries.sh`.

## 2026-11-12 - Standalone binary builds scan their compiled output for stale zod (senpi#6497 follow-up)

### What changed

- `scripts/build-binaries.sh`: after each platform's `bun build --compile`, `scripts/assert-binary-zod-cores.mjs` scans the compiled executable and fails the build on a zod core older than 4.6.6 or a zod 3.x copy, except the copies the Claude agent SDK embeds, which are allowed only for the exact pinned SDK version, only while the SDK's own source files carry their pinned content hashes, and only once per allowed file or binary.

### Why

- The binaries were protected only by the lockfile pin; a stale zod now fails the release build instead of shipping.

### Why an extension could not handle it

- The release build script is core.

### Expected merge conflict zones

- LOW: the compile loop in `scripts/build-binaries.sh`.
