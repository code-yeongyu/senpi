## 2026-11-12 - The compiled binaries and the bundle scan for stale zod 4 and zod 3 copies (senpi#6497 follow-up)

### What changed

- `scripts/bundle-zod-core-guard.mjs`: the scan also recognises an unpatched zod 3.x classic copy by its emoji pattern string (`^(\p{Extended_Pictographic}|\p{Emoji_Component})+$`, which zod 4.6.x's own `zod/v3` layer rewrote) and reports it as stale "3.x"; the earlier `ZodEffects` marker is not used because every zod 4 package's `zod/v3` layer carries it and the real bundle imports that layer. The Claude agent SDK's embedded unpatched layer is pinned per file like its 4.6.2 core. New `assertBinaryZodCores(binaries)` scans compiled executables, allowing only one pinned 4.6.2 core and one pinned 3.x layer (as a real compile embeds them), failing on any other stale core or zod 3.x copy, and failing closed on a binary with no current (4.6.6 or newer) core.
- `scripts/assert-binary-zod-cores.mjs` (new) runs that scan from `scripts/build-binaries.sh` right after each platform's `bun build --compile`, before the release archives are made.
- `scripts/bundle-zod-core-guard.test.mjs`, `scripts/bundle-zod-binary-guard.test.mjs`, `scripts/zod-real-output.test-support.mjs` (new): fixtures are real bundler output (zod 3.25.76 is caught; zod 4.6.7's `zod/v3` and `zod/v4` are not); the binary scan against clean, 4.6.2-only, extra-copy, 4.0.0, zod 3 and no-zod binaries, the script's exit codes, and its place in the build script.

### Why

- The compiled binaries were protected only by the lockfile pin; nothing scanned their output. The guard also could not see a stale zod 3.x copy reached through `zod/v3` (it was covered only because such a layout also bundles a 4.0.0 core).

### Why an extension could not handle it

- The release build scripts are core.

### Expected merge conflict zones

- LOW: the compile loop in `scripts/build-binaries.sh`.

## 2026-11-12 - Standalone binary builds scan their compiled output for stale zod (senpi#6497 follow-up)

### What changed

- `scripts/build-binaries.sh`: after each platform's `bun build --compile`, `scripts/assert-binary-zod-cores.mjs` scans the compiled executable and fails the build on a zod core older than 4.6.6 (other than the Claude agent SDK's pinned 4.6.2) or on any zod 3.x copy.

### Why

- The binaries were protected only by the lockfile pin; a stale zod now fails the release build instead of shipping.

### Why an extension could not handle it

- The release build script is core.

### Expected merge conflict zones

- LOW: the compile loop in `scripts/build-binaries.sh`.
