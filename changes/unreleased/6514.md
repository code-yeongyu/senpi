## 2026-11-12 - The compiled binaries and the bundle scan for stale zod 4 and zod 3 copies (senpi#6497 follow-up)

### What changed

- `scripts/bundle-zod-core-guard.mjs`: the scan also recognises an unpatched zod 3.x classic copy by its emoji pattern string (`^(\p{Extended_Pictographic}|\p{Emoji_Component})+$`, which zod 4.6.x's own `zod/v3` layer rewrote) and reports it as stale "3.x"; the earlier `ZodEffects` marker is not used because every zod 4 package's `zod/v3` layer carries it and the real bundle imports that layer. The only stale zod allowed is what the vendored `@anthropic-ai/claude-agent-sdk` embeds (a 4.6.2 core and an unpatched `zod/v3` layer), and `STALE_ZOD_ALLOWANCE` pins it to the exact SDK version (the installed package and every `bun.lock` / `package-lock.json` entry must equal it) and to the sha256 of each allowed copy's bytes (core = banner up to the `zod/v3` pattern, layer = 32 KiB from that pattern), per bundle file and per compiled binary. A different SDK version, a changed byte in an allowed copy, a copy in another file, or a different count fails with a message naming the SDK; a pass prints each allowed copy (SDK version, file, hash). New `assertBinaryZodCores(binaries)` scans compiled executables the same way, failing on any other stale core or zod 3.x copy and failing closed on a binary with no current (4.6.6 or newer) core.
- `scripts/assert-binary-zod-cores.mjs` (new) runs that scan from `scripts/build-binaries.sh` right after each platform's `bun build --compile`, before the release archives are made, and prints the allowed copies; `scripts/build-coding-agent-bundle.mjs` prints them for the bundle.
- `scripts/bundle-zod-core-guard.test.mjs`, `scripts/bundle-zod-binary-guard.test.mjs`, `scripts/zod-real-output.test-support.mjs` (new): fixtures are real bundler output (zod 3.25.76 is caught; zod 4.6.7's `zod/v3` and `zod/v4` are not); the binary scan against clean, 4.6.2-only, extra-copy, 4.0.0, zod 3 and no-zod binaries, the script's exit codes, and its place in the build script.

### Why

- The compiled binaries were protected only by the lockfile pin; nothing scanned their output. The guard also could not see a stale zod 3.x copy reached through `zod/v3` (it was covered only because such a layout also bundles a 4.0.0 core).

### Why an extension could not handle it

- The release build scripts are core.

### Expected merge conflict zones

- LOW: the compile loop in `scripts/build-binaries.sh`.

## 2026-11-12 - Standalone binary builds scan their compiled output for stale zod (senpi#6497 follow-up)

### What changed

- `scripts/build-binaries.sh`: after each platform's `bun build --compile`, `scripts/assert-binary-zod-cores.mjs` scans the compiled executable and fails the build on a zod core older than 4.6.6 or a zod 3.x copy, except the copies the Claude agent SDK embeds, which are allowed only for the exact pinned SDK version and only with their pinned content hashes.

### Why

- The binaries were protected only by the lockfile pin; a stale zod now fails the release build instead of shipping.

### Why an extension could not handle it

- The release build script is core.

### Expected merge conflict zones

- LOW: the compile loop in `scripts/build-binaries.sh`.
