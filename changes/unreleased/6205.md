## 2026-11-08 - A synchronously throwing dispose no longer leaks the close grace timer (senpi#5929)

### What changed

- `packages/coding-agent/src/modes/rpc/session-router-close.ts`: `disposeWithinGrace` wraps `binding.dispose()` in an async wrapper (same shape as `abortForHostShutdownWithin`), so a synchronous throw becomes a rejection and the race's `finally` still clears the grace timer; the error still reaches `finalizeClose`'s catch and is logged.
- `packages/coding-agent/test/suite/regressions/issue-5929-close-grace-timer.test.ts`: new. Drives `finalizeClose` under fake timers with a synchronously throwing dispose and asserts no timer stays armed.
- Registry fakes in `test/suite/rpc-multi-session-close.test.ts`, `test/rpc-multi-session.test.ts`, `test/rpc-open-bypath-record-clear.test.ts`, `test/rpc-tool-media-session-scope.test.ts` now carry `closeGraceMs: 2_000`, so those tests exercise the normal grace path instead of the ~0 ms late path.

### Why

- A dispose that throws synchronously (for example from `toolSpans.closeAll()` in `session-binding.ts`) left the grace timer armed for up to `closeGraceMs` while the error was already handled, and registry fakes without `closeGraceMs` armed `setTimeout(..., undefined)`, so their tests only passed because dispose settled before the first macrotask.

### Why an extension could not handle it

- The close path's grace window and the registry's `closeGraceMs` live in the RPC host core, before any extension loads.

### Expected merge conflict zones

- LOW: the `disposeWithinGrace` body in `session-router-close.ts`.
