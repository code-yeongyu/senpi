### Changed
- A model chosen explicitly now holds for the whole session: a run started with `--model`, or a session opened with `open_session` naming `provider` and `modelId`, ends a failed turn (a rate limit, an overload) with that model's error instead of moving to another model in the fallback chain. An opener that wants fallback passes `retryFallback` with `modelFallback: true`. A session on the default model keeps model fallback as before ([#6526](https://github.com/code-yeongyu/senpi/pull/6526)).

### Fixed
- When model fallback moves a session to another model, or back, the model now reads a note saying which model is answering, so it no longer states its launch model while another model writes its replies ([#6526](https://github.com/code-yeongyu/senpi/pull/6526)).

## 2026-11-12 - An explicitly chosen model pins the session; fallback switches leave a context note (senpi#6524)

### What changed
- `packages/coding-agent/src/core/launch-model-pin.ts` (new): `launchRetryFallback` gives a launch that named a model and no fallback policy of its own the pinned policy `{ modelFallback: false, fallbackChains: {} }`; an explicit policy always wins.
- `packages/coding-agent/src/main.ts`: a standalone run (no launch profile) applies that policy when `--model` was given.
- `packages/coding-agent/src/core/model-switch-marker.ts` (new) builds a hidden `model_switch` custom message for each fallback switch and revert. `agent-session.ts` queues it from the retry controller's `switchModel` callback and writes it right before the next request (the scheduled continuation and the turn-start restore), so the model that answers reads it.

### Why
- A session launched on one model answered about a quarter of its turns from other models and kept stating its launch model (omo#13243). A model chosen explicitly must answer or fail with its own error, and any switch must be readable by the model.

### Why an extension could not handle it
- The fallback policy is resolved at launch and the switch happens in the session's retry path.

### Expected merge conflict zones
- `packages/coding-agent/src/main.ts`: the `applyRetryFallbackProfile` call in `createCliRuntimeFactory`.
- `packages/coding-agent/src/core/agent-session.ts`: the `switchModel` callback passed to `RetryFallbackController`, the turn-start `_maybeRestoreFallbackPrimary()` call and the `continueRun` callback of the scheduled continuation.

## 2026-11-12 - A model named on open_session pins the session (senpi#6524)

### What changed
- `packages/coding-agent/src/modes/rpc/session-router-open-profile.ts`: an `open_session` that names `provider` and `modelId` and sends no `retryFallback` gets the pinned policy as its launch profile's `retryFallback`, so it rides the same path as a client-supplied policy (park, handover and reattach keep it). A host default model is not the client's choice and is not pinned.

### Why
- Task children and other openers name the model they need; a silent fallback on them is the omo#13243 defect.

### Why an extension could not handle it
- The launch profile is built by the host router.

### Expected merge conflict zones
- `packages/coding-agent/src/modes/rpc/session-router-open-profile.ts`: the `retryFallback` field of the profile returned by `validatedOpenProfile` and the new `withRetryFallback` helper at the end of the file.
