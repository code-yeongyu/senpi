## 2026-10-17 - Export section helpers for before_agent_start (senpi#3579)

### What changed

- `packages/coding-agent/src/core/system-prompt.ts`: exports `isValidSystemPromptSectionName` and `renderCustomSections` so the extension runner validates and renders `before_agent_start` sections with the same rules as `buildSystemPrompt`.

### Why

The runner appends handler-added sections to the turn prompt (see `extensions/changes.md`, senpi#3579) and must not fork the name rule or the tag format.

### Why an extension could not handle it

The helpers are consumed by core runner code, not by an extension.

### Expected merge conflict zones

`assertSystemPromptSectionNames` and the `renderCustomSections` declaration in `system-prompt.ts`.

## 2026-10-17 - before_agent_start systemPromptOptions.sections (senpi#3579)

### What changed

- `packages/coding-agent/src/core/extensions/runner.ts`: `emitBeforeAgentStart` passes every handler one per-emit copy of the options whose `sections` starts empty each turn (sections already on the base options are rendered into `systemPrompt`, so they are never appended twice). After each handler returns or throws, the runner keeps a private copy of the valid entries and drops entries with an invalid name or non-string content, reported through `emitError` against that handler; valid entries from a handler that throws are kept. The accepted entries are appended as `<name>\ncontent\n</name>` blocks once before the builtin run-last handlers dispatch (`beforeAgentStartDispatchOrder` marks that phase `closing`), so MCP instructions still close the prompt, and any entries added later are appended after dispatch. Rendering reads only the private copy, so a handler that mutates or freezes `sections` after returning cannot fail the turn. Until then `event.systemPrompt` shows the chain without those blocks, so `event.systemPrompt + ...` never duplicates a section.
- `packages/coding-agent/src/core/extensions/types.ts`: `BeforeAgentStartEvent.systemPromptOptions` is typed `BuildSystemPromptOptions & { sections: Record<string, string> }`, and the doc comment states the append contract.

### Why

Upstream Pi (0.87.0+) gives handlers a normalized `sections` object and renders the prompt from it. Extensions built for that contract (`pi-agent-browser-native` 0.9.6) crashed on `sections.<name> = ...`, and a section added after `sections ??= {}` never reached the model.

### Why an extension could not handle it

The event object and the final prompt both belong to the runner; an extension cannot change what other extensions receive or how their sections are rendered.

### Expected merge conflict zones

`beforeAgentStartDispatchOrder` (the `closing` flag on the builtin run-last phase), the start of `emitBeforeAgentStart` (options copy, `acceptSections`, `appendSections`), the section insert at the top of its dispatch loop, the handler call inside that loop, the final section append before its return, and the `system-prompt.ts` import in `runner.ts`; the `systemPrompt`/`systemPromptOptions` fields of `BeforeAgentStartEvent` in `types.ts`. Upstream renders the whole prompt from the normalized options, while the fork appends sections to its string prompt, because builtins return `systemPrompt` every turn and upstream treats that as a forced prompt that ignores sections.
