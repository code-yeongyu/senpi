## 2026-11-15 - A remote invoke carries the session port, and its result returns the session writes (senpi#6754)

### What changed

- `packages/agent/src/execution/remote-protocol.ts`: `RemoteInvoke.session?` (a JSON object: the session port's read half the call carries; a non-object is `malformed invoke`) and `RemoteToolResult.sessionEffects?` (the call's session writes). New `HandToolResult` type (`AgentToolResult` plus `sessionEffects`); `toRemoteToolResult` keeps `sessionEffects`. Both fields are optional: absent means today's behavior.
- `packages/agent/src/execution/remote-executor.ts`: `HandCall.session?` passes the carried half to the scope, and `HandScope.run` returns a `HandToolResult`.
- `packages/agent/src/execution/remote-tool-host.ts`: `RemoteToolHostOptions.sessionPort?` (`RemoteSessionPort<E> { carry(call), parse(effects), commit(call, effects: E) }`). `carry` is read when a call is dispatched, so the calls of a parallel batch carry the same snapshot and their writes must compose. `parse` is the loop's closed parser of a call's `sessionEffects` at this boundary: a refusal becomes the call's error result and nothing is committed; `commit` receives only what `parse` returned, before that call's `tool_execution_end`. `sessionEffects` never reaches the result message or the events, and a failing commit becomes the call's error result.
- `packages/agent/src/index.ts`: exports `HandToolResult` and `RemoteSessionPort`.

### Why

- `packages/agent/src/index.ts` exports the two new types so the loop (`sessionPort`) and the hand (`HandScope.run`) can name them.
- senpi#6754: a hosted loop registers no tool, so its session tools (todo, tool_search, goal, schedule, relocate) run on the hand. Their subject, the session, lives in the loop, so a call must carry what it reads and return what it writes. The effects ride inside the result so a durable hand ledger replays them with the outcome, and the loop commits them once.

### Why an extension could not handle it

- The remote invoke and settled messages and the remote ToolHost are agent-core's wire; no extension sees them, and only `packages/agent/src/index.ts` exports its types.

### Expected merge conflict zones

- LOW: `RemoteSessionPort`; `RemoteInvoke`, `RemoteToolResult`, the `invoke` branch of `decodeRemoteMessage`, `toRemoteToolResult`, `HandCall`/`HandScope.run`, and `invokeOf`/`finish` in `createRemoteToolHost`.
- LOW: `packages/agent/src/index.ts`: the remote-protocol and remote-tool-host export lists.

## 2026-11-15 - A hand's session call reads the loop's active set and prompt options, and changes the set through the session port (senpi#6754)

### What changed

- `packages/coding-agent/src/core/extensions/runner.ts`: `LoopHookCallFacts` gains `getActiveTools`, `setActiveTools` and `getSystemPromptOptions`. On a runner without a session, `getActiveTools()` answers the set the call carried (empty otherwise) and `pi.setActiveTools()` goes to the call (a no-op outside one, as before). A call context binds `getSystemPromptOptions`. `bindSessionlessFacts` takes `refreshTools`, which the runtime calls when an extension registers a tool after it was built.

### Why

- `packages/coding-agent/src/core/extensions/runner.ts`: a hosted loop's `tool_search` and lazy activation change the loop's active set from the hand, and `todo` reads the session's prompt surface. Before, the active set was always empty and unchangeable on a hand, and a tool registered later was never callable.

### Why an extension could not handle it

- `packages/coding-agent/src/core/extensions/runner.ts` binds the active set, the prompt options and tool registration; an extension cannot redirect another extension's calls to them.

### Expected merge conflict zones

- LOW: `packages/coding-agent/src/core/extensions/runner.ts`: `LoopHookCallFacts`, `bindSessionlessFacts`, `getActiveTools` and the loop-hook call branch of `createContext`.

### What changed

- `packages/coding-agent/src/core/extensions/builtin/todotools/index.ts`: an instance that never got `session_start` (a hand's runtime running a hosted loop's call) reads the list from the session the call carried at the start of each call. A synced instance records its call as before.

## 2026-11-15 - A hosted loop's session tools run on the hand through the session port (senpi#6754)

### What changed

- `packages/coding-agent/src/modes/rpc/loop-hook-call.ts`: `CarriedSession` gains `branch?` (this hand's entries and the user's messages after the last compaction, in branch order), `header?`, `activeTools?` and `systemPromptOptions?`. The read-only session answers `getBranch`/`getEntries` (`branch`, else `handEntries`) and `getHeader`. `LoopHookEffects` gains `activeTools`, a change `{ activate, deactivate }` relative to the set the call carried, never a whole set, so the changes of a parallel batch's calls compose when the loop applies each to its current set. `effectsReply` builds the effects part of a reply for both loop-hook and tool calls.
- `packages/coding-agent/src/modes/rpc/hand-session-port.ts` (new): `parseCarriedSession` (moved from `loopless-loop-hooks.ts`, extended) and `runInSession`, which runs one tool call inside the call's session and returns its writes as `sessionEffects`. A tool that needs activation (not active on registration) and that the carried active set lacks is first activated through the extensions' lazy activators; one that cannot be activated is refused `Tool <name> not found`, as a local session refuses it, and never runs.
- `packages/coding-agent/src/modes/rpc/loopless-loop-hooks.ts`: uses `parseCarriedSession` and `effectsReply`.
- `packages/coding-agent/src/modes/rpc/runtime-factory-loopless.ts`: `LooplessRuntime.runInSession`; the tool registry is rebuilt on `refreshTools` and `definitions` reads the current one.
- `packages/coding-agent/src/modes/rpc/remote-executor-scope.ts`: a call that carries `session` runs through `runInSession`; any other call runs as before.

### Why

- senpi#6754: on a hand, `todo` failed (`ctx.sessionManager` unbound) and `tool_search` was unknown. The hosted loop's session tools must run there with the same code as locally. Fused and split-local sessions never carry a session, so the session plane (S32) keeps routing their `runs: "brain"` tools loop-side.

### Why an extension could not handle it

- The tool path of the loopless runtime and its session facts belong to the hand engine.

### Expected merge conflict zones

- MEDIUM: `CarriedSession`, the readonly session members and `dispatchLoopHook` (other #5898 slices touch `loopless-loop-hooks.ts`); LOW: `openScope().run` and the registry build in the loopless factory.

## 2026-11-15 - The session port's write half is a closed contract (senpi#6754)

### What changed

- `packages/coding-agent/src/core/hand/session-effects.ts` (new): `SessionEffects` (`sent`, `notices`, `entries`, `userMessages`, `activeTools` as `{ activate, deactivate }`, `droppedLate`), `parseSessionEffects` (refuses every unknown kind, member and shape with `SessionEffectsContractError`) and `applyActiveToolsChange`.

### Why

- A loop commits a hand's session writes into its own session, so it must accept only the closed shape (review L1 on #6762), as `hook-contract.ts` does for the loop-hook reply; and a parallel batch's active-set changes must compose (review M1).

### Why an extension could not handle it

- It is the loop side's contract of the hand wire, shared by the loop-hook path and the tool path.

### Expected merge conflict zones

- LOW: new file.

## 2026-11-15 - A headless session's calls carry its session to the chosen hand (senpi#6754)

### What changed

- `packages/coding-agent/src/modes/headless/loop-session-port.ts` (new): `createLoopSessionPort(session)`, the loop side of the session port for an engine session: it carries the branch after the last compaction (custom entries and user messages), leaf, header, idle and active set, and commits parsed writes into the session (entries appended, the active-set change applied to the current set, messages and user messages sent as `pi.sendMessage`/`pi.sendUserMessage` send them, notices shown).
- `packages/coding-agent/src/modes/headless/hand-selection.ts`: `HandSelectionOptions.sessionPort?(sessionId)`; a linked hand's remote ToolHost gets it.
- `packages/coding-agent/src/modes/headless/headless-host.ts`: `headlessHostOptions` passes each session's port to the hand selection.

### Why

- Review L2 on #6762: no shipped `createRemoteToolHost` passed a session port, so a session whose tools run on a chosen hand ran todo there with no session (`Cannot read properties of undefined (reading 'getBranch')`).

### Why an extension could not handle it

- The hand selection and the engine's session runtimes are the headless host's own wiring.

### Expected merge conflict zones

- LOW: `linkTo` and `restore` in `hand-selection.ts`; `headlessHostOptions` in `headless-host.ts`.
