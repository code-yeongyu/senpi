## 2026-11-28 - Export every engine path an embedding launcher reaches, plus the bundle's runtime manifest (senpi#7657)

### What changed

- `packages/coding-agent/package.json`: adds the exports `./cli`, `./valid-cwd`, `./private-fd-startup-release`, `./session-worker` (programs and launcher entries, `import` only) and `./kill-guard-command`, `./kill-guard`, `./host-probe`, `./supervisor-route`, `./config`, `./model-coverage` (with their `.d.ts`), each at the compiled file an embedder used to import by path. `./runtime-manifest.json` names `dist/bundle/runtime-manifest.json` under the `default` condition.
- `packages/coding-agent/src/model-coverage.ts` (new): re-exports what a launcher needs to check model coverage without booting the engine: `builtinProviders`, `ModelRuntime`, `AuthStorage`, `ReadOnlyAuthStorage`, `InMemoryCodingAgentModelsStore`, `SettingsManager`, `registerAnthropicSubscriptionExtension`, `loadAnthropicSubscriptionProviderSettings`.
- `packages/coding-agent/test/package-distribution.test.ts`: a data export must name a JSON file inside `dist/bundle/`; every other export keeps the compiled-source-with-types rule.

### Why

- oh-my-openagent imports `dist/cli.js`, `dist/modes/rpc/host-probe.js`, `dist/cli/kill-guard-command.js`, `dist/modes/rpc/supervisor-route.js`, `dist/config.js`, `dist/valid-cwd.js`, `dist/private-fd-startup-release.js`, `dist/private-fds.js`, `dist/core/{model-runtime,auth-storage,models-store,settings-manager}.js`, `dist/core/extensions/virtual-modules.js` and the anthropic-subscription modules by relative path, compiles `dist/modes/rpc/session-worker.js` and `dist/core/kill-guard/index.js` into its binary, and checks `dist/core/brand.js` to detect a partial install. Every one of those is per-file output that the next stage stops shipping; exported subpaths keep the same targets now and can move to the bundle later without another launcher change. `runtime-manifest.json` sits in `dist/bundle/` in both layouts, so its presence and the `cli.js` beside it stay a stable launcher check.

### Why an extension could not handle it

- The package's export map is its distribution contract.

### Expected merge conflict zones

- LOW: the end of the `exports` map in `package.json`.

## 2026-11-28 - Extensions get the host's own instance of every library subpath (senpi#7657)

### What changed

- `packages/coding-agent/src/core/extensions/senpi-subpath-modules.ts` (new): `SENPI_SUBPATH_MODULES`, the host's namespace for every `@code-yeongyu/senpi/<subpath>` library export (`config`, `engine`, `engine-trust`, `host-probe`, `kill-guard`, `mcp-env-grants`, `model-coverage`, `pending-input`, `presenter-authority`, `private-fds`, `prompt-presets`, `session-worker-data`, `subscription-egress`, `supervisor-route`, `tools-core`). The programs and launcher entries (`rpc-entry`, `program-resume-startup`, `cli`, `valid-cwd`, `private-fd-startup-release`, `session-worker`, `kill-guard-command`, `bun-runtime`), the unpublished `client` and the `runtime-manifest.json` data export are not listed.
- `packages/coding-agent/src/core/extensions/loader.ts`: `VIRTUAL_MODULES` spreads `SENPI_SUBPATH_MODULES` in place of its single `session-worker-data` entry.

### Why

- Inside a bundled or compiled senpi, an extension importing any other subpath resolved the package's per-file `dist/` copy. On an installed 2026.11.28-1, an extension importing the library subpaths made the bundled Node CLI read 2070 per-file modules, a second engine graph with its own module state and classes beside the bundle's.

### Why an extension could not handle it

- Which module instance an extension import resolves to is decided by the loader's virtual-module table.

### Expected merge conflict zones

- LOW: the end of the `VIRTUAL_MODULES` table and the import block of `loader.ts`.

## 2026-11-28 - The release bundle emits an entry for every exports subpath (senpi#7657)

### What changed

- `scripts/bundle-entry-points.mjs`: `exportEntryPoints()` reads the coding-agent manifest's `exports` and returns one entry per subpath whose `import` condition names a compiled module, named for it (`.` is `index`). The `runtime-manifest.json` data export has no entry. `bundleRequiredInputs()` lists them in place of the hand-written `index`, `rpc-entry` and `client` inputs.
- `scripts/build-coding-agent-bundle.test.mjs`: the built bundle carries an entry for every exports subpath and the file each data export names.
- `scripts/build-coding-agent-bundle.mjs`: the main split build takes `cli` plus every export entry, so each subpath shares the CLI's module instances. The plugin that empties `bun/runtime-modules` for Node no longer applies to that module's own entry, so `dist/bundle/bun-runtime.js` keeps its real contents.
- `scripts/node-bundle-smoke.test.ts`: under Node and Bun, an extension importing every library subpath gets, export for export, the running bundle's own entry for it.

### Why

- First stage (S2a) of shipping one copy of the code: the bundle must serve every subpath before `exports` can point at it. `exports` and the per-file tree stay unchanged in this stage.

### Why an extension could not handle it

- The bundle layout is release build tooling.

### Expected merge conflict zones

- LOW: the main `build()` call's `entryPoints` and `bunRuntimeModulesPlugin` in `build-coding-agent-bundle.mjs`; `bundleRequiredInputs()`.
