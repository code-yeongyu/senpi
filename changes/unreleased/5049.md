## 2026-10-30 - A `!last-resort` fallback-chain entry reachable only through a usage limit, billing or a signed-out provider (senpi#3845)

### What changed

- `packages/coding-agent/src/core/retry-fallback/chains.ts`: `splitLastResort()` and `LAST_RESORT_FLAG`; `parseFallbackSelector` marks `lastResort`, `canonicalizeFallbackChains` keeps the flag on entries and ignores flagged keys, and `candidatesAfter` locates a session resting on a last-resort rung by its selector.
- `packages/coding-agent/src/core/retry-fallback/candidates.ts`: `CandidateFilters.allowLastResort`; a last-resort selector is skipped as `last-resort-gated` unless it is set.
- `packages/coding-agent/src/core/retry-fallback/controller.ts`: `opensLastResort()` (billing reason, any usage-limit scope, billing prose, provider-not-configured sentinel, or no auth for the current provider) opens the rung for one `tryFallback` walk; `canTryFallback(refusedProvider, failure)` takes the failure for the same decision.
- `packages/coding-agent/src/core/retry-fallback/validate.ts`: entries accept the flag; a flagged key warns.
- `packages/coding-agent/src/core/agent-session.ts`: the retry-decision calls to `canTryFallback` pass the failed assistant message.

### Why

- A host (omo#10750) appends the parent session's model as the last rung of a task child's chain, but the rung was also taken for overloads, refusals and hard errors. It should only rescue a child whose every rung is spent or signed out.

### Why an extension could not handle it

- Candidate selection and the retry decision run inside the core retry-fallback controller and `AgentSession`; RPC `set_retry_fallback` is launch-time only, so a host cannot add the rung after it observes a limit.

### Expected merge conflict zones

- LOW: `scanCandidates` in `candidates.ts`, `canTryFallback`/`tryFallback` in `controller.ts`, `candidatesAfter` and `expandEntries` in `chains.ts`, the `canTryFallback()` calls in `AgentSession`'s retry decision.
