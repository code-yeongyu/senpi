### Added
- Loop-hook link for a loop that runs away from the user's machine: `createLoopHookHost` sends each hooked loop event to the user's machine (`serveLoopHooks`) and resolves with its result before the provider request. While that machine is offline the call waits and resumes exactly once. A call the previous process never started is sent again with the same ID; one it started is never re-run and ends `LoopHookRestartedError`. KILL-HOOK-01..05 conformance cases are registered and exported from `./conformance` ([#5741](https://github.com/code-yeongyu/senpi/pull/5741)).

<!-- changes-log: packages/coding-agent/CHANGELOG.md -->
### Added
- A hand serving a loop that runs elsewhere can be the home of two-sided extensions (`twoSidedHome: "hand"` on the hand's scopes): their tool hooks stay with the tool on the hand instead of being forwarded to the loop, and the hand runs their loop hooks and the user's shell hooks on the same runtime (`createLooplessHand`), bound to the loop session's id for that call only. A runner without a session now runs extensions' `before_agent_start`. The default (`"loop"`) is unchanged ([#5741](https://github.com/code-yeongyu/senpi/pull/5741)).

## 2026-11-04 - Loop-hook link and KILL-HOOK (S33, senpi#5741)

### What changed

- `packages/agent/src/execution/loop-hook-host-protocol.ts`, `loop-hook-host.ts`, `loop-hook-host-hand.ts` are new: the one-lane loop-hook protocol, the loop host's side (`createLoopHookHost`) and the user machine's side (`serveLoopHooks`).
- `packages/agent/src/execution/testing/kill-hook.ts` is new: KILL-HOOK-01..05.
- `packages/agent/src/conformance/registry.ts` registers the KILL-HOOK cases; `packages/agent/src/conformance/index.ts` exports `KILL_HOOK_CASES` and `KILL_HOOK_DECLARATIONS`.
- `packages/agent/src/index.ts` exports the loop-hook host and hand.

### Why

Brain/hand split S33 (decisions C8, K5, K7): with the loop away from the user's machine, the user's loop hooks still run on that machine and shape the provider request, and the work pauses while that machine is offline.

### Why an extension could not handle it

The link runs below the session, on the execution transport; no extension sees the loop host's provider requests before they leave.

### Expected merge conflict zones

`conformance/registry.ts` tail (the registry chain S27a, S26b, S33, S35); the `execution/` export block of `src/index.ts`; the `./conformance` export list.

## 2026-11-04 - Two-sided extensions can live on the hand (S33, senpi#5741)

### What changed

- `packages/coding-agent/src/modes/rpc/loopless-tool-handlers.ts`: `extensionToolHandlers(runner, twoSidedHome)`; with `"hand"`, no extension's tool handlers are forwarded to the loop.
- `packages/coding-agent/src/modes/rpc/runtime-factory-loopless.ts` and `remote-executor-scope.ts` pass the `twoSidedHome` option through (default `"loop"`, S29's behavior).
- `packages/coding-agent/src/modes/rpc/remote-executor-scope.ts`: `createLooplessHand` returns the scopes, `runLoopHooks(scope, event, payload)` and `loopHooks(event, payload)`, which run the user's loop hooks on that scope's own runtime (the same extension instances its tool calls run on), and `close()`. A scope ID stays bound to its first root (`scope_binding_mismatch` otherwise); a loop-hook call never reopens a disposed scope; each runtime is disposed once; `close()` waits for every disposal and ignores a runtime that never opened, and after it every call is refused. `createLooplessHandScopes` is its scopes.
- `packages/coding-agent/src/modes/rpc/loopless-tool-handlers.ts`: `extensionLoopHooks` serves two events, in a session's order, each carrying every field of the loop's own event plus the loop's idle state (`input`: `inputId`, `text`, `images`, `source`, `attribution`, `streamingBehavior`; `before_agent_start`: `prompt`, `systemPrompt`, `trigger`, `images`, `preview`, `systemPromptOptions` as the loop built them, so apart from `cwd`, which is set to this machine's workspace, they describe the loop's machine): `input` returns the input result (`continue`, `handled`, or `transform` with the new text), which the loop returns from its own `input` handler, and `before_agent_start` returns the combined result. Both run only the user's extensions and the hooks builtin, inside a `createLoopHookCall` binding (the loop session's id, read-only, for that call only; reading it from a kept context after the call throws `LoopHookCallEndedError`, naming the member, which is the one deliberate refusal after a call), and each reply carries the messages its handlers sent (`sent`) and their notices (`notices`), including ones from a call's work after an earlier call of the same loop session ended (held up to `LATE_PER_SESSION`, past which the oldest held notice is dropped, or the oldest message when none is held, counted as `droppedLate` and never thrown) and its own handlers' failures (`errors`; a concurrent tool call's are not attributed to it).
- `packages/coding-agent/src/modes/rpc/runtime-factory-loopless.ts`: the loopless runtime exposes `runLoopHooks` and binds its loop-hook call facts.

### Why

Brain/hand split S33 (K5): with a hosted loop, a two-sided extension runs whole on the user's machine, so its tool hooks stay there.

### Why an extension could not handle it

Whether a hand forwards an extension's tool events is the loopless runtime's decision.

### Expected merge conflict zones

`loopless-tool-handlers.ts` `extensionToolHandlers` head; the `local` option blocks of the runtime factory and the hand scopes.

## 2026-11-04 - before_agent_start on a runner without a session; loop-hook call facts (S33, senpi#5741)

### What changed

- `packages/coding-agent/src/core/extensions/runner.ts`: `emitBeforeAgentStart` defines `ctx.getSystemPrompt` instead of assigning it. On a runner without a session the copied member is a getter-only loop-side member, so every extension's `before_agent_start` threw there.
- `packages/coding-agent/src/core/extensions/runner.ts`: `bindSessionlessFacts` takes an optional `loopHookCall` source. While a loop-hook call is in progress on a hand, a context of a runner without a session gets that call's read-only `sessionManager` (the loop session's id only), its abort `signal`, the loop's idle state (`isIdle`), and `ctx.ui.notify` goes to the call (`LoopHookCallFacts.notify`); `pi.sendMessage` from work a call started goes to that call's sender (`loopHookSend`), also after the call ended. Each is carried back to the loop. Outside any call these stay unbound. Exports `LoopHookCallFacts`.
- `packages/coding-agent/src/core/extensions/runner.ts`: `emitBeforeAgentStart` (option `only`) and `emitInput` (trailing `only`) can dispatch to a subset of extensions.

### Why

Brain/hand split S33 (C8, K5): a hand runs the user's loop hooks for a loop that runs elsewhere, on its own runner without a session.

### Why an extension could not handle it

The handler context and the event dispatch are the runner's.

### Expected merge conflict zones

`runner.ts`: the `getSystemPrompt` lines in `emitBeforeAgentStart`, its options type and dispatch head; `emitInput`'s parameter list and dispatch head; `bindSessionlessFacts`; the end of `createContext`.
