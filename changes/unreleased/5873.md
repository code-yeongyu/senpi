## 2026-11-05 - nested ctx.executeTool() runs on the prepared ToolHost (senpi#5873)

### What changed

- `packages/coding-agent/src/core/execute-tool-on-host.ts`: new `nestedToolOnHost(agent, tool)` returns the tool whose `execute` runs the body as a one-call sequential batch on `createPreparedToolHost`, with the agent's batch store, execution scope and `onExecutionPipeline` witness sink. The body gets the signal and update callback its caller passed, and a thrown body is rethrown. The host call that `runExecuteToolOnHost()` already made moves into the shared `runOnHost()` / `hostBody()` (pass-through argument schema, preflight facts carried to the host's copy), with no change to `pi.executeTool()`.
- `packages/coding-agent/src/core/agent-session.ts`: `_executeNestedToolCall` hands `runToolCall` the resolved tool wrapped by `nestedToolOnHost()`. `runToolCall` keeps preparation, validation, the `tool_call` preflight, the abort race, update gating, error conversion and the `tool_result` hooks.

### Why

Plan row S19a (senpi#5826): every tool body runs on the ToolHost, so no `executeTool()` call, including one a running tool makes, reaches a tool without the prepared executor's prepare, freeze and release.

### Why an extension could not handle it

`ctx.executeTool()` is the session's own tool context; an extension cannot change how the session runs a nested call.

### Expected merge conflict zones

`agent-session.ts` in `_executeNestedToolCall` and its imports.
