## 2026-11-07 - RPC clients trust a workspace and read/write its project settings (senpi#6176)

### What changed

- `packages/coding-agent/src/modes/rpc/project-workspace-commands.ts`: new. `get_project_trust` / `set_project_trust` (the `/trust` choices, saved through `ProjectTrustStore.setMany`, applied with `AgentSession.applyProjectTrustChange`; refused with `project_trust_locked` under `--approve`/`--no-approve`) and `get_project_settings` / `set_project_setting` (the project settings file read as stored; one top-level key written through `SettingsManager.setProjectSetting`).
- `packages/coding-agent/src/modes/rpc/connection-handler.ts`: the four cases.
- `packages/coding-agent/src/modes/rpc/rpc-session-command-types.ts`, `rpc-read-response-types.ts`, `rpc-mutation-response-types.ts`: the wire types.
- `packages/coding-agent/src/modes/rpc/rpc-error-types.ts`: `project_trust_locked`, `project_not_trusted`, `project_settings_unreadable`.
- `packages/coding-agent/src/modes/rpc/method-classes.ts`: `get_project_trust` observe; `set_project_trust`, `get_project_settings`, `set_project_setting` device_admin (the digest moves).
- `packages/coding-agent/src/modes/rpc/method-classes-schema-session.ts`: their inbound schemas.
- `packages/coding-agent/src/modes/rpc/session-attachment-gate.ts`, `session-command-activity.ts`: the two reads join the read allow-lists.
- `packages/coding-agent/src/modes/rpc/loopless-runtime-settings.ts`: passes `projectTrustLocked` from the launch flag.

### Why

- An RPC session resolves trust without a UI, so a project is never trusted over RPC and its settings, skills, prompts, extensions and MCP servers never load for the desktop app, local or remote; no verb could save a decision or edit project settings.

### Why an extension could not handle it

- Trust decides which extensions load at all, and the session rebuild and the RPC method-class table are core; an extension cannot run before the trust decision it would be making.

### Expected merge conflict zones

- LOW: the `get_loaded_surfaces` neighbourhood in `connection-handler.ts`, `method-classes.ts` and the schema table.

## 2026-11-07 - SettingsManager reads the project file regardless of trust and writes one key (senpi#6176)

### What changed

- `packages/coding-agent/src/core/settings-manager.ts`: `projectTrustLocked` create option + `isProjectTrustLocked()`; `readProjectSettingsFile(path)` (parsed and migrated, never trust-gated, no write); `setProjectSetting(key, value)` through `updateProjectSettings` (trusted-only, refuses a file that failed to load instead of skipping the write silently), awaiting the write queue.

### Why

- The RPC workspace verbs (senpi#6176) need the project file as stored and a single-key write on the same locked merge-on-write path the terminal uses.

### Why an extension could not handle it

- Project settings storage, its lock and its load-error state are private to `SettingsManager`.

### Expected merge conflict zones

- LOW: `SettingsManagerCreateOptions`, next to `getProjectSettings` and `isProjectTrusted`.

## 2026-11-07 - A saved trust decision outranks the per-process trust memo (senpi#6176)

### What changed

- `packages/coding-agent/src/main.ts`: `createCliRuntimeFactory` uses `projectTrustByCwd` only while nothing is saved for the folder, and passes `projectTrustLocked` from `--approve`/`--no-approve`.

### Why

- The memo kept an RPC session's "untrusted" for the folder, so a decision saved later through `set_project_trust` never reached the next session the same engine opened.

### Why an extension could not handle it

- The memo and the runtime factory are core startup code.

### Expected merge conflict zones

- LOW: the project-trust block at the top of the runtime-services step.
