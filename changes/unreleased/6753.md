## 2026-11-15 - A forwarded loop event on a hand returns its result and keeps a session's budgets (senpi#5898)

### What changed

- `packages/coding-agent/src/core/extensions/runner.ts`:
  - `emitForwardedLoopEvent` is generic over the event and returns its result. A forwarded `session_before_*` event (on a hand, `session_before_compact`) returns what a session's `emit` returns: the last handler result, and the first `cancel` ends the walk. `dispatchLifecycle` collects that result and halts on `cancel`. Every other event still returns `undefined`.
  - A forwarded `session_shutdown` takes a session's own shutdown path (`dispatchEmit`, now with the provenance filter): each handler gets `event.signal` and the `sessionShutdownHandlerTimeoutMs` cap, and a handler past it is aborted, reported and skipped.
  - `bindSessionlessFacts` takes `getAgentDir`, so a runner without a session reads its handler budgets from its own agent directory.

### Why

- A hosted loop's PreCompact hooks and its users' compaction extensions run on the hand. Their `cancel` or custom `compaction` must go back to the loop that compacts.
- A hung `session_shutdown` handler on the hand would otherwise hold the call forever, where a local session stops waiting at its cap.

### Why an extension could not handle it

- The runner owns how handler results combine and how long it waits for a handler. An extension cannot read another extension's result or bound another extension's handler.

### Expected merge conflict zones

- LOW: `emitForwardedLoopEvent`, `dispatchLifecycle`, the handler loop of `dispatchEmit` and `bindSessionlessFacts` in `runner.ts`.

## 2026-11-15 - A hand serves a hosted loop's compaction and shutdown events (senpi#5898)

### What changed

- `packages/coding-agent/src/modes/rpc/loopless-loop-hooks.ts`: `extensionLoopHooks` serves `session_before_compact` (its reply carries the combined `SessionBeforeCompactResult`), `session_compact`, `session_compact_failed` and `session_shutdown`. It takes the loop's cancel signal; `session_before_compact` handlers get the call's own signal, which aborts while they run when the loop cancels the call.
- `packages/coding-agent/src/modes/rpc/loop-hook-payloads.ts`: new. It is the hand's boundary parse of every forwarded loop event's payload, moved out of `loopless-loop-hooks.ts`. A compaction `preparation` carries `fileOps` as string arrays, which become Sets on the hand. A malformed payload is refused, never partly applied.
- `packages/coding-agent/src/modes/rpc/agent-message-schema.ts`, `session-entry-schema.ts`, `compaction-settings-schema.ts`: new. Zod schemas for every `AgentMessage` role, every `SessionEntry` type and every `CompactionSettings` field (non-negative token counts, ratios in [0, 1]); each is keyed by its union, so a new role, entry type or settings field fails to compile until it is covered.
- `packages/coding-agent/src/modes/rpc/loop-hook-call.ts`: `LoopHookCall.run` takes a `LoopHookCallScope` (session, cwd, idle, carried session, the loop's `cancel`) and passes the call's own signal to `dispatch`; the loop's cancel aborts it.
- `packages/coding-agent/src/modes/rpc/remote-executor-scope.ts`: `LooplessHand.loopHooks` passes the link's cancel signal through.
- `packages/coding-agent/src/modes/rpc/runtime-factory-loopless.ts`: the loopless runtime sets the extension event handler budget from its own settings (`extensionEventHandlerWarnMs`, `extensionEventHandlerTimeoutMs`), as a session does, and binds its agent directory.

### Why

- senpi#5898 (K8, K9): the brain emits every loop event and the hand runs the hooks. The user's PreCompact and PostCompact shell hooks, and their extensions' compaction and shutdown handlers, never ran for a hosted loop.
- Review of #6753: forwarded handlers ran unbounded on the hand, the parsers passed malformed nested fields to handlers, and a loop's cancel never reached the hooks still running.

### Why an extension could not handle it

- The loop-hook lane, the call's facts and the runtime's handler budget belong to the loopless runtime.

### Expected merge conflict zones

- MEDIUM: `extensionLoopHooks` event branches (other #5898 slices add events there), the parsers in `loop-hook-payloads.ts`, and `LoopHookCall.run` callers.

## 2026-11-15 - The loop-hook link cancels a call its caller stopped waiting for (senpi#5898)

### What changed

- `packages/agent/src/execution/loop-hook-host-protocol.ts`: new message `hook.cancel { callId }` (loop host to hand), on the call's lane.
- `packages/agent/src/execution/loop-hook-host.ts`: when a `run` caller's signal aborts, the host sends `hook.cancel` for that call besides rejecting it.
- `packages/agent/src/execution/loop-hook-host-hand.ts`: `LoopHookRunner` takes a third argument, the call's `AbortSignal`; `serveLoopHooks` aborts it on `hook.cancel`.

### Why

- An aborted call only rejected the loop host's own wait, so the user's hooks kept running on the user's machine after the loop cancelled compaction.

### Why an extension could not handle it

- The loop-hook link is agent-core protocol; nothing above it can reach a call in flight on the other machine.

### Expected merge conflict zones

- LOW: the message union and decoder in `loop-hook-host-protocol.ts`, `run`'s abort handler in `loop-hook-host.ts`, `serve` in `loop-hook-host-hand.ts`.
