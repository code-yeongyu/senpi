## 2026-11-22 - Leaving GPT after a reload restores the edit tools (senpi#3838)

### What changed

- `packages/coding-agent/src/core/extensions/builtin/gpt-apply-patch/extension.ts` leaves the active edit tools in place if `apply_patch` cannot activate. A successful swap records the tools it removed, keeping earlier names when settings reload adds another edit tool. On a non-GPT model, it removes `apply_patch` and restores only recorded tools that the current selection permits.
- `packages/coding-agent/src/core/extensions/builtin/gpt-apply-patch/types.ts` lets the extension use the existing session-entry API.

### Why

- A new extension instance needs to recover which tools the GPT swap removed. Lazy activation can add `apply_patch` without replacing any tools, and a settings reload can add or revoke an edit tool before the next model switch.

### Why an extension could not handle it

- The fix is inside the builtin extension that owns the swap.

### Expected merge conflict zones

- LOW: toolset synchronization and session startup in `extension.ts`, and the extension API type in `types.ts`.

## 2026-11-22 - Use the current tool selection when restoring swapped tools (senpi#3838)

### What changed

- `packages/coding-agent/src/core/agent-session.ts` can check the current `defaultTools` selection when enabling a built-in tool. The check is opt-in, leaves already-active tools alone, and does not override explicit tool flags.

### Why

- A built-in tool can remain registered after settings reload removes it from `defaultTools`. Restoring a tool from a previous selection should not enable it again.

### Why an extension could not handle it

- The session knows whether CLI options or settings determine tool selection.

### Expected merge conflict zones

- LOW: active tool selection and extension binding in `agent-session.ts`.

## 2026-11-22 - Let extensions respect defaultTools when enabling tools (senpi#3838)

### What changed

- `packages/coding-agent/src/core/extensions/types.ts` adds the optional `respectDefaultTools` flag to `setActiveTools`. `packages/coding-agent/src/core/extensions/loader.ts` passes it through to the session.

### Why

- An extension restoring a previous toolset needs to respect current settings without changing existing callers of `setActiveTools`.

### Why an extension could not handle it

- The extension API needs to forward the option to the session that owns the effective selection.

### Expected merge conflict zones

- LOW: the `setActiveTools` signature and loader forwarding.
