## 2026-11-12 - A live writer is judged by its start time before its boot instant (senpi#3152)

### What changed

- `packages/coding-agent/src/core/session-writer-claims.ts`: a writer claim records the writer's process key (`WriterProbes.readProcessKey`); `ownerGone` compares keys exactly when both sides have one, then judges a live same-host writer by its process start time, and the boot instant decides only when the start time cannot be read.
- `packages/coding-agent/src/core/session-holders.ts`: the holder record (`HolderRecord`) carries the holder's process key.

### Why

- A wall-clock step moves the kernel's recorded boot instant, so a live writer whose claim predates a step past the tolerance read as another boot and could be displaced (senpi#3152, review of #6530).

### Why an extension could not handle it

- Writer claims are core session ownership.

### Expected merge conflict zones

- LOW: `ownerGone` in `session-writer-claims.ts`.

## 2026-11-12 - The resident writer probe checks its gone set first and judges a live writer by its start time (senpi#3152)

### What changed

- `packages/coding-agent/src/modes/rpc/host-handover-resident-writer.ts`: the reopen watch's probe checks its `gone` set before any boot read, so a gone writer no longer re-reads the kernel record (a `sysctl` spawn on macOS) on every 250 ms poll, and a verified live writer is re-checked by its pid alone; the resident writer records its process key, which decides exactly when both sides have one; otherwise a live same-host writer is judged by its process start time first, the boot instant only when that cannot be read.

### Why

- Review LOWs on #6530 (senpi#3152): the extra kernel reads per poll, and a live writer recorded before a wall-clock step past the tolerance read as another boot.

### Why an extension could not handle it

- The RPC host handover is host internals.

### Expected merge conflict zones

- LOW: `residentWriterProbe`.

## 2026-11-12 - A process is identified by a key no wall-clock step moves (senpi#3152)

### What changed

- `packages/coding-agent/src/core/extensions/builtin/terminal/process-key.ts` (new): `readProcessKey(pid)` returns `<boot>:<start>` from values the kernel stores and never rewrites. On Linux that is `/proc/sys/kernel/random/boot_id` and the start time in clock ticks from `/proc/<pid>/stat`. On macOS it is `kern.bootsessionuuid` and `p_starttime` as `ps -o lstart=` prints it in UTC (1 s resolution; the instant is stored at fork). There is no key elsewhere, and Windows keeps the millisecond rule. The boot half is read once per process.
- `packages/coding-agent/src/core/extensions/builtin/terminal/lease-file.ts`: a reclaim-lock holder record carries the holder's `processKey`. `reclaimLockState` compares keys exactly when the record and the live pid both have one, and otherwise judges a live holder pid by its process start time first, the boot instant deciding only when the start time cannot be read. This also judges session holder records, the move lock and terminal-state GC.

### Why

- On Linux the start instant compared before was `btime + start ticks`, and `btime` moves with every clock step, so a live holder recorded before a step read as a reused pid. The boot id also closes pid reuse across a reboot, where a matching start time used to look live (#6562 review).

### Why an extension could not handle it

- The lease and reclaim-lock primitives are the builtin terminal's own.

### Expected merge conflict zones

- LOW: `reclaimLockState` and `takeReclaimLock` in `lease-file.ts`.
