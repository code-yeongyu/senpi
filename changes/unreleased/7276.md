## 2026-11-22 - A tool can run the tool_result handlers for work it already did (senpi#7232)

### What changed

- `packages/coding-agent/src/core/extensions/types.ts`: `ExtensionToolContext.reportToolResult(report)` runs the session's `tool_result` handlers for a result the calling tool reports (`toolName`, `input`, `content`, optional `details` and `isError`). No tool runs and no `tool_call` handler is asked. The event carries the id `<calling id>/reported-<n>` and `parentToolCallId`; it emits no `tool_execution_*` event and leaves no `nestedCalls` record. It resolves to `{ toolCallId, result, failures }` and never rejects for a handler failure.
- `packages/coding-agent/src/core/extensions/runner.ts`: `createToolContext()` defines `reportToolResult` and numbers the reports of one call. `emitToolResult()` also hands each handler that threw, timed out or was interrupted to the new dispatch option `onHandlerFailure`, in addition to the extension error listeners.
- `packages/coding-agent/src/core/extensions/reported-tool-result.ts` (new, fork-only): the `ReportedToolResult`, `ReportedToolResultFailure` and `ReportedToolResultOutcome` types and `emitReportedToolResult()`, which builds the event.
- `packages/coding-agent/src/core/extensions/two-sided-forwarding.ts` (fork-only): `ToolEventDispatchOptions.onHandlerFailure`.
- `packages/coding-agent/src/core/extensions/types.ts`: new observe-only event `tool_call_ready` (`ToolCallReadyEvent`: `toolCallId`, `toolName`, optional `parentToolCallId`, `input`) with its `pi.on` overload and `ExtensionEvent` member. `packages/coding-agent/src/core/extensions/runner.ts`: `emitToolCallReady()` fires it with a deep copy of the arguments the call runs with, awaited before the tool runs under the call's and the turn's abort (an abort blocks the call); `emitToolCall()` calls it once the whole chain let the call run, and not when it serves one forwarded handler (`only`), whose chain ends where the call runs. A blocked call gets none. The session and loopless callers that skip `emitToolCall()` without a `tool_call` handler call `emitToolCallReady()` instead (see the core and RPC entries). `packages/coding-agent/src/core/extensions/index.ts` re-exports `ToolCallReadyEvent`. `packages/coding-agent/src/core/extensions/event-placement.ts` (fork-only): `tool_call_ready` is a `runtime` event.

### Why

- A codemode cell writes files without a `write` or `edit` call (its `write()` helper, `fs`, a child process, a Python cell), so those files skipped diagnostics and every other write hook. In a multi-harness build comparison, agents wrote most of their source that way.
- The existing way to reach the hooks, `ctx.executeTool("write", ...)`, writes the file a second time: it can overwrite a change made in between, asks for permission again for a file that is already on disk, and can be blocked by a `tool_call` guard, which would hide the hook output. Running only the `tool_result` chain for the content on disk has none of those failure modes.

### Why an extension could not handle it

- A `tool_call` handler may redirect a call by mutating `event.input` (`tool_execution_start` is emitted before that chain runs), and handler order across extensions is load order, so no handler can be sure it sees the final arguments. Only the runner knows when the chain ended.
- `tool_result` dispatch belongs to the runner: an extension can register a handler, but nothing public lets one run the other extensions' handlers, and the per-handler deadline, abort handling and hook lifecycle events live inside `emitToolResult()`.

### Expected merge conflict zones

- LOW: `ExtensionToolContext` in `types.ts` (one method after `executeTool`, one import line).
- LOW: `createToolContext()` in `runner.ts` (one property, one counter, one import line).
- LOW: the end of `emitToolCall()` in `runner.ts` (one `emit` call); the `ToolCallEvent` block, the `ExtensionEvent` union and the `pi.on` overloads in `types.ts` (one interface, one member, one overload).
- MEDIUM: the three failure branches inside the `emitToolResult()` handler loop in `runner.ts` (one added call each), the same lines senpi#7073 and oh-my-openagent#14354 touched.

## 2026-11-22 - Root exports for a reported tool result (senpi#7232)

### What changed

- `packages/coding-agent/src/index.ts`: exports the types `ReportedToolResult`, `ReportedToolResultFailure` and `ReportedToolResultOutcome` from the package root, and `ToolCallReadyEvent` beside `ToolCallEvent`.

### Why

- They are the argument and the result of `ExtensionToolContext.reportToolResult()`, which extensions import from the package root like the rest of the tool-context API.

### Why an extension could not handle it

- The package root is the public import surface; an extension cannot add an export to it.

### Expected merge conflict zones

- LOW: one `export type { ... }` block next to the `lifecycle-api.ts` export.

## 2026-11-23 - A call with no tool_call handler still fires tool_call_ready (senpi#7232)

### What changed

- `packages/coding-agent/src/core/agent-session.ts`: `preflightToolCall()` builds the `tool_call` event once; with no `tool_call` handler registered it returns `runner.emitToolCallReady(event, signal)` instead of `undefined`, so `tool_call_ready` observers see every call about to run, and an abort during their wait blocks the call.

### Why

- Codemode holds a model `write` or `edit` call's file from `tool_call_ready`, the point the final path is known; a session with no `tool_call` handler skipped the dispatch and with it the event.

### Why an extension could not handle it

- Whether the `tool_call` dispatch runs is decided here, before any extension is asked.

### Expected merge conflict zones

- LOW: the no-handler branch at the end of `preflightToolCall()` (the event moved above it, one return changed).

## 2026-11-23 - A loopless call with no tool_call handler still fires tool_call_ready (senpi#7232)

### What changed

- `packages/coding-agent/src/modes/rpc/loopless-tool-handlers.ts`: `beforeToolCall` with no `tool_call` handler registered calls `runner.emitToolCallReady()` instead of resolving `undefined`.

### Why

- Same contract as a session: `tool_call_ready` fires for every call about to run, which is where codemode holds a model write's file.

## 2026-11-22 - Files an eval cell writes go through the write hooks and are listed in its result (senpi#7232)

### What changed

- `packages/senpi-codemode/src/written-files/` (new): `source-file.ts` holds the one definition of a source file (a regular file inside the session cwd, outside `.git`, `node_modules` and the session's artifacts directory, not ignored by the workspace, at most 1 MiB, whose first 8 KiB are UTF-8 text). `workspace-scan.ts` lists the candidates: in a repository through `git status --porcelain=v2` (files that differ from HEAD or are untracked, plus files committed since the previous scan), elsewhere through `git ls-files --others --exclude-standard` against an empty repository kept in the session artifacts, so the workspace's own ignore files apply. `scan-boundaries.ts` is the injected git and filesystem boundary. `tracker.ts` compares a scan before the first live cell starts with one at each settlement. `write-hooks.ts` sends each written file through `ctx.reportToolResult()` as a `write` result. `report.ts` adds the block to the result. `model-writes.ts` records the `write` and `edit` calls the model issues while a detached cell runs.
- Containment and restored files (review findings): `scan-boundaries.ts` confines every stat and read through `workspaceFs()` over the injected `FsAccess`. A candidate's directories are resolved first and its real location must lie inside the real workspace root; the stat and the read use that resolved path, the read refuses a symlink as the last entry (`O_NOFOLLOW`) and returns nothing when the directories resolve elsewhere once it is done. A tracked path below a directory that now links out of the workspace is neither listed, read nor hooked. In a repository `workspace-scan.ts` keeps the previous scan's candidates as candidates, inside the same 5,000-path limit, so a modified tracked file the cell writes back to its HEAD content is listed and hooked; a file the cell deleted is not reported.
- Exclusions, carried candidates and the final entry (second review findings): `workspace-fs.ts` (new) holds `ScanFs` and `workspaceFs()`, the one place that decides whether a path may be stat'd and read: its real location must lie inside the real workspace root and outside `.git`, `node_modules` and the real session artifacts directory, so an in-workspace alias to one of those is not read. A read first lstats the resolved path and reads only when the file it opened is that regular file (same device and inode, checked in `FsAccess.read` before a byte is read), so a last entry swapped for a symlink is not followed where the platform has no `O_NOFOLLOW`; without an inode nothing is read. The open is non-blocking so a FIFO swapped in cannot hold it. `workspace-scan.ts` carries over only the previous scan's tracked candidates (`ScannedFiles.tracked`): an untracked file leaves `git status` only when it is deleted, committed (found by the diff) or ignored, so a file the cell makes ignored is not reported.
- Case, index deletions and a moved last entry (third review findings): `workspace-fs.ts` also excludes a resolved segment that differs from `.git` or `node_modules` only in case when the filesystem resolves both spellings to the same directory (`FsAccess.identity()`, the new device-and-inode lookup that follows links), so a case-insensitive workspace cannot reach its own `node_modules` as `NODE_MODULES` while a case-sensitive one still lists such a directory as ordinary source. `FsAccess.read()` now asks its `accept` callback asynchronously, after the open and before any read, and `workspaceFs()` answers yes only when the path still resolves to the same location, the final entry's real location is that location and an lstat still sees the checked regular file; a last entry replaced by a link to the checked file moved out of the workspace (same device and inode) is therefore not read without `O_NOFOLLOW`. What remains is documented there: the checks bracket the open, not the read, so a file moved out afterwards is read through the descriptor opened while it was inside, and a directory swapped away and back between checks is not seen. `workspace-scan.ts` reads an index deletion (`1 D.`, as after `git rm --cached`) as untracked, reads the commit diff through `--name-status`, and lets neither such a deletion nor a committed one carry a path forward from the earlier scan, so a file taken out of the index and then ignored is neither listed nor hooked.
- Unknown lookups, records git does not write, and hook rewrites (fourth review findings): `FsAccess.identity()` now returns a `PathIdentity` (`found`, `absent` for ENOENT and ENOTDIR, `unknown` for any other failure) instead of a value or undefined. `workspace-fs.ts` lets a case variant of `.git` or `node_modules` through only when one of the two spellings is confirmed absent or both are found to be different directories. A lookup that cannot tell excludes the segment, so a failed lookup of `node_modules` no longer lets `NODE_MODULES/example.ts` be read. In a repository, `workspace-scan.ts` carries an earlier tracked candidate that left `git status` without a record only when one `git --literal-pathspecs ls-files -z --cached -- <paths>` call, under the same deadline and path limit, finds it in the index. `git rm --cached` of a file HEAD does not have writes no deletion record, so before this such a file, once ignored, was still listed and hooked. When git cannot answer, nothing is carried. `tracker.ts` makes a settlement own the files it reports until its write hooks for them return, so a formatter's rewrite is never charged to a cell that settles meanwhile. The claim is taken inside the settling scan's queue slot, so no scan runs between report and claim. A scan that finds an owned file changed leaves it out and keeps its baseline, and after the hook returns, its result is recorded as hooked (`WrittenFilesWindow.hooked()`), also when the hook call failed. `release()` and `close()` drop what is left. No lock is held across the hooks: a hook may call `write` (recorded without queueing) or run an eval cell (its scans queue behind nothing of the hooking cell), so neither can deadlock. A stuck hook holds only its own file, and only until the host's `tool_result` handler deadline (120 s by default). Waiting on the hooks instead was rejected because a hook that runs a cell would wait on itself.
- Claims and cancellation (fifth review findings): a settlement now owns only the files it will send through the write hooks. `selectWrittenFiles()` in `write-hooks.ts` picks them (the first 20 source files, none on a host without the hooks) inside the settling scan's queue slot, and `tracker.ts` claims that same selection, so a change another cell makes to a file the first cell only counted, past the limit or not source, is listed and hooked by that cell instead of being skipped as owned. A file whose hook will not start is let go at once (`WrittenFilesWindow.skipped()`): the cell was cancelled, or the file could not be read back. `reportWrittenFiles()` checks the cell's signal again after reading a file back, so a cell cancelled during that read starts no new hook; a hook already running is not interrupted. A cell that closes while the selection reads its files claims nothing.
- Cancellation during a hook, and names that begin with two dots (sixth review findings): a claim is now pending until its hook is dispatched and started from then on, and `WrittenFilesWindow.start()` in `tracker.ts` is the one place that marks it, called by `reportWrittenFiles()` just before each `tool_result` dispatch. Closing a cell lets go of its pending claims and keeps a started one until that hook returns, fails or reaches the host's handler deadline; the state the hook left is then recorded as hooked. Before, a cell cancelled and closed while a formatter ran let go of that file, so a second cell could list and hook the formatter's rewrite before the first hook returned. `start()` refuses once the cell has closed, so a cell closed while its settlement was still selecting dispatches nothing, whether or not its signal was aborted. The tracker now uses the same rule as `workspace-fs.ts` (`escapesWorkspace()`, which rejects only the parent segment and the paths below it), so a file named `..draft.ts` is released and has its hook's rewrite recorded like any other file.
- Unhooked claims, model writes in flight, and the claim boundary (seventh review findings): the shared baseline now advances per file only for a change that is reported. A claim that ends without its hooks starting (the cell was cancelled, closed, its `start()` refused, or its settlement failed first) puts that file's baseline back through the scan queue, unless a later settlement has already reported a newer change to it, and a cell closed while its settlement was selecting keeps the baseline of the files it listed. Before, such a cell advanced the baseline anyway, so the next cell missed a write no one hooked. A file the cell reports it could not read back keeps the advanced baseline. `model-writes.ts` now holds a model `write` or `edit` call's file from `tool_execution_start`, which the host finishes before the call runs, through its own `tool_result` handlers, until `tool_execution_end` (`WrittenFiles.startToolCall()`, `WrittenFilesTracker.holdForCall()`). A settlement in between skips the file and keeps its baseline, and the end records the state the call left. Before, the tracker learned the path only at the end, so a detached cell settling during the call's hooks listed the file and ran a second hook chain for it. A call whose end never arrives is let go at the next `turn_start`, since a turn starts only once every call of the previous turn has ended. A claim lasts until the whole handler chain for its file returns, not until one handler's deadline, and a write a handler makes after that is reported by whichever cell settles next.
- A model write that starts during a settlement (eighth review finding): a settlement checked ownership once, before it awaited the selection, and claimed and dispatched afterwards, so a model `write` or `edit` that started on a listed file in between could get a second `tool_result` chain from the cell, run on the model's content while the model's own chain was still running. Ownership is now checked again, with no await between the check and the state change, at the selection commit (right after `select` returns, together with the claims) and at dispatch (`WrittenFilesWindow.start()`, now returning `started`, `refused` or `ceded`). `FileOwnership.watchHolds()` records the files model calls take from the settlement's first look to its claims, and a call that takes a claimed file marks the claim contested. A file taken in either window is ceded: no hook, not listed, not counted, and its baseline is kept, so the call's end records what it left and a later change is reported normally. A call that starts while the cell's hook for the file is already running gets its own chain; the cell's contested claim then records nothing when its hook returns, so a failed call's content is reported by the next cell instead of being taken as hooked. The window types and `offWindow()` moved from `tracker.ts` to the new `window.ts`.
- `packages/senpi-codemode/src/tool/run-eval-cell.ts`: a cell opens the check before kernel acquisition, waits for the first scan before its code runs, and settles it after the kernel result with its run budget and idle watchdog paused. The result gains one text part and `details.writtenFiles`. The cell's state is published from the kernel result before that settlement, so a stop, `eval_cells.list` or the wake-source count never waits on the write hooks, and a stop that arrives while they run returns the ended state and cancels nothing.
- `packages/senpi-codemode/src/tool/detached-cell-manager.ts` and `managed-cell.ts`: `complete()` takes the settling result as an optional third argument, makes it the cell's result when it lands (a new cell under the same id supersedes it) and holds the completion notification and `waitForTerminal()` until then; `stop()`, `peek()` and `list()` do not wait. A detached cell's own settlement therefore runs its hooks once, attributed to its own call, whether or not another cell ever runs.
- `packages/senpi-codemode/src/tool/detached-notification-queue.ts`: a pending notification may carry `ready`; it joins a batch only once that resolves, and `flush()` waits for those still waiting. A `ready` that rejects still delivers the notification, with the result the cell has. A detached cell's notification is ready when its own written files settled, so one cell's slow write hook no longer holds back another cell's notification.
- `packages/senpi-codemode/src/written-files/model-writes.ts` and `src/index.ts`: a model `write` or `edit` call takes its hold at `tool_call_ready`, on the path it runs with, and no longer at `tool_execution_start`. A call a `tool_call` handler blocked or redirected therefore never holds the path it was first given, so it cannot take that file from a cell that wrote it (which, with no later cell, left the cell's write unhooked). `tracker.ts` holds the file under the workspace path of its real location as well (`FsAccess.realpath`, the same lookup a scan's containment check uses, which gives the on-disk spelling), so a call that names a file in another case on a case-insensitive filesystem, or through a symlinked alias, holds and records the spelling a scan reports. `WrittenFiles.startToolCall()` and `WrittenFilesTracker.holdForCall()` are now async.
- `packages/senpi-codemode/src/extension/runtime-factory.ts`: one check per session runtime; `createExecuteTool()` reports each nested call that completed without an error, so a file a nested `write` or `edit` took through the hooks is not sent again. On a hand whose loop runs elsewhere the files are listed and no hook runs.
- `packages/senpi-codemode/src/tool/types.ts`: `EvalToolDetails.writtenFiles` (`EvalWrittenFilesDetails`).
- `packages/senpi-codemode/src/index.ts`: subscribes to `tool_execution_start`, `tool_execution_end` and `turn_start` for `model-writes.ts`.
- Bounds: one `git` process per scan killed at 500 ms, at most 5,000 changed or untracked paths per scan, at most two scans per cell; three scans in a row that fail or run over budget turn the check off for the session and the cell says so. The first 20 files are listed and hooked, the rest are counted; hook output is capped at 2,000 code points per file and 12,000 per cell.
- A detached cell delivers the same block in its completion notification, which is built from the settled result's text.
- `packages/senpi-codemode/test/gate/allowlist.json`: the eight new modules enter the extension and first-kernel import scopes; the new contract rows are listed.

### Why

- A cell can write through its `write()` helper, `fs`, `Bun.write`, a child process or a Python, Ruby or Julia cell. None of those is a `write` or `edit` call, so the files skipped diagnostics and every write hook extensions register. In a multi-harness build comparison, agents wrote most of their source from eval cells (34 file writes in one run, every file in another).
- Comparing the workspace before and after the cell is the only detection that covers every way of writing. Asking git for the changed set keeps the cost independent of how the cell wrote and bounded on a large repository.

### Why an extension could not handle it

- The cell runner is this extension: only it knows when a cell's code starts and settles, and only it assembles the result the model reads.

### Expected merge conflict zones

- LOW: `executeCell()` in `run-eval-cell.ts` (the open, the wait before `kernel.run`, the settle after `handler.finalize`, the close in `finally`).
- LOW: `complete()`, `#settle()` and `create()` in `detached-cell-manager.ts` (the pending final result).
- LOW: `createRuntime()` and `createExecuteTool()` in `runtime-factory.ts`.
- LOW: `CodemodeEvent` and the `createEvalTool` options in `index.ts`.
