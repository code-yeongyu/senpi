## 2026-11-22 - A tool can run the tool_result handlers for work it already did (senpi#7232)

### What changed

- `packages/coding-agent/src/core/extensions/types.ts`: `ExtensionToolContext.reportToolResult(report)` runs the session's `tool_result` handlers for a result the calling tool reports (`toolName`, `input`, `content`, optional `details` and `isError`). No tool runs and no `tool_call` handler is asked. The event carries the id `<calling id>/reported-<n>` and `parentToolCallId`; it emits no `tool_execution_*` event and leaves no `nestedCalls` record. It resolves to `{ toolCallId, result, failures }` and never rejects for a handler failure.
- `packages/coding-agent/src/core/extensions/runner.ts`: `createToolContext()` defines `reportToolResult` and numbers the reports of one call. `emitToolResult()` also hands each handler that threw, timed out or was interrupted to the new dispatch option `onHandlerFailure`, in addition to the extension error listeners.
- `packages/coding-agent/src/core/extensions/reported-tool-result.ts` (new, fork-only): the `ReportedToolResult`, `ReportedToolResultFailure` and `ReportedToolResultOutcome` types and `emitReportedToolResult()`, which builds the event.
- `packages/coding-agent/src/core/extensions/two-sided-forwarding.ts` (fork-only): `ToolEventDispatchOptions.onHandlerFailure`.

### Why

- A codemode cell writes files without a `write` or `edit` call (its `write()` helper, `fs`, a child process, a Python cell), so those files skipped diagnostics and every other write hook. In a multi-harness build comparison, agents wrote most of their source that way.
- The existing way to reach the hooks, `ctx.executeTool("write", ...)`, writes the file a second time: it can overwrite a change made in between, asks for permission again for a file that is already on disk, and can be blocked by a `tool_call` guard, which would hide the hook output. Running only the `tool_result` chain for the content on disk has none of those failure modes.

### Why an extension could not handle it

- `tool_result` dispatch belongs to the runner: an extension can register a handler, but nothing public lets one run the other extensions' handlers, and the per-handler deadline, abort handling and hook lifecycle events live inside `emitToolResult()`.

### Expected merge conflict zones

- LOW: `ExtensionToolContext` in `types.ts` (one method after `executeTool`, one import line).
- LOW: `createToolContext()` in `runner.ts` (one property, one counter, one import line).
- MEDIUM: the three failure branches inside the `emitToolResult()` handler loop in `runner.ts` (one added call each), the same lines senpi#7073 and oh-my-openagent#14354 touched.

## 2026-11-22 - Root exports for a reported tool result (senpi#7232)

### What changed

- `packages/coding-agent/src/index.ts`: exports the types `ReportedToolResult`, `ReportedToolResultFailure` and `ReportedToolResultOutcome` from the package root.

### Why

- They are the argument and the result of `ExtensionToolContext.reportToolResult()`, which extensions import from the package root like the rest of the tool-context API.

### Why an extension could not handle it

- The package root is the public import surface; an extension cannot add an export to it.

### Expected merge conflict zones

- LOW: one `export type { ... }` block next to the `lifecycle-api.ts` export.

## 2026-11-22 - Files an eval cell writes go through the write hooks and are listed in its result (senpi#7232)

### What changed

- `packages/senpi-codemode/src/written-files/` (new): `source-file.ts` holds the one definition of a source file (a regular file inside the session cwd, outside `.git`, `node_modules` and the session's artifacts directory, not ignored by the workspace, at most 1 MiB, whose first 8 KiB are UTF-8 text). `workspace-scan.ts` lists the candidates: in a repository through `git status --porcelain=v2` (files that differ from HEAD or are untracked, plus files committed since the previous scan), elsewhere through `git ls-files --others --exclude-standard` against an empty repository kept in the session artifacts, so the workspace's own ignore files apply. `scan-boundaries.ts` is the injected git and filesystem boundary. `tracker.ts` compares a scan before the first live cell starts with one at each settlement. `write-hooks.ts` sends each written file through `ctx.reportToolResult()` as a `write` result. `report.ts` adds the block to the result. `model-writes.ts` records the `write` and `edit` calls the model issues while a detached cell runs.
- `packages/senpi-codemode/src/tool/run-eval-cell.ts`: a cell opens the check before kernel acquisition, waits for the first scan before its code runs, and settles it after the kernel result with its run budget and idle watchdog paused. The result gains one text part and `details.writtenFiles`.
- `packages/senpi-codemode/src/extension/runtime-factory.ts`: one check per session runtime; `createExecuteTool()` reports each nested call that completed without an error, so a file a nested `write` or `edit` took through the hooks is not sent again. On a hand whose loop runs elsewhere the files are listed and no hook runs.
- `packages/senpi-codemode/src/tool/types.ts`: `EvalToolDetails.writtenFiles` (`EvalWrittenFilesDetails`).
- `packages/senpi-codemode/src/index.ts`: subscribes to `tool_execution_start` and `tool_execution_end` for `model-writes.ts`.
- Bounds: one `git` process per scan killed at 500 ms, at most 5,000 changed or untracked paths per scan, at most two scans per cell; three scans in a row that fail or run over budget turn the check off for the session and the cell says so. The first 20 files are listed and hooked, the rest are counted; hook output is capped at 2,000 code points per file and 12,000 per cell.
- A detached cell delivers the same block in its completion notification, which is built from the settled result's text.
- `packages/senpi-codemode/test/gate/allowlist.json`: the eight new modules enter the extension and first-kernel import scopes; the new contract rows are listed.

### Why

- A cell can write through its `write()` helper, `fs`, `Bun.write`, a child process or a Python, Ruby or Julia cell. None of those is a `write` or `edit` call, so the files skipped diagnostics and every write hook extensions register. In a multi-harness build comparison, agents wrote most of their source from eval cells (34 file writes in one run, every file in another).
- Comparing the workspace before and after the cell is the only detection that covers every way of writing. Asking git for the changed set keeps the cost independent of how the cell wrote and bounded on a large repository.

### Why an extension could not handle it

- The cell runner is this extension: only it knows when a cell's code starts and settles, and only it assembles the result the model reads.

### Expected merge conflict zones

- LOW: `executeCell()` in `run-eval-cell.ts` (the open, the wait before `kernel.run`, the settle before `handler.finalize`, the close in `finally`).
- LOW: `createRuntime()` and `createExecuteTool()` in `runtime-factory.ts`.
- LOW: `CodemodeEvent` and the `createEvalTool` options in `index.ts`.
