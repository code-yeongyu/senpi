## 2026-11-16 - A follow-up queued behind an error run starts, or fails typed under an account hold (senpi#6868)

### What changed

- `packages/coding-agent/src/core/queued-input-after-error.ts` (new): the decision for a follow-up still queued when a run ends on a provider error (`start`, or `fail` naming the hold); the hold derivation from the retry-fallback holds (`queuedInputHold`, a spent account else a held family); the fail loop (`failQueuedFollowUps`, which publishes each failure BEFORE its dequeue); and the `queued_input_failed` event: `queuedId`, `text`, `mode`, the client message identity and `error { code: "account_usage_limit", provider, message, resetAt? }`.
- `packages/coding-agent/src/core/agent-session.ts`: `agent_end` decides a queued follow-up after the existing continuation checks. This applies to a run whose last response ended `stopReason: "error"` from the provider (not a `failureSource: "local"` failure), with no user abort, no cancelled or blocked retry and no required compaction. Queued steering keeps its rules (a started follow-up delivers it first).
  - When the provider holds no spent account and no held family, the follow-up starts its own turn.
  - Under a hold, each queued follow-up gets a `queued_input_failed`, then is dequeued through `changeQueuedInput` (its pending-input record and `queue_update` as for any dequeue).
  - `AgentSessionEvent` carries the new event, and RPC clients receive it through the session record stream.
  - The #4036 comments, the `agent_before_settle` held-queue comment and the outlived-run warning state the new rule.

### Why

- An error run returns before the loop's follow-up poll. Under the old rule input queued behind it waited for the next prompt, so it sat queued on an idle session with nothing to drain it.
- A remote sender waiting on that prompt hung until the session closed (senpi#6868). The person at a TUI could type again; an RPC sender cannot.
- A held account must still never be asked again by a queue (senpi#3131), so under a hold the input fails typed and the sender resolves.

### Why an extension could not handle it

- The queue, the run's end and the provider holds are owned by `AgentSession`; an extension sees `agent_end` but cannot start a continuation of a session's own queue or read the retry-fallback holds.

### Expected merge conflict zones

- MEDIUM: the `agent_end` continuation block in `agent-session.ts` (next to the post-compaction exemption and retry-exhaustion continuations), the `AgentSessionEvent` union, and `_warnQueuedInputOutlivingRun`'s comment.
- LOW: new fork-only file.

## 2026-11-16 - A queued input refused under a provider hold reads failed (senpi#6868)

### What changed

- `packages/coding-agent/src/modes/rpc/client-admissions.ts`: on `queued_input_failed`, a still-queued admission is stored `completed` with the typed refusal (before the dequeue's `queue_update` could store it as completed with no outcome).
- `packages/coding-agent/src/modes/rpc/effect-outcome-copy.ts`: `queuedInputRefusedOutcome`, `{ kind: "refused", reason: <error code>, detail, action }`.
- `packages/coding-agent/src/modes/rpc/effect-status.ts`: an input whose outcome is `refused` projects as `failed`, like a dropped or cleared input.
- `packages/coding-agent/src/modes/rpc/session-record-stream.ts`: `queued_input_failed` goes out with a host-minted client message id removed, like `queue_update`.

### Why

- Review M1 of #6869: a client that reconnected or polled `get_effect_status` saw a held follow-up as `done`, contradicting the live `queued_input_failed`.

### Why an extension could not handle it

- The per-input receipts and their projection belong to the RPC host.

### Expected merge conflict zones

- LOW: the `queue_update` branch of `ClientAdmissions`; `projectAdmission`'s failed mapping; fork-only files.

## 2026-11-16 - A queued follow-up refused under a provider hold goes back to the editor (senpi#6868)

### What changed

- `packages/coding-agent/src/modes/interactive/interactive-mode.ts`: `queued_input_failed` puts the follow-up's text back in the editor, ahead of any draft, and shows a warning naming the hold.

### Why

- Review M2 of #6869: under a hold the TUI dropped the queued follow-up from its pending list with no notice. Before the change it stayed queued for the next prompt.

### Why an extension could not handle it

- The editor and the pending-message display belong to the interactive mode's event switch.

### Expected merge conflict zones

- MEDIUM: the `handleEvent` switch next to `queue_update`.

## 2026-11-16 - A hosted step-commit failure is a local failure (senpi#6868)

### What changed

- `packages/agent/src/local-failure.ts`: `isLocalFailure` is also true for a `StepCommitError` (by its brand). A run that fails because its step commit failed after the provider answered therefore ends with `failureSource: "local"`, as a queued-input port failure does (senpi#3866).
- `packages/agent/src/conformance/loop-core-manifest.ts`: `step-commit.ts` joins `LOOP_CORE_MODULES`, since `local-failure.ts` (loop core) now reads its brand; the module imports nothing and defines only the commit-failure contract.

### Why

- No provider produced that failure, so it must not be read as one. The coding-agent session starts a follow-up queued behind a provider error (senpi#6868); a fenced hosted instance must instead keep refusing its queued drain after a commit failure. The local marking also keeps it out of the turn retry and the provider health bookkeeping, which already skip local failures.

### Why an extension could not handle it

- The failure message is built inside the agent run's catch path; nothing outside the agent package sees the thrown error.

### Expected merge conflict zones

- LOW: fork-only `local-failure.ts`.
