## 2026-11-25 - Launch checks, launch key and model listing shared with the engine functions (senpi#7451)

### What changed

- `packages/coding-agent/src/main.ts`: the four checks run after argument parsing (rpc with `@file`, the `--fork`, `--rebind` and `--session-id` conflicts, the session id format) come from `src/cli/session-flag-refusal.ts` and print the same `Error:` line with exit 1. `--list-models` builds its services through `src/cli/model-listing.ts`. `auth check` runs `runAuthCheck` from `src/cli/auth-check.ts` and prints the same output with the same exit codes. A launch key delivered on the private descriptor `api-key` is read once at startup (`src/cli/launch-key.ts`) into the place `--api-key` lands; with no such descriptor nothing changes.

### Why

- The omo SDK needs an importable launch and the gated inputs of the engine functions (oh-my-openagent#14943, slice E1a-s). The exported functions and the CLI must share one core per operation, and the security design (oh-my-openagent#14946) fixes a launch key's carrier as a readable handle on a private descriptor, never argv or environment.

### Why an extension could not handle it

- These are the CLI's own startup checks and built-in root commands, run before any extension loads.

### Expected merge conflict zones

- LOW: the removed `validateForkFlags`, `validateRebindFlags` and `validateSessionIdFlags` and their call site; the `--list-models` block; the `auth check` branch of `runAuthCommand`; one block after argument diagnostics; imports.

## 2026-11-25 - The entry refuses an unusable launch key before any hop (senpi#7451)

### What changed

- `packages/coding-agent/src/cli.ts`: calls `refuseUnusableLaunchKey()` (`src/cli/launch-key.ts`) once, after the kill-guard judge and before the re-exec under Bun and the isolated child. When the private table offered the `api-key` channel a descriptor this process cannot adopt, it prints `Error: launch_key_unreadable: ...` and exits 78. Otherwise it does nothing, so every other start is unchanged.

### Why

- A hop forwards a refused descriptor as `null`, which the next process reads as "taken upstream, no key here", and that engine would start on another credential in silence. Only the process that refused the descriptor knows it was refused, so the refusal must happen there (review of senpi#7463, M1).

### Why an extension could not handle it

- It runs in the entry before any extension, runtime selection or engine import.

### Expected merge conflict zones

- LOW: one import and one call next to `dispatchKillGuardCommand`.
