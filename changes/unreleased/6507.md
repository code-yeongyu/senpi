## 2026-11-12 - A release names the session it sealed, and can refuse one it did not expect (senpi#6484)

### What changed

- `packages/coding-agent/src/modes/rpc/session-registry-claims.ts`, `session-registry-open.ts`, `session-registry-opening.ts`, `session-registry-switch.ts`: the registry registers the runtime's swap hook (see the `src/core` entry of this change), which runs in the same synchronous step that makes a replacement's session current, and brings that one entry in line there (`followRunningSession`: stored path, path claim, durable id, cwd), so after `new_session`, `switch_session`, `fork` or `clone` the host's record of the handle names the new session at once instead of at the next `list_sessions`.
- `packages/coding-agent/src/modes/rpc/session-release.ts`, `session-unload.ts`, `rpc-host-response-types.ts`: release and unload read the file they act on from the session object, never from the host's record; the release answer gains `session_id`.
- `packages/coding-agent/src/modes/rpc/session-release.ts`, `rpc-host-command-types.ts`, `method-classes-schema-host.ts`, `rpc-error-types.ts`, `rpc-types.ts` (re-exports the new code), `session-move-wire.ts`, `host-capabilities.ts`: `release_session { expectSessionId }`, compared at both lookups, refused `session_mismatch` (or `invalid_session_id` for a malformed value); capability `release_session_expect_id`. With or without the field, a release whose session is replaced while it waits (a move's export, an interrupt's settle) is refused `session_mismatch` instead of sealing the successor with the first session's staged state; that check runs before the `attached` and busy checks, whose refusals would invite a retry onto the successor. After an interrupt, every refusal that carries `dropped` also carries `taken_from`, the durable id of the session that input was taken from.
- `packages/coding-agent/src/core/session-move/finish.ts`, `packages/coding-agent/src/modes/rpc/session-move-commands.ts`: `finish` on a writable file removes the move's bundle and staged state only when that file holds an ownership entry for the move of its own session, and answers `held_this_move`.
- `packages/coding-agent/src/core/session-move/ownership.ts`, `packages/coding-agent/src/modes/rpc/session-move-commands.ts`, `session-move-request.ts`, `session-move-wire.ts`, `method-classes-schema-host.ts`, `host-capabilities.ts`: `move_session { op: "ownership" }` answers `{ ownership, sealed_for_move, held_this_move }` from one read of the session file and changes nothing; capability `move_session_ownership`. `heldByMove` is the one rule both it and `finish` use. A path with no session file is refused `not_a_session_file`, never answered `writable`.

### Why

- After a replacement in the same folder, a release sealed the new session's file and answered the old session's path, so a client acted on a session that was not released.
- A client could not say which session it meant: a release sent after the handle's session was replaced released the new one.
- A release that a replacement crossed sealed the successor with the first session's staged extension state and, after an interrupt, handed back the first session's queued input as if it were the successor's.
- A finish naming another file of the same folder erased the staged state of the session the release had sealed.
- A sender had no read-only way to learn which file a move sealed: an export rewrites the bundle with the dropped input that call passes, and a finish ends the move.

### Why an extension could not handle it

- The host's record of a handle, the release path and the move's finish are the host's own.

### Expected merge conflict zones

- LOW: the capability list in `host-capabilities.ts`, the release refusal codes in `rpc-error-types.ts`, the `release_session` entry in `rpc-host-command-types.ts`.

## 2026-11-12 - The runtime tells its host the moment a replacement's session becomes current (senpi#6484)

### What changed

- `packages/coding-agent/src/core/agent-session-runtime.ts`: `setAfterSessionSwap` registers one hook that the runtime calls in the same synchronous step that makes a replacement's session current, right after the swap and before any await, for `new_session`, `switch_session`, `fork` and `clone`.

### Why

- A host that keeps its own record of which session a handle runs could only bring that record in line later, so a command that read the record in between acted on the session that had just been replaced: a release sealed the new session's file and answered the old one's path.

### Why an extension could not handle it

- Extensions hear of a replacement through awaited events, after the swap. Nothing an extension does runs inside the swap's own synchronous step, and the record that has to follow is the host's.

### Expected merge conflict zones

- `agent-session-runtime.ts`: the lines right after the replacement's session is assigned.

### Fixed

- After `new_session`, `switch_session`, `fork` or `clone` in the same folder, `release_session` answered the old session's file while it sealed the new one; it now answers the file and the durable id (`session_id`) of the session it sealed.
- `move_session { op: "finish" }` for a writable file the move never held no longer removes the move's bundle and staged state; its answer gains `held_this_move`.

### Added

- `release_session { expectSessionId }`: the durable id of the session the caller means; a release whose route now names another session is refused `session_mismatch` and releases nothing (capability `release_session_expect_id`).
- `move_session { op: "ownership" }`: whether a session file is sealed for a move and was held by it, read without changing anything (capability `move_session_ownership`).
