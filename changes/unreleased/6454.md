## 2026-11-11 - release_session for a move answers the export in the same answer (senpi#6267)

### What changed

- `packages/coding-agent/src/modes/rpc/session-release-export.ts` (new): the `export` request a `release_session` reason `move` takes (`parseReleaseExport`, read by the rule the `export` op reads `inline` and `inlineMaxBytes`), the export it runs once the session is released (`exportForRelease`, which cannot reject: every failure becomes `{ ok: false, error, detail }`), and the capability `release_session_move_export`.
- `packages/coding-agent/src/modes/rpc/session-release.ts`: `releaseSession` reads the export request right after the reason check, before the draining and busy checks, and refuses `invalid_move_request` for one the host cannot run, with nothing interrupted, staged or sealed. Today's release moved unchanged into `claimAndSeal`; the export runs after it answered, outside its `finally`, and its outcome is `data.export`. `SessionReleasePort` gains `agentDir` and `hostedPaths`.
- `packages/coding-agent/src/modes/rpc/session-move-held-here.ts` (new): what a move step answers when the only holder of the session it met is this host's own process, which is the runtime of a session this host released that has not stopped yet. The release's export says the session had not finished stopping on this host when it was released, that nothing was exported, and to give it back with `finish` and a declined answer; a `finish` refused in that state says the session was not given back and to send `finish` again. The code stays `session_held`, and a session another process holds keeps `SessionHeldError`'s text. `exportForRelease` and the `finish` refusal of `moveSession` in `session-move-commands.ts` use it.
- `packages/coding-agent/src/modes/rpc/session-release-busy.ts` (new): the busy signals, their refusal code and data, moved out of `session-release.ts` unchanged.
- `packages/coding-agent/src/modes/rpc/session-move-commands.ts`: the `export` op's body is `exportMoveBundle` and its refusal mapping is `moveRefusalOf`, both exported so the release answers exactly what the op answers; `MoveExportPort` is the part of the move port an export needs.
- `packages/coding-agent/src/modes/rpc/session-move-request.ts`: `parseInlineRequest` holds the `inline` / `inlineMaxBytes` rule for both callers; an `export` request with no `droppedUserMessages` stays omitted instead of becoming an empty list.
- `packages/coding-agent/src/modes/rpc/session-router-routing.ts`: the release port lends the host's agent directory and hosted paths.
- `packages/coding-agent/src/modes/rpc/rpc-host-command-types.ts`, `packages/coding-agent/src/modes/rpc/rpc-host-response-types.ts`, `packages/coding-agent/src/modes/rpc/session-move-wire.ts`, `packages/coding-agent/src/modes/rpc/method-classes-schema-host.ts`, `packages/coding-agent/src/modes/rpc/host-capabilities.ts`: the request field, the answer's `export` (`RpcReleaseExportOutcome`), its inbound schema and the advertised capability.
- `packages/coding-agent/docs/rpc.md`: the release section, the `release_session` reference entry, the `export` row and the table of "Moving without a bundle folder".

### Why

- A move away from a host took two requests on that host before the bundle could travel: the release, then the export. Over a relay each is a round trip. With the export in the release's answer the sender needs one.
- The export can only fail after the seal (a runtime that still holds the file because the teardown reached its close grace, a disk error), so it is reported inside a successful release: a refusal would reopen admission on a session the host no longer has and remove the staged state the seal names.
- With the export inside the release, the holder it meets after a teardown that reached its close grace is this host's own runtime. The text of `session_held` was written for a session open in another process ("Quit it there, then try again"), so it named this host as that process; the give-back sent while that runtime was still stopping was refused with the same text.

### Why an extension could not handle it

- `release_session` and its teardown are the RPC host's own surface, and the export needs the host's hosted-session list and agent directory.

### Expected merge conflict zones

- LOW: the head of `releaseSession` in `session-release.ts`, the `export` case of `session-move-commands.ts`, the `release_session` arms in the command and response types, the capability list in `host-capabilities.ts`, and the release section of `docs/rpc.md`.

## 2026-11-11 - An export of a move whose bundle is kept keeps its dropped input (senpi#6267)

### What changed

- `packages/coding-agent/src/core/session-move/export.ts`: `droppedUserMessages` is optional on `ExportSessionForMoveOptions`. Omitted, the export keeps the list the kept bundle of the same move records, read inside the move lock before the bundle folder is replaced; a bundle that is absent, unreadable or another move's gives an empty list. Sent, an empty list included, the list is written as before.

### Why

- A release for a move can now answer the export itself and records the queued input it took out in that bundle. A caller that lost that answer does not know the list, and an export sent again would have written an empty one and erased it.

### Why an extension could not handle it

- The move core owns the bundle and the move lock.

### Expected merge conflict zones

- None upstream: `core/session-move/` is fork-only. LOW against other move work: the manifest literal in `writeMoveBundle`.
