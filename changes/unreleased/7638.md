## 2026-11-28 - The ignored-setting notice names the project's own file; the 2026-11-27 trust entry corrected (senpi#7633)

### What changed

- `packages/coding-agent/src/core/settings-manager.ts`: the notice for an executable-naming key ignored from an untrusted project names the settings file relative to the project (`.senpi/settings.json`) in its message, and no longer carries the file's absolute path.
- Correction to "2026-11-27 - Settings that name an executable need a trusted project (senpi#6362)": as merged, project trust does not default to false. `SettingsManager.create` without a trust decision uses the decision the person saved for the folder and drops an untrusted project's executable-naming keys; `fromStorage`, the constructor and the project loaders still read the project scope as trusted (`projectTrusted` defaults to `true`). The keys are the ones `EXECUTABLE_SETTING_PATHS` lists: `shellPath`, `shellCommandPrefix`, `npmCommand`, `externalEditor` and the Cursor CLI provider's `enabled` and `executablePath`.

### Why

- The notice reaches every surface that shows settings errors (RPC clients, logs), and the absolute path names the person's folders; the project-relative name is enough to find the file.
- The 2026-11-27 entry described an earlier revision of #7595. Its last commit kept project settings loading as before and drops only the executable-naming keys, so a reader of that entry expected a stronger default than the code has.

### Why an extension could not handle it

- The notice is written by the core settings manager every reader shares, and the correction is to this tracker's own record.

### Expected merge conflict zones

- LOW: `dropUntrustedProjectKeys` in `settings-manager.ts`.
