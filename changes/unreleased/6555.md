## 2026-11-12 - A move whose landing file is already taken is refused before the source releases (senpi#6471)

### What changed

- `packages/coding-agent/src/core/session-move/landing-occupied.ts` (new): `landingFile(target, sessionId)` answers what stands where a moved session would land: `free`, `predecessor` (a sealed earlier copy of the same session) or `occupied` (another session, or a copy that can still be written). `MoveTargetOccupiedError` now lives here, with its message unchanged.
- `packages/coding-agent/src/core/session-move/prepare.ts`: `prepareMove` takes `landing` (the session's id, its file name and the session folder) and, after the repository check, refuses `move_target_occupied` when `landingFile` answers `occupied`. It only reads, and a refusal readies nothing.
- `packages/coding-agent/src/core/session-move/import.ts`: `replacePredecessor` asks `landingFile` instead of its own inline check. What it refuses and what it removes are unchanged.

### Why

- An occupied landing file was found only by the import, which runs after the sender released the session, so a move that could not land still ended that session's runtime and sealed its file.
- The check before the release has to be the same question as the import's, or the two steps refuse and accept differently; one function is what makes that impossible.

### Why an extension could not handle it

- The move ledger and the session files are engine state; no extension can refuse a `prepare`.

### Expected merge conflict zones

- LOW: `replacePredecessor` and the import block at the top of `import.ts`; the body of `prepareMove`.

## 2026-11-12 - move_session prepare can be told the session and refuses an occupied landing file (senpi#6471)

### What changed

- `packages/coding-agent/src/modes/rpc/session-move-request.ts`: op `prepare` parses `session: { id, fileName }` and `sessionDir`. `session` needs `cwd`; `sessionDir` needs `session`; the id follows the move's plain-id rule and the file name the manifest's rule. Each violation is `invalid_move_request`.
- `packages/coding-agent/src/modes/rpc/session-move-commands.ts`: `prepare` picks the session folder exactly as `import` does (the named `sessionDir`, else the default folder of `cwd`) and refuses a `sessionDir` that is a file, as `import` does.
- `packages/coding-agent/src/modes/rpc/session-move-wire.ts`, `host-capabilities.ts`: the capability `move_session_prepare_occupied`, and the two fields on the `prepare` command type.
- `packages/coding-agent/src/modes/rpc/method-classes-schema-host.ts`: the `prepare` record lists `session` and `sessionDir`.
- `packages/coding-agent/docs/rpc.md`: the fields, the refusal, what a host without the capability does, and the three things the check does not settle.

### Why

- A caller needs to know before it releases a session whether the move can land, and needs a capability to know whether the host made that check.

### Why an extension could not handle it

- `move_session` is a host method; its request shape and capabilities are not extensible.

### Expected merge conflict zones

- LOW: the capability list in `host-capabilities.ts` and the pinned list in `rpc-multi-session-protocol-info.test.ts`; the `move_session` rows of `method-classes-schema-host.ts`; the `prepare` row of the command table in `docs/rpc.md`.

### Fixed

- A move whose landing file is already taken was refused only by the import, after the sender had released, sealed and exported the session. `move_session { op: "prepare" }` can now be told the session the move brings (`session: { id, fileName }`, with the `sessionDir` the import will be given) and refuses `move_target_occupied` before anything is released (capability `move_session_prepare_occupied`). A `prepare` without the new fields behaves as before, and the import keeps its own check.
