## 2026-11-11 - Each import attempt of a move stages in a folder of its own (senpi#4016)

### What changed

- `packages/coding-agent/src/core/session-move/import-staging.ts` (new): where one import attempt assembles the session it is about to land, `<sessionDir>/.move-staging/<moveId>/attempt-<random>`. An attempt stages in, commits from and removes only its own folder, whatever the outcome, and the move's folder goes once nothing else is in it. Nothing is resumed from another attempt's staged file: a retry stages again from the bundle. Before an attempt stages, staging of any move in that session folder not modified for an hour is removed, as the inline bundle staging already does; younger staging belongs to another attempt and is left alone. A cleanup that fails leaves the folder for a later sweep and never changes what the import answers.
- `packages/coding-agent/src/core/session-rebind.ts`: `rebindSessionFile` takes `beforeRename`, run after the sidecars are moved and right before the rename that lands the file; if it throws, the rewritten copy is removed, the moved sidecars go back and nothing lands. The same change as main's (senpi#6463), byte for byte.
- `packages/coding-agent/src/core/session-move/import-staging.ts`: `assertSidecarsLanded`, the import's `beforeRename`: every sidecar the manifest lists must be in the session folder before the rename, else `MovedSidecarMissingError` and nothing lands.
- `packages/coding-agent/src/core/session-move/import.ts`: staging, the payload copies and the extension-state placement move to that module; `importMovedSession` keeps the import's decisions (verify, repository, the ledger's receive and commit) and runs its staging inside it.

### Why

- An age sweep can take a live attempt's staging (a suspended machine, a clock that steps forward): inside its commit, after the staged session file was read, the commit skipped the sidecars that were no longer there and landed the session without them, accepted, so the extension state and resident blobs were lost on both sides (senpi#6445's custody review). With the check before the rename, such an attempt fails instead and the move settles failed.
- Staging runs outside the move's record lock and the folder was one per move, so two imports of one move into one session folder staged in the same place (a caller sends the import again when the first has not answered: a transport timeout shorter than the import, a settle after a restart). The second removed the whole folder and copied again while the first was still writing into it, and whichever ended first removed the folder under the other: the landed session could hold two `session_moved_in` entries, and a commit could rename a file another attempt had just replaced.

### Why an extension could not handle it

- The move core owns the import's staging and its commit point.

### Expected merge conflict zones

- None upstream: `core/session-move/` is fork-only. LOW against other move work: the staging call in `importMovedSession` and its catch.

### Fixed

- Two imports of one moved session into one folder no longer disturb each other: each attempt stages in a folder of its own, so the session lands once and whole, and staging an import that died left behind is cleaned up by age ([#6445](https://github.com/code-yeongyu/senpi/pull/6445)).
