## 2026-11-11 - Provider strict mode and scope are one registry per realm (omo#12965)

### What changed

- `packages/ai/src/provider-scope-registry.ts` (new): the browser-neutral lookup of the realm's `provider-scope/v1` registry (`lookupProviderScopeRegistry`, never creates one) and the structural check of a scope object another pi-ai copy may have placed.
- `packages/ai/src/node/provider-scope.ts`: creates that registry through `@earendil-works/pi-realm-registry`. The `AsyncLocalStorage` and both strict modes live in its closure. `activeProviderScope`, `runWithProviderScope` and `bindToProviderScope` go through it, and a scope whose members another copy shaped differently refuses like a closed one. It no longer installs scope accessors.
- `packages/ai/src/api-registry.ts`, `packages/ai/src/images-api-registry.ts`: strict mode and the active scope are read from the registry at call time; with no registry in the realm they keep the module-local strict mode and no scope. `installProviderScopeAccessor` and `installImagesProviderScopeAccessor` are removed (their only caller was `node/provider-scope.ts`). A strict mode that is not a boolean reads as on. `getApiProviderAtEvaluation` is the non-throwing lookup for registration that runs while a module evaluates.
- `packages/ai/src/compat.ts`: `registerBuiltInApiProviders()` uses `getApiProviderAtEvaluation` for its two lookups, so a pi-ai copy evaluated while the realm's strict mode is on still loads. Every runtime lookup keeps strict mode.

### Why

- A process can hold more than one copy of pi-ai in one realm (the bundled engine next to the SDK graph a plugin imports). Strict mode and the scope were module state, so a second copy resolved providers from its global registry while the first one refused.

### Why an extension could not handle it

- The state belongs to pi-ai's registries; an extension cannot make two copies of a module share module state.

### Expected merge conflict zones

- MEDIUM: the scope lookup at the top of `api-registry.ts` and `images-api-registry.ts`, and `registerBuiltInApiProviders()` in `compat.ts`.

## 2026-11-11 - pi.engine, and the kernel-tool contexts are one registry per realm (omo#12965)

### What changed

- `packages/coding-agent/src/core/extensions/types.ts`: `ExtensionAPI` gains the read-only `engine` property, typed as the engine index namespace.
- `packages/coding-agent/src/core/extensions/loader.ts`: the API object's `engine` getter returns the namespace the loader already serves extensions for `@code-yeongyu/senpi`.
- `packages/coding-agent/src/core/extensions/kernel-tools-context.ts`: `kernelToolsStorage` and `kernelToolInvokerStorage` are the two members of the realm's `kernel-tools/v1` registry. `activeKernelTools()` and `activeKernelToolInvoker()` read them and treat a store value missing its members as absent.
- `packages/coding-agent/src/core/extensions/runner.ts`: `ExtensionContext.kernelTools` reads through those two functions.
- `packages/coding-agent/src/core/extensions/builtin/kill-guard/index.ts`: passes a `warn` callback, used when the shared kill-guard record cannot be read and this copy's own record is used.

### Why

- On Node a plugin bundle's own import of the engine evaluates a second copy of it. `pi.engine` lets the plugin run on the engine that loaded it, and the kernel-tool contexts must be visible to the runner whichever copy entered them.

### Why an extension could not handle it

- This is the extension API and the loader themselves.

### Expected merge conflict zones

- LOW: the session-context block at the top of `ExtensionAPI` in `types.ts`, the first lines of the API object in `createExtensionAPI`, and the `kernelTools` getter in `runner.ts`.

## 2026-11-11 - The realm-registry package joins the build, release and publish sets; realm census (omo#12965)

### What changed

- `scripts/release-packages.mjs`, `scripts/registry-packages.mjs`, `scripts/local-release.mjs`, `scripts/senpi-publish-pack-checks.mjs`, `scripts/build-all.mjs`: `packages/realm-registry` (`@earendil-works/pi-realm-registry`, published as `@code-yeongyu/senpi-realm-registry`) is versioned in lockstep, built in the first phase, packed, published and pack-checked like telemetry.
- `scripts/check-entry-graphs.mjs`: knows the package's source directory.
- `scripts/check-realm-census.mjs`, `scripts/realm-census-roots.mjs`, `scripts/realm-census-population.mjs`, `scripts/realm-census-initializers.mjs`, `scripts/realm-census-source.mjs`, `scripts/realm-census.json` (new): the realm census. Every workspace package whose code runs in the engine realm is a root, and every module-scope binding or static class field in a root that can hold state must be classified in the table. An unclassified, stale or reclassified entry, a root set that differs from the table, or an `AsyncLocalStorage` kept per copy without a recorded ground fails `bun run check`.

### Why

- pi-ai ships on its own and machine-ops is vendored into the engine tarball, so the helper they both import has to be a published package. The census makes a new cross-copy table an explicit review decision instead of something a review has to notice.

### Why an extension could not handle it

- Release and check tooling is not an extension surface.

### Expected merge conflict zones

- LOW: the package lists in the release scripts. MEDIUM: `scripts/realm-census.json`, which every PR that adds, renames or removes module-scope state in a root must update.
