## 2026-11-21 - A pinned release's merge-back keeps main's side of a generated catalog conflict (senpi#6119)

### What changed

- `scripts/release-pin.mjs`: after the changelog rebuild, `syncPinnedReleaseIntoMain` puts main's whole generated catalog back (`restoreMainCatalog`): every path `isRegeneratedCatalogPath` (`scripts/release-test-gate.mjs`) calls generator output takes main's content, and one only the release added is removed, whether or not git conflicted on it. The catalog is one unit (`.manifest.json` hashes every data file), so a per-file resolution could pair main's manifest with a data file only the release changed. Any other conflict still fails the release with the same error.
- Tests: `scripts/release-pin-catalog-merge.test.mjs` (new) merges a pinned release whose catalog commit conflicts with main's refresh (main keeps its catalog, the tag keeps the release's), one where the release also changed and added data files git merged cleanly (main's catalog is still restored whole) and one whose conflict is in a hand-written provider file (still refused).

### Why

- A pinned release regenerates the catalog on the pinned tree; when main refreshed the same generated files later, the merge-back conflicted after the whole forced suite and nothing was published (release run 44870406986).

### Why an extension could not handle it

- These are the repository's own release scripts.

### Expected merge conflict zones

- LOW: the end of `syncPinnedReleaseIntoMain` in `scripts/release-pin.mjs`.
