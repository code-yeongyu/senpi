## 2026-11-17 - The endpoint lock directory is private to each user, and bridged to the pre-6874 one (senpi#6871)

### What changed

- `packages/coding-agent/src/modes/rpc/host-ensure-lock.ts`: the ensure lock, the senpi#4602 fence and the owner token of an endpoint live in `<tmpdir>/senpi-rpc-host-locks-<uid>` (0700, created or proven through `utils/user-private-dir.ts`) instead of `<tmpdir>/senpi-rpc-host-locks`; win32 keeps the unsuffixed name. `acquireEndpointLock(socket, ".lock" | ".fence.lock", options)` takes this user's lock, then the same lock in the legacy directory when `legacyHostEnsureLockTarget` bridges it: a real directory (opened `O_NOFOLLOW`) this uid owns and can write, no one else can write, and its group only when that is the user's own primary group (umask 002 on user-private-group systems). The legacy directory is never created.
- `packages/coding-agent/src/modes/rpc/host-endpoint-owner.ts`: the fence goes through `acquireEndpointLock`; the owner token is written to both directories while the bridge holds (each staged file removed, then created exclusively, so a symlink planted at the staged name is never followed) and read from both, the higher `generation` winning; a generation's teardown removes both copies.
- `packages/coding-agent/src/modes/rpc/host-ensure.ts`: `ensureHost` takes its lock through `acquireEndpointLock` (same budget and busy mapping).

### Why

- `<tmpdir>` is `/tmp` for every Linux user, so the old directory was shared by the whole machine: the first user created it 0755 and every other user's host died on `EACCES` creating its lock, crash-looping.
- The directory depends on the uid and `TMPDIR` only, never on `XDG_RUNTIME_DIR` (review M1): that variable differs between a login shell and cron, `sudo -u`, `docker exec` or a detached job, and disappears at logout, so two processes of one user could have held one socket's exclusive lock at once, and a long-lived host could have moved directories mid-life.
- A directory others can write into is refused rather than chmodded (review L3): entries planted while it was writable would survive the chmod and be opened by path later. A deliberately squatted per-uid name still blocks this user's ensures (the lock directory must be one agreed name); the error names the owner who can remove it.
- The legacy bridge accepts a directory its group can write only when that is the user's primary group, assuming that group is private (user-private groups); with a shared primary group its members see the legacy lock files exactly as with an older engine.
- During an upgrade an old and a new engine serve one socket; without the bridge they would take two different locks and fences and reopen the senpi#4602 adoption race (review L1).

### Why an extension could not handle it

- The lock, the fence and the owner token are the RPC host's own cross-process serialization; no extension takes part in them.

### Expected merge conflict zones

- LOW: `hostEnsureLockTarget` and the new `acquireEndpointLock` / `legacyHostEnsureLockTarget` in `host-ensure-lock.ts`; `withEndpointFence`, `readEndpointOwner` and `writeEndpointOwner` in `host-endpoint-owner.ts`; the lock acquisition in `ensureHostInKeyRoot`.

## 2026-11-17 - The bundled bun temp fallback root is private to each user (senpi#6871)

### What changed

- `packages/coding-agent/src/utils/bundled-bun.ts`: the shim temp fallback moved from `join(tmpdir(), "senpi-bundled-bun")` to `<tmpdir>/senpi-bundled-bun-<uid>` (`BundledBunHost.tempShimRoot`, from `bundledBunShimRoots()`), and it is used only after `utils/user-private-dir.ts` proves it a 0700 directory of this user; a symlink, another user's or a writable-by-others directory there is skipped. The `<agentDir>/bundled-bun` root is unchanged: created and used as before, whatever mode an older engine left it with.
- `packages/coding-agent/src/utils/user-private-dir.ts` (new): the per-user directory scheme the RPC endpoint locks, the hook spill directory and this fallback share.

### Why

- On Linux the old fallback was one `/tmp` directory for every user, so another user's first use broke this user's shims, and the directory that agent shells get on PATH sat where others could create names.

### Why an extension could not handle it

- The shim directory is appended to PATH by `getShellEnv()` before any extension runs.

### Expected merge conflict zones

- LOW: `bundledBunShimRoots`, `materialize` and `bundledBunDir` in `bundled-bun.ts`.

## 2026-11-17 - PI_TUI_DEBUG render dumps stay in the TUI's own log directory (senpi#6871)

### What changed

- `packages/tui/src/tui.ts`: `PI_TUI_DEBUG=1` render dumps go to `path.join(this.logDirectory, "tui-render")`, created 0700, instead of `path.join(os.tmpdir(), "tui")`. Each dump keeps its 0600 mode.

### Why

- On Linux `os.tmpdir()` is `/tmp` for every user, so `<tmpdir>/tui` was one directory for the whole machine. Whoever created it first owned it: every other user's render then threw `EACCES` writing its dump, and the dumps (whole screen contents) sat in a directory other users could list. `logDirectory` is already where this TUI's crash and debug logs go (the user's agent directory).

### Why an extension could not handle it

- The dump is written from inside `TuiBase`'s render loop; no extension hook sees or redirects it.

### Expected merge conflict zones

- LOW: the `PI_TUI_DEBUG` block near the end of `doRender` in `packages/tui/src/tui.ts`, if upstream changes its dump directory or contents.
