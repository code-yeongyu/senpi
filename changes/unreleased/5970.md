## 2026-11-05 - Startup refuses or takes over a held session before touching its file (senpi#5756)

### What changed

- `packages/coding-agent/src/main.ts`: `createSessionManager` admits an existing session file on its resolved path before anything loads, migrates, settles, rebinds or runs it: `openSessionOrExit` and `rebindSessionOrExit` admit first, the `--resume` picker admits the picked file before `resolveResumeTarget` can rebind it, and `--continue` and `--session-id` admit before loading. Forking only reads its source and is not admitted. A refusal exits `SESSION_HELD_EXIT_CODE` (76), a declined take-over exits 0. Prompting is offered only in interactive mode with a TTY on stdin.

### Why

The startup path only warned (#2951/#2956) when another live process held the session, so a second run of the same session started (the startup path of #5744, which #5750 fixed for `/resume`). Loading a held file before refusing could also rewrite it (version migration) or truncate the tail the holder was still appending.

### Why an extension could not handle it

Session selection and opening happen in `main.ts` before any extension is loaded.

### Expected merge conflict zones

- LOW: `openSessionOrExit`, `rebindSessionOrExit`, the `--resume`, `--continue` and `--session-id` branches of `createSessionManager`, and the `session-opening.ts` import.

## 2026-11-05 - Startup admission for a held session; held deliveries defer (senpi#5756)

### What changed

- `packages/coding-agent/src/cli/session-opening.ts`: new `admitStartupSession(sessionFile, io)` returning `open`, `cancelled` or `refused`, and `SESSION_HELD_EXIT_CODE`. It reuses `checkSessionHolders`, `describeSessionHolders`, `takeOverRefusal` and `stopSessionHolders`. Without a person to ask, or for a holder that cannot be stopped safely, it refuses and names the holder; otherwise it asks, stops the holder on take-over, and refuses if the session is still (or newly) held. A failed lookup stays advisory. `prepareSessionOpening` is unchanged.
- `packages/coding-agent/src/cli/schedule-delivery.ts`: `DeliveryResult` failures may carry `sessionHeld: true`; `runDeliveryProcess` reports it for the launch's `sessionHeldExitCode`, which only `sessionResumeDelivery` sets (`SESSION_HELD_EXIT_CODE`). `--exec` hooks are unchanged.
- `packages/coding-agent/src/cli/schedule-runner.ts`: `deliverClaimed` treats a `sessionHeld` result as a deferral: it undoes a recurring job's re-arm, puts the claimed generation back in `pending/` and returns a `deferred` event, so no `failed/` record is written.

### Why

senpi#5756: opening a held session at startup must never start a second writer. A session opened between the runner's `deferWhileSessionOpen` check and the child's admission would otherwise fail that occurrence for good.

### Why an extension could not handle it

It runs before the runtime and its extensions exist, and the runner owns the occurrence records.

### Expected merge conflict zones

- LOW: the import block of `session-opening.ts`, `DeliveryResult`/`ProcessLaunch` and the `close` handler in `schedule-delivery.ts`, the result handling in `deliverClaimed`.

## 2026-11-05 - Held-session admission helpers (senpi#5756)

### What changed

- `packages/coding-agent/src/core/foreign-session-holders.ts`: `takeOverRefusal(holders, retry = "then /resume again")` takes the retry hint, so the startup refusal says to open the session again. `/resume` output is unchanged.
- `packages/coding-agent/src/core/session-manager.ts`: new `SessionManager.recentSessionFile(cwd, sessionDir)`, the file `continueRecent` would open, found without loading it; `continueRecent` uses it.

### Why

The startup refusal reuses the `/resume` refusal reasons, and `--continue` must admit its file before loading it, since a load can migrate and rewrite the file.

### Why an extension could not handle it

Core helpers shared by `/resume`, startup and session loading.

### Expected merge conflict zones

- LOW: the `takeOverRefusal` signature; `SessionManager.continueRecent` and the new static next to it.
