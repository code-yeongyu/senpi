## 2026-10-28 - Job widgets: live widgets for background sessions and the job_widget_state event (P3)

### What changed

- `packages/coding-agent/src/core/extensions/builtin/job-widgets/`: the engine is wired to sessions. `registry-job.ts` holds one job (its text sources, its derivation runtime, replaced by a fresh one when a spec is installed, and where its spec request stands); a job joins the state once its first spec request starts. `registry.ts` (`JobWidgetRegistry`) holds one session's jobs and request controller: new output schedules a refresh at most every 250 ms, a 1 s unref'd ticker runs only while some job is open, and on exit a job settles to `done` with its last view frozen. `state-publisher.ts` sends the session's state at most once a second and only when what a client draws changed (`updatedAtMs` alone does not count). `session-host.ts` keeps the registries by session id, so a reload parks a session's registry and the next generation re-binds it; it holds the public host API `registerJobWidgetSource`, `getJobWidgetState` and `setJobWidgetAuthorResolver`. `session-author.ts` resolves the author model from `jobWidgets.model`, then the host route, then the session's current model, and sends the request through the session's model runtime with reasoning off. `extension.ts` is the new `job-widgets` builtin: on `session_start` it opens the session's widgets unless `jobWidgets.enabled` is false, and it sends `job_widget_state` through `pi.events` and `pi.rpc` (a stale-generation error alone is dropped). `public.ts` is the public barrel.
- Views carry no secrets: `runtime.ts` takes a `redactSource` option and every source's lines go through one stateful redactor per source (`SourceLineReader` feeds it each complete line in order, marks text the tap dropped unread as a cut, ends it when the source closes, and cuts lines at 4,096 characters only after redaction): the built-in private-key rule, the session's secret obfuscation, then `redactSecrets`, before lines are matched or kept, so a key that spans lines, refreshes or a dropped gap never reaches a view, and `registry-job.ts` redacts the label and stage it derives from, so no view text is ever cut through a token. `view-redact.ts` (`redactJobWidgetState`) then redacts every string of every view (only `kind` and `tone` pass through) at the publisher boundary, for each sent state and for `getJobWidgetState`; clients persist the state.
- `packages/coding-agent/src/core/extensions/builtin/index.ts`: registers `job-widgets` right after `terminal`.
- `packages/coding-agent/src/core/extensions/builtin/monitor-state-event.ts`: adds `JOB_WIDGET_STATE_EVENT = "job_widget_state"`.

### Why

- Long background jobs print numbers nobody reads until they end; this turns their output into a small live chart that every client (TUI, RPC, desktop) receives the same way.

### Why an extension could not handle it

- It is a builtin extension; outside its own directory it only adds a registry entry and an event-name constant beside the existing ones.

### Expected merge conflict zones

- LOW: the `terminal` neighborhood of `builtinExtensions` in `builtin/index.ts`, and the constants at the top of `monitor-state-event.ts`.

## 2026-10-28 - Background sessions feed job widgets (job widgets P3)

### What changed

- `packages/coding-agent/src/core/extensions/builtin/terminal/job-widget-tap.ts` (new): `tapBackgroundSession` offers a background session to the session's job widgets through `registerJobWidgetSource`: its decoded output (the retained output first, so an auto-detached command keeps what it printed in its window) feeds a text tap, its exit settles the widget, and its runtime's disposal (eviction or teardown) forgets it. `untapBackgroundSession` withdraws a session someone typed into. When the session has no widgets nothing is tapped.
- `packages/coding-agent/src/core/extensions/builtin/terminal/extension-state.ts`: `onBackgroundStart` taps the session when its runtime lives in this process (a tool child's sessions do not); new `onSessionInput` untaps it.
- `packages/coding-agent/src/core/extensions/builtin/terminal/tools/context.ts`: `onBackgroundStart` takes an optional fourth `command` argument; new optional `onSessionInput(id)`.
- `packages/coding-agent/src/core/extensions/builtin/terminal/tools/bash.ts`: both background starts (`run_in_background` and the auto-detach) pass `input.command`.
- `packages/coding-agent/src/core/extensions/builtin/terminal/tools/bash-input.ts`: calls `onSessionInput` after input or keys were written.
- `packages/coding-agent/src/core/extensions/builtin/terminal/runtime-session.ts`: `onDispose(listener)`, called once when the wrapper is disposed.

### Why

- Background sessions are the main source of long jobs worth charting; a session driven through `bash_input` is interactive, not a metric stream, and monitor watchers never become background sessions.

### Why an extension could not handle it

- The terminal owns the sessions' runtimes and their start, input, exit and eviction; nothing outside it sees them.

### Expected merge conflict zones

- LOW: `buildToolContext` in `extension-state.ts`, the two `onBackgroundStart` calls in `tools/bash.ts`, and `dispose` in `runtime-session.ts`.

## 2026-10-28 - jobWidgets settings (job widgets P3)

### What changed

- `packages/coding-agent/src/core/settings-shapes.ts`: `JobWidgetsSettings` (`enabled`, `model`, `authorAfterMs`) and `JOB_WIDGETS_DEFAULT_AUTHOR_AFTER_MS` (15000).
- `packages/coding-agent/src/core/settings-manager.ts`: `Settings.jobWidgets` and `getJobWidgetsSettings()`, which type-checks every field: `enabled` defaults to true, a blank `model` reads as unset, and `authorAfterMs` must be a finite number of at least 0, else 15000.

### Why

- The job-widgets builtin needs one switch, an optional author model and the age threshold, read the same strict way as the other settings blocks.

### Why an extension could not handle it

- Settings shapes and getters live in the settings manager.

### Expected merge conflict zones

- LOW: the `Settings` interface near `askUser`, the settings-shapes import list, and the getters after `getAskUserSettings`.

## 2026-10-28 - Job widgets public host API (job widgets P3)

### What changed

- `packages/coding-agent/src/index.ts`: re-exports `core/extensions/builtin/job-widgets/public.ts` (`registerJobWidgetSource`, `getJobWidgetState`, `setJobWidgetAuthorResolver`, `TextTap`, `JOB_WIDGET_STATE_EVENT` and the v1 contract types).

### Why

- Hosts (omo's task jobs) register jobs and their model route. The root entry is the path the extension loader maps to the running instance, so the registry's module state is shared with the host; a subpath export would load a second copy.

### Why an extension could not handle it

- The public entry point is `src/index.ts`.

### Expected merge conflict zones

- LOW: the line after the event-bus export in `src/index.ts`.

### Added
- Live widgets for long background commands: a background job that keeps printing numbers (a render, a benchmark, a test run) gets a small live chart that RPC clients receive as the `job_widget_state` extension event (`extension_events` clients), at most once a second and only when it changes. It is on by default; `jobWidgets.enabled: false` turns it off, `jobWidgets.model` picks the model, and extensions can register their own jobs with `registerJobWidgetSource` ([#4677](https://github.com/code-yeongyu/senpi/issues/4677)).
