## 2026-10-27 - Per-spawn caller env channel for daemon-started children (fixes senpi#4381)

### What changed

- `packages/coding-agent/src/modes/rpc/session-caller-env.ts` (new): the caller-passable name set (`callerEnvPassableNames`: exactly `OMOCAT_LANE` by default, plus the host's `SENPI_RPC_CALLER_ENV_NAMES`, never a session-owned or host-owned name), the boundary validators `sessionEnvShapeError` / `sessionEnvError` (16 entries, `[A-Z_][A-Z0-9_]*` names, string values of at most 4096 characters, no NUL; the refusal names the offender, cut to its first 64 characters plus `...`, and the passable set, never a value), and `inheritedSessionEnv` (a task child takes its parent's entries, its own win).
- `packages/coding-agent/src/modes/rpc/rpc-host-command-types.ts`: `open_session.env?: Record<string, string>`.
- `packages/coding-agent/src/modes/rpc/rpc-error-types.ts`, `packages/coding-agent/src/modes/rpc/rpc-types.ts`: `RPC_ERROR_INVALID_SESSION_ENV` (`invalid_session_env`).
- `packages/coding-agent/src/modes/rpc/custom-capability.ts`, `packages/coding-agent/src/modes/rpc/host-capabilities.ts`: the `session_env` host capability, advertised by the multi-session host.
- `packages/coding-agent/src/modes/rpc/session-router-open-profile.ts`: validates `env` at the wire boundary after every other profile field, resolves a `spawnedBy` parent THIS host holds open and bound, the same rule attach uses (by durable or routing id), and stores the merged result as the profile's `sessionEnv`; an opening, closing, quarantined or closed parent, or one elsewhere, contributes nothing. The opening connection is not tied to the parent: inheritance follows the attach trust boundary (any client that could attach to the parent and run its tools can open a child that inherits its env), which grants nothing attach does not.
- `packages/coding-agent/src/modes/rpc/session-registry-types.ts`: `frozenProfile` freezes `sessionEnv`.
- `packages/coding-agent/src/modes/rpc/host-daemon-env.ts`: exports `isTransientDaemonEnvName` so the passable-name configuration can refuse the names the host or a session sets itself.
- `packages/coding-agent/src/modes/rpc/host-handover-parked.ts`, `packages/coding-agent/src/modes/rpc/host-handover-parked-open.ts`: a parked session records its own `sessionEnv` (shape-checked on read) and the successor's reopen replays it as `env`, so the value follows the session and never the generation's process environment.
- `packages/coding-agent/src/modes/rpc/tool-child/context.ts`: `ChildToolContext.sessionEnv`, narrowed by value, so a tool child's bash applies the same per-session entries.
- `packages/coding-agent/src/modes/rpc/rpc-client.ts`: `openSession({ env })`.
- `packages/coding-agent/docs/rpc.md`: "Caller env per session (`session_env`)" (including the exact inheritance boundary), the `open_session` row and the `invalid_session_env` error.

### Why

- A shared daemon's child environment is built from a name allowlist (`host-daemon-env.ts`), so a caller-scoped identity such as a lane id was dropped before the child ran, and the only workaround (the daemon's own environment, or an allowlisted `OMO_*` name) would apply the first caller's value to every later client (#1195, #2208). The value needs a per-spawn channel: on the request, applied to that one session after the allowlist, never merged into the daemon or carried to a successor generation. Task children get their parent's lane without every opener repeating it, which is what makes the tools they run label their posts correctly.

### Why an extension could not handle it

- The wire boundary, the launch profile, the registry's parent lookup, the handover park and the tool child's context are host internals below extension delivery; an extension sees only its own session's context, and could neither validate the names at the boundary nor reach another session's profile.

### Expected merge conflict zones

- LOW: the `open_session` member of `RpcCommand`, the error-constant lists, the capability list in `host-capabilities.ts`, the tail of `validatedOpenProfile` and the `HandoverParkedEntry` shape; every addition is an appended optional field.

## 2026-10-27 - Session launch profile carries a per-session caller env (fixes senpi#4381)

### What changed

- `packages/coding-agent/src/main.ts`: `createCliRuntimeFactory` passes `launchProfile.sessionEnv` to the session it creates, next to `promptSurface` and `browserEngine`.

### Why

- `open_session.env` must reach the session's tool subprocesses through the launch profile, the same per-session path every other open field takes; the process environment is the wrong scope on a shared host.

### Why an extension could not handle it

- The runtime factory is the only place that turns a launch profile into an `AgentSession`.

### Expected merge conflict zones

- LOW: the `createSession` option literal in `createCliRuntimeFactory`.

## 2026-10-27 - `AgentSession.sessionEnv`, the per-session caller env (fixes senpi#4381)

### What changed

- `packages/coding-agent/src/core/agent-session-runtime.ts`: `AgentSessionLaunchProfile.sessionEnv`.
- `packages/coding-agent/src/core/agent-session-services.ts`, `packages/coding-agent/src/core/sdk.ts`: the `sessionEnv` option, passed through to the session.
- `packages/coding-agent/src/core/agent-session.ts`: `AgentSessionConfig.sessionEnv`, stored once at construction, read through `get sessionEnv()` and published to extensions through the `getSessionEnv` context action.

### Why

- The value is the session's, not the process's: a shared host runs many sessions on one process environment, so the session must hold the caller env and hand it to its tools through its own context, exactly as it hands them `browserEngine`.

### Why an extension could not handle it

- The session construction path is not reachable from the extension API.

### Expected merge conflict zones

- LOW: `AgentSessionConfig` and the constructor's first lines, the `browserEngine` getter block and the `getBrowserEngine` context-action literal in `agent-session.ts`; the option pass-through literals in `sdk.ts` and `agent-session-services.ts`.

## 2026-10-27 - The core bash tool applies the session's caller env (fixes senpi#4381)

### What changed

- `packages/coding-agent/src/core/tools/bash.ts`: `resolveSpawnContext` applies `ctx.sessionEnv` to the subprocess environment after the session's `PI_*` values, when the session environment is exposed.

### Why

- On a shared host the process environment is every session's; the variables a caller passed for ONE session must come from that session's context, as `OMO_BROWSER_ENGINE` does.

### Why an extension could not handle it

- The core bash tool's spawn environment is built inside the tool, out of reach of the extension API.

### Expected merge conflict zones

- LOW: the `exposeSessionEnvironment` block in `resolveSpawnContext`.

## 2026-10-27 - `ctx.sessionEnv` on the extension context (fixes senpi#4381)

### What changed

- `packages/coding-agent/src/core/extensions/types.ts`: `ExtensionContext.sessionEnv` (read-only, absent when the opener gave none) and the `getSessionEnv` context action.
- `packages/coding-agent/src/core/extensions/runner.ts`: the context getter, bound from the session's action like `browserEngine`.
- `packages/coding-agent/src/core/extensions/builtin/terminal/tools/bash.ts`: `SessionEnvSource.sessionEnv`; `sessionEnvOverrides` starts from it, so the PTY bash tool, its background sessions and the tool child's placement all apply the session's caller env beneath the `PI_*` values.

### Why

- Tool subprocesses are spawned by the terminal extension, which reads per-session values only through the context it is handed.

### Why an extension could not handle it

- The context contract itself is the change; an extension cannot add a getter to the context it receives.

### Expected merge conflict zones

- LOW: the `browserEngine` getter block in `ExtensionContext` and `ExtensionContextActions` (`types.ts`), the getter block in `runner.ts`, the `SessionEnvSource` type and the first line of `sessionEnvOverrides` in the terminal bash tool.

### Fixed
- The RPC host gained `open_session.env`, a per-spawn caller env channel: a client passes a small explicit set of variables (`OMOCAT_LANE` by default, more through `SENPI_RPC_CALLER_ENV_NAMES`) to the one session it opens, that session's tool subprocesses see them and a task child opened with `spawnedBy` naming it inherits them (on the same trust boundary as attaching to that session), while they are never merged into the host process environment, never carried to a successor generation through it and never visible to any other session; a name outside the passable set is refused with `invalid_session_env` ([#4381](https://github.com/code-yeongyu/senpi/issues/4381)).
