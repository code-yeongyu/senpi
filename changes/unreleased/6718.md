## 2026-11-15 - chatgpt-subscription refuses tool-item requests pre-flight (senpi#6718)

### What changed

- `packages/ai/src/api/subscription-sharing-items.ts` (new): `assertNoSharedSubscriptionToolItems` throws `SharedSubscriptionToolItemsError` (code `subscription_sharing_unsupported_input_item`) when a `chatgpt-subscription` model's request input carries `function_call`, `function_call_output`, `custom_tool_call` or `custom_tool_call_output` items.
- `packages/ai/src/api/openai-codex-responses.ts`: the guard runs after `convertResponsesMessages` in `buildRequestBody`, before any transport is chosen.
- `packages/ai/src/api/openai-responses.ts`: the same guard runs after its `convertResponsesMessages`, covering the SIWC face.
- `packages/ai/src/utils/provider-diagnostic-carrier.ts`: `subscription_sharing_unsupported_input_item` joins the SIWC error table (invalid_request, 400, recovery request).

### Why

- A shared ChatGPT subscription answers such requests with HTTP 400 invalid_request ("User subscription sharing currently supports only text, image, and file messages..."), so every agent tool session on the route — including child and reviewer sessions that inherit it — surfaced a raw provider error instead of an answer (senpi#6715). Refusing pre-flight with the typed error names the model, the offending item types, and the remedy before any request is sent.

### Why an extension could not handle it

- The decision needs the provider identity and the exact wire item types of the request body inside the API client's build step; extensions cannot intercept provider request construction.

### Expected merge conflict zones

- LOW: `openai-codex-responses.ts` and `openai-responses.ts` around the `convertResponsesMessages` call sites; `provider-diagnostic-carrier.ts` SIWC table tail.
