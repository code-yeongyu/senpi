## 2026-11-05 - Resuming a session whose process died mid-goal asks before the goal continues (senpi#5755)

### What changed

- `index.ts` `session_start`: on a `resume`, or a `startup` that opens the saved session (`--continue`, `--session`), with UI, an `active` goal whose session reopened over an interrupted run (the `interrupted-run` hold, no stale stop) is stopped through `pauseOrBlockOnUserAbort`, the same path a quit-time abort takes. The existing `Resume blocked goal?` prompt then asks before any continuation runs; a startup that stopped the goal this way takes the same prompt.
- `stop-pause.ts`: `interruptedRunHeld(ctx)` reads the session's `interrupted-run` hold.

### Why

- senpi#5755: a killed or crashed process never ran the quit-time abort, so the goal stayed `active`. Its continuation sat as a held wake that the person's first message released, and hidden goal continuations followed that message without asking.

### Why an extension could not handle it

- This is the goal extension itself.

### Expected merge conflict zones

- LOW: the goal read at the top of the `session_start` handler in `index.ts`.

### Fixed
- `/resume` of a session whose process died mid-goal, or opening it at launch with `--continue`/`--session`, now asks "Resume goal?" before any goal continuation runs, instead of continuing the goal behind the first message (#5755).
