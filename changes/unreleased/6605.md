## 2026-11-13 - A deleted session's sidecars go where its file goes (senpi#6605)

### What changed

- `packages/coding-agent/src/modes/interactive/components/session-selector.ts`: `deleteSessionFile` sends the session's sidecars where the file went, once the file is gone: every extension's state file for that session id (`extensions/<extension>/<session id>.json`) and its resident blobs (`resident-blobs/<session id>`). Where the `trash` CLI took the file they are given to it too, so a session restored from the trash comes back whole; where the file was unlinked they are removed. What could not follow comes back as `sidecarError`, beside `mediaError`, and the selector shows both; nothing the trash refused is removed for good. The listing and the removal are `sessionSidecars` and `removeSessionSidecars` in the new `packages/coding-agent/src/core/session-sidecars.ts`, which refuse an id that is not a plain session id before they look at anything. `withMediaOutcome` became `withLeftovers`.
- `packages/coding-agent/docs/sessions.md`, `packages/coding-agent/docs/session-format.md`: what goes with a session deleted from `/resume`, and what a file deleted by hand leaves behind.

### Why

- A session's sidecars are named by the session id, not by its file, so they outlived a deleted file. A session that was moved to another device, whose read-only copy was then deleted here, and that was moved back met them: the import skips a sidecar whose destination already exists and clears a predecessor's sidecars only when the predecessor's file is still there. On `main` the session landed with the goal it had when it left and the bundle's was lost; an extension the returning bundle did not list kept state the session no longer had. With senpi#6445 that import is refused until the user removes the file by hand.
- senpi#6445's fragment names one cause of such a leftover, an import that died between moving the sidecars and the rename. Deleting a copy from the selector was the ordinary one.
- They follow the file into the trash instead of being removed there because a restore that silently loses a session's goal and todo list is a loss of its own.

### Why an extension could not handle it

- The session selector's delete action is interactive-mode UI code with no extension hook, and the sidecars belong to every extension that keeps state, not to one.

### Expected merge conflict zones

- LOW: `deleteSessionFile` and its outcome helper in `session-selector.ts`, and the status message of the selector's delete handler.
