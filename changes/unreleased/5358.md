## 2026-11-01 - Kill guard runtime layer: hidden judge subcommand and exports (senpi#5349, PR #5358)

### What changed

- `packages/coding-agent/src/cli.ts` and `packages/coding-agent/src/bun/cli.ts`: both entries first call `dispatchKillGuardCommand()` from the new `src/cli/kill-guard-command.ts`. When the first argument is the hidden `__kill-guard`, it loads only `core/kill-guard/check-command.ts`, runs the check and exits. In the Node launcher that happens before any runtime re-exec or engine import; in the compiled binary's entry (`src/bun/cli.ts`, which `scripts/build-binaries.sh` compiles) it happens before the agent-directory command, provider registration and `cli-main`, so the check never creates or touches the agent dir. The command never appears in help.
- `packages/coding-agent/src/index.ts`: exports `activateKillGuardRuntime`, `releaseKillGuardRuntime`, `activeKillGuardEnvironment` and the `KillGuardRuntime` and `ActivateKillGuardRuntimeOptions` types from the new `core/kill-guard/runtime.ts`. A holder's release (session end, or the user switching the guard off) drops only that holder; the most recently activated remaining holder's layer stays active.

### Why

- The runtime shims judge the real argv of every agent-spawned `kill`, `pkill` and `killall`. In the compiled binary the only executable they can call is the binary itself, and the binary starts at `src/bun/cli.ts`, not `src/cli.ts`; without the dispatch there, every judged kill in the shipped binary failed closed (exit 126) and booted the engine against the agent dir. The codemode extension hands the same runtime layer to eval kernels through the package root.

### Why an extension could not handle it

- The compiled binary's argv dispatch is the CLI launcher itself, and the bundled codemode extension reaches the coding agent only through `@code-yeongyu/senpi`.

### Expected merge conflict zones

- LOW: the block after the static imports and before `reexecUnderBunIfNeeded()` in `src/cli.ts`; the first statements after the static imports in `src/bun/cli.ts`; the kill-guard export list in `src/index.ts`.

## 2026-11-01 - A typed `!` command runs without the kill guard's runtime layer (senpi#5349, PR #5358)

### What changed

- `packages/coding-agent/src/core/bash-executor.ts`: `BashExecutorOptions` gains an optional `env`, passed to `operations.exec()` when set. Absent, the operations choose as before.
- `packages/coding-agent/src/core/agent-session.ts`: `executeBash()` (the user's own `!` and `!!` commands, interactive and RPC) passes `getUserShellEnv()` to the default bash operations: the agent shell environment without the kill guard's PATH shims, `BASH_ENV` wrapper and judge exports. Operations an extension returns from `user_bash` still receive no `env`, as before; ones built on `createLocalBashOperations` then fall back to the agent shell environment, so their commands are judged.

### Why

- The kill guard judges what the agent runs. A command the user typed is the user's decision; judging it would restrict the user, and the command-text guard never covered `user_bash` either.

### Why an extension could not handle it

- `executeBash()` resolves the user command's environment inside the session, after any `user_bash` handler; no extension event sees or sets it.

### Expected merge conflict zones

- LOW: the options object of the `executeBashWithOperations()` call in `AgentSession.executeBash()`; the `operations.exec()` call and `BashExecutorOptions` in `bash-executor.ts`.

## 2026-11-01 - getShellEnv carries the kill guard's runtime layer (senpi#5349, PR #5358)

### What changed

- `packages/coding-agent/src/utils/shell.ts`: `getShellEnv()` passes `getUserShellEnv()` (the previous `getShellEnv()` body, now also used for the user's own `!` commands) through `withKillGuardRuntime()`. While a session has the kill guard's runtime layer active, that function puts the shim directory first on `PATH`, sets `BASH_ENV` to the wrapper (keeping a user's own `BASH_ENV` in `SENPI_KILL_GUARD_USER_BASH_ENV`), exports the judge variables, and sets `SHLVL=1` when the environment has no usable level. bash skips `BASH_ENV` in a top-level shell whose stdin is a socket (its rshd rule; Node and libuv pipes are sockets) or that sshd started, and an inherited `SHLVL` makes every agent `bash -c` a nested shell. With no active layer the environment is unchanged.

### Why

- PTY bash, the core bash tool and monitors all spawn with `getShellEnv()`. Putting the shims there makes every agent command and its children judge `kill`, `pkill` and `killall` on their real argv.

### Why an extension could not handle it

- The environment is built here before any extension can intervene, and the core bash tool that SDK consumers get never passes through the terminal extension.

### Expected merge conflict zones

- LOW: `getShellEnv()`, the new `getUserShellEnv()` below it, and the new import.

## 2026-11-01 - Kill guard judge entry shipped in the npm bundle (senpi#5349, PR #5358)

### What changed

- `scripts/build-coding-agent-bundle.mjs`: a `kill-guard-check` lazy entry (in `scripts/bundle-entry-points.mjs`) emits `core/kill-guard/check-entry.js` as `kill-guard-check.js`. The build fails when `core/kill-guard/runtime.js` lands in a different directory, because that module resolves the entry by URL.

### Why

- On an npm install the runtime shims run the judge as the host's runtime plus this entry script.

### Why an extension could not handle it

- This is the release bundle build itself.

### Expected merge conflict zones

- LOW: `lazyEntryPoints` in `scripts/bundle-entry-points.mjs` next to the `kill-guard` entry, and the directory checks in `buildBundle`.

### Added
- Kill guard runtime layer: on macOS and Linux every agent shell, monitor and eval kernel gets `kill`, `pkill` and `killall` shims first on `PATH` and a `BASH_ENV` wrapper for bash's builtin `kill` (chaining any `BASH_ENV` you set). Signal targets only known when a command runs, such as `pkill -f "$P"`, `xargs kill` or a script's `kill $PID`, are judged then and refused with exit 126. The npm install and the compiled binary both judge them. Commands you type yourself with `!` are not judged, unless an extension's `user_bash` handler runs them through operations that use the agent shell environment. `terminal.killGuard: "off"` installs nothing ([#5358](https://github.com/code-yeongyu/senpi/pull/5358))
