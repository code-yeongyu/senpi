## 2026-11-01 - Kill guard runtime layer: hidden judge subcommand and exports (senpi#5349, PR #5358)

### What changed

- `packages/coding-agent/src/cli.ts`: when the first argument is the hidden `__kill-guard`, the launcher loads only `core/kill-guard/check-command.ts`, runs the check and exits, before any runtime re-exec or engine import. The command never appears in help.
- `packages/coding-agent/src/index.ts`: exports `activateKillGuardRuntime`, `releaseKillGuardRuntime`, `deactivateKillGuardRuntime`, `activeKillGuardEnvironment` and the `KillGuardRuntime` and `ActivateKillGuardRuntimeOptions` types from the new `core/kill-guard/runtime.ts`.

### Why

- The runtime shims judge the real argv of every agent-spawned `kill`, `pkill` and `killall`. In the compiled binary the only executable they can call is the engine itself, so it needs a judge entry that answers without booting the agent. The codemode extension hands the same runtime layer to eval kernels through the package root.

### Why an extension could not handle it

- The compiled binary's argv dispatch is the CLI launcher itself, and the bundled codemode extension reaches the coding agent only through `@code-yeongyu/senpi`.

### Expected merge conflict zones

- LOW: the block after the static imports and before `reexecUnderBunIfNeeded()` in `src/cli.ts`; the kill-guard export list in `src/index.ts`.

## 2026-11-01 - getShellEnv carries the kill guard's runtime layer (senpi#5349, PR #5358)

### What changed

- `packages/coding-agent/src/utils/shell.ts`: `getShellEnv()` passes its result through `withKillGuardRuntime()`. While a session has the kill guard's runtime layer active, that function puts the shim directory first on `PATH`, sets `BASH_ENV` to the wrapper (keeping a user's own `BASH_ENV` in `SENPI_KILL_GUARD_USER_BASH_ENV`), and exports the judge variables. With no active layer the environment is unchanged.

### Why

- PTY bash, the core bash tool and monitors all spawn with `getShellEnv()`. Putting the shims there makes every agent command and its children judge `kill`, `pkill` and `killall` on their real argv.

### Why an extension could not handle it

- The environment is built here before any extension can intervene, and the core bash tool that SDK consumers get never passes through the terminal extension.

### Expected merge conflict zones

- LOW: the `return` of `getShellEnv()` and its new import.

## 2026-11-01 - Kill guard judge entry shipped in the npm bundle (senpi#5349, PR #5358)

### What changed

- `scripts/build-coding-agent-bundle.mjs`: a `kill-guard-check` lazy entry (in `scripts/bundle-entry-points.mjs`) emits `core/kill-guard/check-entry.js` as `kill-guard-check.js`. The build fails when `core/kill-guard/runtime.js` lands in a different directory, because that module resolves the entry by URL.

### Why

- On an npm install the runtime shims run the judge as the host's runtime plus this entry script.

### Why an extension could not handle it

- This is the release bundle build itself.

### Expected merge conflict zones

- LOW: `lazyEntryPoints` in `scripts/bundle-entry-points.mjs` next to the `kill-guard` entry, and the directory checks in `buildBundle`.

### Added
- Kill guard runtime layer: on macOS and Linux every agent shell, monitor and eval kernel gets `kill`, `pkill` and `killall` shims first on `PATH` and a `BASH_ENV` wrapper for bash's builtin `kill` (chaining any `BASH_ENV` you set). Signal targets only known when a command runs, such as `pkill -f "$P"`, `xargs kill` or a script's `kill $PID`, are judged then and refused with exit 126. `terminal.killGuard: "off"` installs nothing ([#5358](https://github.com/code-yeongyu/senpi/pull/5358))
