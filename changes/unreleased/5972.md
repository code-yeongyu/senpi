## 2026-11-05 - Shared sealed answer route, terminal answers and S5-4 gate folds (senpi#4249)

### What changed

- `packages/coding-agent/src/modes/rpc/secret-sealed-answer-route.ts` is new: `answerSealedFrame`, the 7.1 handling of one `mcp_presenter_secret_answer` frame, shared by the RPC host and the terminal.
- `packages/coding-agent/src/modes/rpc/secret-input-presentations.ts`: `answerSealed` delegates to the shared route.
- `packages/coding-agent/src/modes/rpc/secret-input-requests.ts`:
  - `input` reports the request id through an optional `created` callback;
  - `answerLocal` answers a request from the terminal's own input and leaves a receipt, so a later sealed answer is `already_answered`.
- `packages/coding-agent/src/modes/rpc/session-worker-host-secrets.ts`:
  - a record that claims to be a `secret_sealed_offer` but is malformed is refused, never relayed as a raiser frame;
  - worker exit unbinds the session's latch.
- `packages/coding-agent/src/modes/rpc/session-worker-secrets.ts`: `isSealedOffer` requires `hpkePk` to be a 32-byte base64url key.
- `packages/coding-agent/src/modes/rpc/secret-sealed-hpke.ts`: the open returns `update()`'s buffer itself, so the caller's zeroing reaches every plaintext byte.

### Why

- D11 secret phase (senpi#4249), row S5-5: terminal (S3-6b) parity needs the RPC host's sealed answer handling on the terminal's control endpoint. The four LOWs of S5-4's delta gate are folded here.

### Why an extension could not handle it

- The secret prompt latch, the sealed answer checks and the worker isolate protocol are host internals of the RPC mode.

### Expected merge conflict zones

- None: every path is fork-only.

## 2026-11-05 - Terminal secret prompts race sealed holders (senpi#4249)

### What changed

- `packages/coding-agent/src/modes/interactive/terminal-sealed-secrets.ts` is new:
  - `TerminalSealedSecrets`, the terminal session's sealed route over its presenter control;
  - `raceTerminalSecretInput`, which races the terminal's own input against sealed answers on one latch. The first answer wins, the losing side is dismissed, and without a sealed route the input runs alone, unchanged.
- `packages/coding-agent/src/modes/interactive/terminal-presenter-surface.ts`:
  - `attachSealedSecrets` attaches the route;
  - `mcp_presenter_secret_answer` is answered with `mcp_presenter_secret_reply` on the sender's connection only.
- `packages/coding-agent/src/modes/interactive/mcp-local-presenter.ts`: the local presenter carries `admit` and the attached `sealed` route.
- `packages/coding-agent/src/modes/interactive/session-control-rpc-commands.ts`: `mcp_presenter_secret_answer` is a terminal control command.
- `packages/coding-agent/src/modes/interactive/interactive-mode.ts`: the extension UI `input` callback goes through `raceTerminalSecretInput`.

### Why

- D11 secret phase (senpi#4249), row S5-5: on a terminal session an enrolled same-account desktop may answer a secret prompt, sealed, and the first answer wins (compatibility table, TUI own session).

### Why an extension could not handle it

- The TUI's secret input, its control endpoint and the presenter surface are host internals of the interactive mode.

### Expected merge conflict zones

- `packages/coding-agent/src/modes/interactive/interactive-mode.ts`: one call site in `createExtensionUIContext`'s `input`.
