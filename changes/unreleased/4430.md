## 2026-10-27 - A re-login releases a billing-pinned fallback (senpi#4099)

### What changed

- `packages/coding-agent/src/core/retry-fallback/controller.ts`: a fallback episode records the original provider's recovery revision when it starts. At each turn boundary, `maybeRestorePrimary` re-reads that revision first. When it has changed, the billing pin and the original's cooldown, unusable mark and circuit are released before the existing revert gate runs. A continuation boundary never releases, and a refusal pin still holds.
- `packages/coding-agent/src/core/retry-fallback/credential-recovery.ts` (fork-only): `releaseOnCredentialChange`, the release step.
- `packages/coding-agent/src/core/retry-fallback/controller-types.ts`: the optional `recoveryRevision(provider)` controller dependency and `ActiveFallbackState.recoveryRevision`.
- `packages/coding-agent/src/core/credential-recovery-revision.ts` (fork-only): the revision value. It holds each stored slot's installation-keyed HMAC credential revision plus the names of blocked slots, never key material. An unreadable store answers `undefined`, which releases nothing.
- `packages/coding-agent/src/core/agent-session.ts`: wires `recoveryRevision` to the session's credential store.

### Why

- A billing pin assumes that retrying the same account never recovers it. A re-login replaces that account, but nothing re-checked the pin, so the session stayed on the fallback until restart (senpi#4099, part of senpi#3038).

### Why an extension could not handle it

- The pin, cooldowns and circuit live inside the session's retry-fallback controller, and no extension hook reaches them.

### Expected merge conflict zones

- `maybeRestorePrimary`'s opening guards and the state literal in `applyCandidate` (`controller.ts`); the controller deps literal in the `AgentSession` constructor.
