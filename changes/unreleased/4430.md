## 2026-10-27 - A sign-in releases a billing-pinned fallback (senpi#4099)

### What changed

- `packages/coding-agent/src/core/retry-fallback/controller.ts`: a fallback episode records the original provider's login id when it starts. At each turn boundary, `maybeRestorePrimary` first runs the release step. When that releases the billing pin, the existing revert gate tries the original once. A continuation boundary never releases, and a refusal pin still holds.
- `packages/coding-agent/src/core/retry-fallback/credential-recovery.ts` (fork-only): `releaseOnCredentialChange`, the release step. At a turn boundary it reads the store only while a billing pin holds; the only other read is `applyCandidate`'s, once when an episode begins at its first fallback switch, to record the starting id. It releases only when the stored login id is non-empty and differs from the recorded one; an id that disappears ("") never releases. It clears the billing pin and the original's cooldown, unusable mark and circuit.
- `packages/coding-agent/src/core/retry-fallback/controller-types.ts`: the optional `recoveryRevision(provider)` controller dependency and `ActiveFallbackState.recoveryRevision`.
- `packages/coding-agent/src/core/credential-recovery-revision.ts` (fork-only): the revision value, the `loginId` the last sign-in stored ("" when none did). It reloads through the metadata read (`list`), so a sign-in another process wrote is seen and no key reference is resolved. An unreadable store answers `undefined`, which releases nothing.
- `packages/coding-agent/src/core/auth-storage.ts`: `set`, the login write path, stamps a fresh `loginId` (`stampLogin`) on the credential it stores.
- `packages/coding-agent/src/core/agent-session.ts`: wires `recoveryRevision` to the session's credential store.

### Why

- A billing pin assumes that retrying the same account never recovers it. A sign-in replaces that account, but nothing re-checked the pin, so the session stayed on the fallback until restart (senpi#4099, part of senpi#3038).
- The first version keyed the release on the HMAC of the stored material. A token refresh by any session on the account changes that material too, so every refresh counted as a re-login: the session switched back, sent one failing request and fell back again. Only a sign-in writes a new login id. A refresh keeps it or drops it to "" (the single-account refresh replaces the flat credential), and "" never releases, so a refresh never counts as a sign-in.

### Why an extension could not handle it

- The pin, cooldowns and circuit live inside the session's retry-fallback controller, and the login id is written by the credential store's login path; no extension hook reaches either.

### Expected merge conflict zones

- `maybeRestorePrimary`'s opening guards and the state literal in `applyCandidate` (`controller.ts`); the controller deps literal in the `AgentSession` constructor; the `appendLoginSlot` line in `AuthStorage.set`.

## 2026-10-27 - Models.login stamps a login id that refreshes never mint (senpi#4099)

### What changed

- `packages/ai/src/models.ts`: `Models.login` stamps the credential it commits through `stampLogin(appendLoginSlot(...))`, so every sign-in stores a fresh `loginId`.

### Why

- Retry fallback needs a durable "someone signed in" signal that a token refresh never produces (senpi#4099). The material HMAC moves on every refresh.

### Why an extension could not handle it

- Extension login flows commit through `Models.login`, and only that write path knows a sign-in happened.

### Expected merge conflict zones

- The `appendLoginSlot` call inside `Models.login`'s `modify`.

## 2026-10-27 - Credentials carry a login id that only a sign-in writes (senpi#4099)

### What changed

- `packages/ai/src/auth/types.ts`: optional `loginId` on `ApiKeyCredential` and `OAuthCredential`. It is not key material. A refresh keeps or drops it and never mints one: the pooled merges spread the stored credential and keep it, while the single-account refresh (`mergeRefreshed` with no accounts) replaces the flat credential and drops it.
- `packages/ai/src/auth/pool/login-id.ts` (fork-only): `stampLogin(credential)` sets a fresh random `loginId` on a credential a sign-in (a login or an account import) stores.

### Why

- Retry fallback needs a durable "someone signed in" signal that a token refresh never produces (senpi#4099). The material HMAC moves on every refresh.

### Why an extension could not handle it

- The field belongs to the stored credential contract that every login and refresh path shares.

### Expected merge conflict zones

- The `ApiKeyCredential` and `OAuthCredential` interfaces in `auth/types.ts`.

## 2026-10-27 - Account imports and the native first-run copy stamp a login id (senpi#4099)

### What changed

- `account-command.ts`: `/cursor-account import local|native` stores the updated credential through `stampLogin`, like a login.
- `native-bootstrap.ts`: the first-run copy of the native `cursor` login into the managed `native` slot stores it through `stampLogin`. The branches that leave an existing credential alone write nothing new and stamp nothing.

### Why

- Both paths add a signed-in account but wrote through `modify` without a login id, so a session that a billing failure had pinned to a fallback never saw them as a sign-in and stayed on the fallback (senpi#4099).

### Why an extension could not handle it

- These are this lane's own account-add writes.

### Expected merge conflict zones

- The `modify` callback in `importAccount` (`account-command.ts`) and in `bootstrapNativeCredential` (`native-bootstrap.ts`).
