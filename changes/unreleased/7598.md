## 2026-11-27 - Unattached session commands are refused by default (senpi#6245, senpi#5735)

### What changed

- `packages/coding-agent/src/modes/rpc/session-attachment-gate.ts`: `attachmentGate` refuses every non-exempt session command from a connection not attached to the session with `session_not_attached` (`errorData.reason`, `errorData.action`). `SENPI_RPC_REQUIRE_ATTACH` is no longer read. New `ALLOW_UNATTACHED_ENV` (`SENPI_RPC_ALLOW_UNATTACHED`), `ALLOW_UNATTACHED_REMOVAL_DATE` (2027-01-31) and `readUnattachedOptOut(env, write)`, which returns true only for `"1"` and writes one stderr line. Under the opt-out a served violation logs `(served: SENPI_RPC_ALLOW_UNATTACHED=1)`. Every `ATTACH_GATE_EXEMPT` entry carries its reason; the set is unchanged.
- `packages/coding-agent/src/modes/rpc/session-router-context.ts`: `RouterContext.allowUnattached`, read once per host when the router context is built.

### Why

- A same-user process could send `prompt`, `steer` or `follow_up` with a forged `clientMessageId` (omo's cross-device reply route) on a connection that never attached, and a client let go by a quiet takeover could keep driving the session it lost (#5735). The opt-out is a migration aid, not a security boundary: a same-user process that can restart the host can also set it.

### Why an extension could not handle it

- The attachment gate runs in the RPC router before any session or extension sees the command.

### Expected merge conflict zones

- LOW: `attachmentGate` and `ATTACH_GATE_EXEMPT` in `session-attachment-gate.ts`; the field block of `RouterContext` in `session-router-context.ts`.

### Breaking Changes
- A socket host refuses every non-exempt session command from a connection not attached to the session with `session_not_attached`; `SENPI_RPC_REQUIRE_ATTACH` is no longer read. `SENPI_RPC_ALLOW_UNATTACHED=1` serves them again until its removal after 2027-01-31; it is a migration aid, not a security boundary ([#7598](https://github.com/code-yeongyu/senpi/pull/7598))
