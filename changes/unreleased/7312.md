## 2026-11-22 - Correction: two older entries describe code that has since changed (senpi#3848, senpi#6705)

### What changed

- `packages/coding-agent/src/core/provider-composer.ts`: no code change. Correction to the `hideFreeModels` entry, whose "Why an extension could not handle it" and "Expected merge conflict zones" sections say the `whitelist` / `blacklist` filter runs inside `applyModelsJson()` and name its final `models.filter(...)` as a conflict zone. Since senpi#3829 visibility (`whitelist`, `blacklist`, `hideFreeModels`) is applied once in `composeModelProvider`'s `getAllModels`, after custom-model upserts, extension model replacement and the extension's OAuth `modifyModels`; `applyModelsJson()` no longer filters.
- `packages/coding-agent/src/core/session-cwd.ts`: no code change. Correction to the senpi#6686 entry, which says the RPC session path "reaches no synchronous filesystem call". `assertSessionCwdExists` still reaches the pre-existing `existsSync` in `getMissingSessionCwdIssue`, which `test/suite/no-sync-in-session-path.baseline.json` records; senpi#6686 added no new synchronous filesystem call to that path.

### Why

- Tracker files resolve to ours on upstream syncs, so a stale location or an overstated guarantee misleads the next sync. Released entries are not edited in place (senpi#3610); this entry supersedes the two statements above.

### Why an extension could not handle it

- Tracker accuracy only; no behavior change.

### Expected merge conflict zones

- LOW: `composeModelProvider`'s `getAllModels` visibility filter in `provider-composer.ts` (the real conflict zone for whitelist / blacklist / hideFreeModels), and `getMissingSessionCwdIssue` in `session-cwd.ts`.
