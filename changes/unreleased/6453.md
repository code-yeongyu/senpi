## 2026-11-11 - A client can ask what an unload would do, and holds are counted per client (senpi#6443)

### What changed

- `packages/coding-agent/src/modes/rpc/session-unload.ts`: `unload_session { dryRun: true }` answers what the real call would do now and changes nothing. It returns before the effect ledger and before anything is interrupted: `outcome: "ready"` or `"refused"` with the reason, detail and action the real call would carry, plus `blockers` (every standing one, in the order the real call checks them) and `interruptible` (what this call would interrupt instead). A dry run whose `effectId` the session already recorded for an unload answers what the real call replays, not the current state, so the two cannot disagree.
- `packages/coding-agent/src/modes/rpc/session-router-attachments.ts`: `otherAttachments` excludes every connection of the CALLER'S CLIENT, not only the asking connection, so the `attached` refusal of `unload_session` and `release_session` counts other clients. A connection's declared name is forgotten where its socket is gone, on every path of the release, and survives a `detach_connection`.
- `packages/coding-agent/src/modes/rpc/session-router-routing.ts`: records the client name for every `set_client_info` before the compact-flag split (`declareClientId`), so a declaration that carries a `sessionId` counts as well as one that does not, whatever the flag says; and reads `otherAttachments` from the attachments module.
- `packages/coding-agent/src/modes/rpc/session-router-context.ts`, `packages/coding-agent/src/modes/rpc/compact-socket-commands.ts`: the client each connection declared (`clientIds`), written only by `declareClientId`. The name is the connection's for its life: a later declaration without `client_id` keeps it.
- `packages/coding-agent/src/modes/rpc/rpc-client.ts`: `RpcClient.setClientInfo(width, capabilities?, clientId?)` can send the name; a bound client sends it with its `sessionId`, the form the router now records.
- `packages/coding-agent/src/modes/rpc/rpc-session-command-types.ts`, `rpc-host-command-types.ts`, `rpc-input-validation.ts`, `method-classes-schema-session.ts`, `method-classes-schema-host.ts`: the `client_id` and `dryRun` fields, their bounds and their schemas.
- `packages/coding-agent/src/modes/rpc/rpc-effect-answer-types.ts`, `host-capabilities.ts`, `packages/coding-agent/docs/rpc.md`: the dry run's answer shape and the capabilities `unload_session_dry_run` and `client_identity`.

### Why

- A client that must stop work of its own before it unloads (cancel child tasks, take queued input back, stop the run) could not ask whether the unload would be refused: it did that work first and learned only from the refusal, leaving the session running for nobody.
- A `list_sessions` row counts the asking client's own attachment, and the refusal counted per connection, so one client holding a session through two of its own connections was told another client held it.

### Why an extension could not handle it

- Both are the host's own attachment bookkeeping and refusal path.

### Expected merge conflict zones

- LOW: `otherAttachments` in `session-router-attachments.ts`, the `set_client_info` line in `admitted` (`session-router-routing.ts`), the blocker list in `session-unload.ts`, the capability list in `host-capabilities.ts`.

### Added

- `unload_session { dryRun: true }` answers what the unload would do now - `ready`, or the refusal it would give, with every standing blocker and what it would interrupt - and changes nothing. Holds are counted per client: a connection that sends `set_client_info { client_id }` is the same client as every other connection carrying that id, so a client's own second connection is never "another client" for the `attached` refusal. Capabilities `unload_session_dry_run` and `client_identity` ([#6453](https://github.com/code-yeongyu/senpi/pull/6453)).
