## 2026-11-13 - The hono and @hono/node-server overrides move past their npm audit advisories (senpi#6624)

### What changed

- `package.json` `overrides`: `hono` 4.13.11 -> 4.13.17 and `@hono/node-server` 2.1.3 -> 2.1.8. The lockfiles (`package-lock.json`, `bun.lock`) are regenerated to match.

### Why

- hono <=4.13.15 carries GHSA-4m76-xfj5-7975, GHSA-h7mg-cq63-vhpq, GHSA-3gg2-335m-rxc6 (low), GHSA-46wx-v44x-9hh2 and GHSA-4h7h-rv7c-7m2v; the fixes landed in 4.13.16 and 4.13.17 is the newest release past `min-release-age=2`. `@hono/node-server` <2.1.6 carries GHSA-qv5m-9pm6-hqp3 and GHSA-jpvv-r467-5p4w, fixed in 2.1.6+. Both were flagged by the scheduled npm audit workflow; the overrides pinned the vulnerable versions exactly, so `npm audit fix` could not move them.

### Why an extension could not handle it

- Dependency resolution for the monorepo is set by the root manifest.

### Expected merge conflict zones

- LOW: the two override lines in `package.json`; the lockfiles regenerate on any conflict.

## 2026-11-13 - The install lock's @hono/node-server override matches the root pin (senpi#6624)

### What changed

- `packages/coding-agent/package.json` `overrides`: `@hono/node-server` 2.1.1 -> 2.1.8, the same version as the root override; `packages/coding-agent/install-lock/package.json` follows. `packages/coding-agent/install-lock/package-lock.json` is regenerated to match.

### Why

- The engine tarball installs one copy of `@hono/node-server`; a pin older than the root's re-introduced the vulnerable 2.1.x range the audit flags (GHSA-qv5m-9pm6-hqp3, GHSA-jpvv-r467-5p4w). hono itself only enters through `@modelcontextprotocol/sdk`; no first-party source imports hono APIs, so nothing can depend on an API the bump removes.

### Why an extension could not handle it

- The install lock and its manifest are not extension surfaces.

### Expected merge conflict zones

- LOW: the `@hono/node-server` line in the `overrides` block of `packages/coding-agent/package.json`.
