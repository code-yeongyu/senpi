## 2026-11-13 - The hono and @hono/node-server overrides move past their npm audit advisories (senpi#6624)

### What changed

- `package.json` `overrides`: `hono` 4.13.11 -> 4.13.18 and `@hono/node-server` 2.1.3 -> 2.1.8. The lockfiles (`package-lock.json`, `bun.lock`) are regenerated to match.

### Why

- hono <=4.13.15 carries GHSA-4m76-xfj5-7975, GHSA-h7mg-cq63-vhpq, GHSA-3gg2-335m-rxc6 (low), GHSA-46wx-v44x-9hh2 and GHSA-4h7h-rv7c-7m2v (first fixes in 4.13.16). 4.13.17 additionally sits inside four medium advisories published in the hono repository's own security advisories on 2026-11-11 and named in the v4.13.18 release notes: GHSA-h25j-2p75-qj33 (>=4.13.16 <=4.13.17; mount forwards a wrong path with a custom getPath), GHSA-74fm-fwc7-3fwp (>=4.13.11 <=4.13.17; serveStatic with allowPercentInPath decodes twice), GHSA-39q9-qp46-w8xg (>=4.12.16 <=4.13.17; bodyLimit keeps every transfer chunk) and GHSA-92p4-j3wq-jmqx (>=4.5.1 <=4.13.17; validator skips on Content-Type parameter formatting). All four are patched in 4.13.18, which is past `min-release-age=2` (published 2026-11-11T08:54:02Z). These ids are not yet in the GitHub global advisory database, so `npm audit` is silent on 4.13.17 today; the same database lag turned GHSA-4m76-xfj5-7975 red 11 days after its repo publication, so the scheduled audit would flag 4.13.17 within days. `@hono/node-server` <2.1.6 carries GHSA-qv5m-9pm6-hqp3 and GHSA-jpvv-r467-5p4w, fixed in 2.1.6+. Both were flagged by the scheduled npm audit workflow; the overrides pinned the vulnerable versions exactly, so `npm audit fix` could not move them.

### Why an extension could not handle it

- Dependency resolution for the monorepo is set by the root manifest.

### Expected merge conflict zones

- LOW: the two override lines in `package.json`; the lockfiles regenerate on any conflict.

## 2026-11-13 - The install lock's @hono/node-server override matches the root pin (senpi#6624)

### What changed

- `packages/coding-agent/package.json` `overrides`: `@hono/node-server` 2.1.1 -> 2.1.8, the same version as the root override; `packages/coding-agent/install-lock/package.json` follows. `packages/coding-agent/install-lock/package-lock.json` is regenerated to match.

### Why

- The engine tarball installs one copy of `@hono/node-server`; a pin older than the root's re-introduced the vulnerable 2.1.x range the audit flags (GHSA-qv5m-9pm6-hqp3, GHSA-jpvv-r467-5p4w). hono itself only enters through `@modelcontextprotocol/sdk`; no first-party source imports hono APIs, so nothing can depend on an API the bump removes.

### Why an extension could not handle it

- The install lock and its manifest are not extension surfaces.

### Expected merge conflict zones

- LOW: the `@hono/node-server` line in the `overrides` block of `packages/coding-agent/package.json`.
