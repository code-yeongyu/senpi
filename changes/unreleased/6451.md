## 2026-11-11 - move_session status answers where an accepted move landed (senpi#6436)

### What changed

- `packages/coding-agent/src/modes/rpc/session-move-landed.ts` (new): `statusAnswer` adds `session_path`, `session_id` and `cwd` (or `landed_file: "gone"`) beside an `accepted` answer; `landedWhenFenced` gives the same fields to the `errorData` of an `import` refused `move_fenced` because its move already landed, with `revoked: true` when that copy was sealed.
- `packages/coding-agent/src/modes/rpc/session-move-commands.ts`: `status` answers through `statusAnswer`, and a refusal carries what `landedWhenFenced` returns.
- `packages/coding-agent/src/modes/rpc/session-move-wire.ts`, `packages/coding-agent/src/modes/rpc/host-capabilities.ts`: the type `RpcMoveLanded` and the capability `move_session_status_landed_path`.
- `packages/coding-agent/docs/rpc.md`: the `status` row and a paragraph on where an accepted move landed.

### Why

- Only the `import`'s own answer named the landed session. A caller that lost that answer and no longer had the bundle could not bind a session that had landed: `status` answered `{ state: "accepted" }` and a landed file nobody opened is in no listing.

### Why an extension could not handle it

- The landing target is the hidden part of the host's move record; no extension reads the move ledger.

### Expected merge conflict zones

- LOW: the `status` case and the refusal in `session-move-commands.ts`, `RpcMoveRecord` in `session-move-wire.ts`, and the capability list in `host-capabilities.ts`.

## 2026-11-11 - The read that settles a move's status also says where the move landed (senpi#6436)

### What changed

- `packages/coding-agent/src/core/session-move/landed-file.ts` (new): `readLanding` reads the file at a move's landing target once and returns what it records for the move and, when it records it, the file's path with the id and the folder its header names; `outcomeIn` is the loop `importOutcome` had, moved as it was.
- `packages/coding-agent/src/core/session-move/import.ts`: `answerMoveStatusAndLanding` returns the answer and, for an accepted move whose record names a target, that landing. The ledger already reads the file at the recorded target under the record's lock to settle an interrupted step; the landing comes from that same read. `answerMoveStatus` returns the answer alone, as before.
- `packages/coding-agent/src/core/session-move/move-ledger.ts`: `MoveFencedError` keeps the move id it was raised for.

### Why

- See the RPC entry above. The answer the sender's `finish` takes (`MoveAnswer`) is unchanged.

### Why an extension could not handle it

- The move ledger and its lock are core.

### Expected merge conflict zones

- LOW: `answerMoveStatus` in `import.ts`, and the constructor of `MoveFencedError` in `move-ledger.ts`.

### Added

- `move_session` `status` for an accepted move also answers where it landed: `session_path`, `session_id` and `cwd`, or `landed_file: "gone"` when the file there no longer records the move. An `import` refused `move_fenced` because the move already landed carries the same fields in `errorData`, with `revoked: true` when that copy was sealed. Hosts advertise `move_session_status_landed_path` ([#6451](https://github.com/code-yeongyu/senpi/pull/6451)).
