## 2026-10-27 - OAuth result pages show the host's brand, not the pi logo (senpi#4434, closes #4432)

### What changed

- `packages/ai/src/utils/oauth-page.ts`: the hard-coded upstream pi `LOGO_SVG` is gone. `setOAuthPageBrand({ name, logo? })` sets the product shown on the sign-in success and error pages; it is kept in a `processSingleton` slot. The page renders the name as text and the logo as an `<img src>` only when it is a base64 image data URI (svg+xml, png, webp, jpeg); any other logo is dropped. Without a brand the page carries no product mark.

### Why

- A desktop beta user saw the inherited pi mark on OmO's sign-in page (#4432). The page has to show the product that runs the engine.

### Why an extension could not handle it

- The callback servers render these pages inside the `ai` package's OAuth flows; no extension hook reaches them.

### Expected merge conflict zones

- MEDIUM: the top of `oauth-page.ts` and the logo markup in `renderPage`, if upstream restyles its OAuth page.

## 2026-10-27 - The brand profile names the sign-in result pages (senpi#4434, closes #4432)

### What changed

- `packages/coding-agent/src/core/brand.ts`: `BrandProfile` gains an optional `logo` (a base64 image data URI) read from `SENPI_BRAND`.
- `packages/coding-agent/src/core/model-runtime.ts`: next to `setWireIdentity`, `setOAuthPageBrand({ name: APP_NAME, logo: BRAND?.logo })` runs at module load.

### Why

- Branded hosts (OmO, the desktop) must show their own product on the OAuth result pages instead of the inherited pi mark (#4432).

### Why an extension could not handle it

- The brand profile is resolved once in core at startup; extensions load after it.

### Expected merge conflict zones

- LOW: the `setWireIdentity` line in `model-runtime.ts`; the `BrandProfile` interface in `brand.ts` (fork-only).

## 2026-10-27 - The MCP sign-in callback page carries the host brand (senpi#4434, closes #4432)

### What changed

- `packages/coding-agent/src/core/extensions/builtin/mcp/auth/callback.ts`: the loopback callback no longer answers with hard-coded `<title>senpi</title>` pages ("Return to senpi and retry"); its success and failure pages come from `oauthSuccessHtml` / `oauthErrorHtml` in `@earendil-works/pi-ai/utils/oauth-page`, so they show the host brand set with `setOAuthPageBrand` (name, and logo when the brand carries one) like the provider sign-in pages.

### Why

- Branded hosts (OmO, the desktop) showed "senpi" after an MCP server sign-in (#4432 review).

### Why an extension could not handle it

- This is the builtin MCP extension's own callback listener; the fix is inside it.

### Expected merge conflict zones

- LOW: the response lines in `LoopbackCallbackServer.#handle` (fork-native module).
