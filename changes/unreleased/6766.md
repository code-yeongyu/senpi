## 2026-11-15 - A hand runs every forwarded loop-side event's user handlers (senpi#5898)

### What changed

- `packages/coding-agent/src/core/extensions/event-placement.ts`: `LOOP_HOOK_FORWARDING` classifies every `loop`/`split` event in `EXTENSION_EVENT_PLACEMENT` as `interceptor`, `notification` or `loop-only`, with `satisfies Record<LoopSideEvent, …>`, so a new loop-side event fails to compile until it is classified. Also new: the `LoopSideEvent` and `ForwardedLoopEvent` types. `before_provider_headers` is `loop-only`.
- `packages/coding-agent/src/core/extensions/runner.ts`:
  - `hasHandlers`, `emitModelSelect`, `emitMessageEnd`, `emitProviderLoginStart` and `emitSessionMove` take an optional `only` filter. With it, only those extensions run, and the sessionless drop does not apply; `emitModelSelect` then uses the prompt options the event carries.
  - `emitBoundary` takes an optional `ForwardedBoundary` (`only`, the loop's drafts so far, its decision) to start from.
  - The new `emitForwardedContext` runs one `context` / `context_with_system` phase for `only`'s extensions, merged as `emitContext` merges that phase.
  - Without the new arguments, every existing caller's dispatch is unchanged.

### Why

- senpi#5898: the brain emits every loop event and the hand runs the user's hooks. A hosted loop's hand must run the user's handlers for every loop-side event and return the result the loop's own emit would have merged.

### Why an extension could not handle it

- The runner owns which handlers run and how their results merge. An extension cannot run another extension's handlers or read their results.

### Expected merge conflict zones

- LOW: the signatures of `hasHandlers`, `emitBoundary`, `emitSessionMove`, `emitModelSelect`, `emitMessageEnd` and `emitProviderLoginStart` in `runner.ts`, and the new `LOOP_HOOK_FORWARDING` table in `event-placement.ts`.

## 2026-11-15 - A hand serves every loop-side event of a hosted loop, and advertises the ones it wants (senpi#5898)

### What changed

- `packages/coding-agent/src/modes/rpc/loopless-loop-hooks.ts`:
  - `extensionLoopHooks` serves every event `LOOP_HOOK_FORWARDING` forwards, through `LOOP_HOOK_PARSERS` (compile-checked against `ForwardedLoopEvent`).
  - A `describe_hooks` call returns `{ wants }`: the forwarded events a user hook of the hand listens to (builtins excluded by provenance). The loop forwards only those, so a per-token `message_update` or `provider_stream_event` nobody wants never crosses the link.
  - `before_provider_headers` is refused.
- Payload parsers, one module per event family, each owning its events' parse and emit:
  - `loop-hook-lifecycle-events.ts`
  - `loop-hook-turn-events.ts`
  - `loop-hook-message-events.ts`
  - `loop-hook-session-events.ts`
  - `loop-hook-compaction-events.ts` (moved from `loop-hook-payloads.ts`)
  - `loop-hook-session-move.ts`
  - `loop-hook-provider-events.ts`

  Messages, session entries and compaction settings are parsed by `agent-message-schema.ts`, `session-entry-schema.ts` and `compaction-settings-schema.ts` (#6753). `agent-message-schema.ts` adds `isAgentMessage` (one message). New: `assistant-stream-schema.ts` (every `message_update` stream event type) and `model-schema.ts` (a model carrying `headers` is refused). `loop-hook-payloads.ts` keeps only what every family shares.
- `packages/coding-agent/src/modes/rpc/loop-hook-session-move.ts`: the move state folder crosses the link as entries (`{ path }` for a folder, `{ path, data }` for a base64 file). Paths are relative and stay inside the folder. Export returns `files`; import writes them into a fresh folder before the handlers run.
- `packages/coding-agent/src/modes/rpc/loop-hook-reply.ts`: builds each reply and refuses a reply part with no JSON form, naming where it sits, instead of dropping it.

### Why

- senpi#5898: every loop-side event a user extension listens to reaches its handler on the hand, with the effect it has in a local session.

### Why an extension could not handle it

- The loop-hook link and the call's facts belong to the loopless runtime.

### Expected merge conflict zones

- MEDIUM: the family parser modules and `loop-hook-payloads.ts` (#6753's stricter parsers land in the same module).
